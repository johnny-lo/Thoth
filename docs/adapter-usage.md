# thoth interface contract for the thin adapter

This page lists exactly what the `thoth-dispatch` skill (`plugins/thoth/skills/thoth-dispatch/SKILL.md`) relies on: commands, flags, exit codes, and `--json` keys. **Everything listed here is a promise.** Removing or renaming any of it, or changing its meaning, is a breaking change: update this page and the skill in the same commit. Adding new keys is not a breaking change. Commands, flags and keys that are not listed are not promised. Full behaviour is in `docs/phase1/usage.md` and `docs/phase2/usage.md`.

*(2026-09-30: this tool was renamed from agentctl to thoth.)*

Verified against the code on branch `adapter/thin-adapter` (2026-09-24).

## Conventions

- **Exit codes:** `0` success. `1` any error or refusal; with `--json`, stderr carries `{"ok": false, "error": "..."}`. `3` a `wait` that timed out.
- **Ids:** task and run ids are 26-character ULIDs. Any unique prefix of 6 or more characters is accepted. Evidence codes look like `E001`.
- **Profiles:** a worker account is a registered profile. `thoth profile list` shows them; `thoth profile check ID` confirms the account is logged in; `thoth profile login ID` is how a person logs it in again. The supported harnesses are `claude-code`, `codex` and `antigravity`; any other value is refused without a run row or task change. Codex login comes from `codex login status`; Antigravity login comes from `agy models` exiting 0 without either stream containing `Please sign in`. Both report null email and subscription type. Additive (MODELS-1): the same `agy models` output is the account's model list (every `id<TAB>display name` line; the `Fetching available models...` line and blank lines are skipped, a repeated id keeps its first line, agy's order is kept), and every login check that stores the plan (`profile check`, `profile login`, `dispatch`, `review start`, `spec review start`) also stores that list on the profile (`global.db` schema 4: `profiles.models`, `profiles.models_seen_at`), when the check was logged in and read at least one model; otherwise the stored list is kept. A failed write is one `warning:` line on stderr and changes nothing else. `thoth profile check ID --json` gains `models_count` (the number of models stored by this check; null when it read none or the write failed) and `models_seen_at` (when, RFC 3339 UTC; null with `models_count`), and the human line ends ` models=N` (`models=-` for null). `auto` is a reserved word, not a profile id: `thoth profile add` refuses `auto` in any letter case (`auto`, `Auto`, `AUTO`), exiting `1` saying so. Breaking change (RJ-1): `--profile auto` no longer asks Thoth to pick a profile; `dispatch`, `review start` and `spec review start` refuse it (see `thoth dispatch` below).
  Additive (TIER-1): Thoth stores each profile's subscription tier as `plan` (lower case, 1–32 of `a-z 0-9 . _ -`) with the time it was seen. It takes Claude's `subscriptionType` from the login check that `profile login`, `profile check`, `dispatch`, `review start` and `spec review start` already run, and codex's `planType` from the app-server answer of `profile usage --refresh` (and, additive QR-1, with `live-quota` on and a codex profile due for the automatic refresh, of `recommend`; Breaking change (RJ-1): the launch commands no longer refresh, since `--profile auto` is gone); agy has no source. When a check does not report a valid tier, the stored one is kept. Output a person reads writes an account as `ID (Label)` (`ID（Label）` on the Traditional Chinese pages: the report, and doctor and setup in Chinese); `Label` is the tier with its first letter upper-cased, else the profile's `account_label` (control characters removed, at most 32 characters), else nothing (just `ID`). Account ids inside `--json` never change. `profile list --json` gives every profile three more keys: `plan` (string or null), `plan_label` (the bracket text or null) and `plan_seen_at` (RFC 3339 UTC or null).
  New (PANEL-3): the login name. The same five login checks (`profile check`, `profile login`, `dispatch`, `review start`, `spec review start`), when they report logged in with an email, store its login name with the time (`global.db` schema 5: `profiles.login_name`, `profiles.login_name_seen_at`): the email trimmed, the part before the first `@`, control characters removed, at most 32 characters. Only that part is stored, never the whole email. No `@`, nothing before it, no email (codex and agy report none today), a failed check or a logged-out one keeps the stored name; each check that has one overwrites it, so a profile that changed login changes name. A failed write is one more stderr line, `warning: could not store the login name of ID: …`, and changes nothing else. The read-only commands (`profile usage` without `--refresh`, `recommend`, `status`, `report`, `doctor`, `models`) still never migrate and read a schema 4 `global.db` as no names. Three places a person reads add the name before the label: `ID (name, Label)`, `ID（名稱，Label）` in Traditional Chinese (full-width comma), `ID (name)` / `ID（名稱）` without a label, unchanged without a name: `thoth doctor`'s (and `thoth setup`'s) profile headings, the report page's account block, and the Thoth panel. Every other output (`profile list`, `profile usage`, `recommend`, `status TASK`, the launch lines, `thoth models`' decision table, the report's decision table) and every `--json` account id stays as before, and `records export` never writes it (the same id may be another login on another computer). The name goes through the existing masking like any output; it is not a secret format, so only a name equal to a known secret value shows as `[redacted:KIND]`. Additive: `profile list --json` gives every profile `login_name` (string or null) and `login_name_seen_at` (RFC 3339 UTC or null); `profile check --json` and `profile login --json` keep `email` as before. `profile list` is not an MCP tool, so the name never reaches the commander's MCP results.
- **Encoding:** spec and review files are UTF-8. A UTF-8 BOM is tolerated by `review record` only. Write files without a BOM.
- **MCP entry:** `thoth mcp` returns the same `--json` documents described on this page as tools; see [the MCP guide](mcp.md). `thoth guide` prints the commander guide; the `--json` keys are ok, version, guide.
- **Commands not listed in `thoth --help`:** `submit`, `decision`, `transcript` and `records` are left out of the Commands list of `thoth --help`, which ends with one closing paragraph naming them. They keep working with the same arguments, exit codes and `--json` output; each is documented where this page describes it (the sections `thoth transcript RUN` and `thoth records export`; `submit` and `decision` under the commands and events that mention them, and in `docs/phase1/usage.md` and `docs/phase2/usage.md`), and `thoth help COMMAND` (or `thoth COMMAND --help`) prints their help. The breaking-change rule on this page applies to them as before.
- **Secret masking (RD-1):** content is masked at the moment it leaves Thoth, never where it is stored. Two kinds of secret are recognised. (1) Seven key formats, by their prefix and length: `anthropic-key` (`sk-ant-`), `openai-key` (`sk-`), `google-api-key` (`AIza`), `github-token` (`ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`), `gitlab-token` (`glpat-`), `aws-access-key-id` (`AKIA`, `ASIA`) and `private-key` (a block from the line that starts with `-----BEGIN`, names a `PRIVATE KEY` and ends in five dashes, through its `-----END` line, or to the end of the text when there is none; extra dashes before the BEGIN line, as a diff that deletes a key file has, are allowed). A `-` or `+` right at the start of a line (a diff's deleted or added line) does not hide a key format after it. (2) Exact values: the value of every environment variable of the thoth process whose name contains `KEY`, `TOKEN`, `SECRET` or `PASSWORD` (kind `env:NAME`), and the keys stored in `$THOTH_HOME/secrets.json` (kind `thoth:aistupidlevel-api-key`, `thoth:artificialanalysis-api-key`, or `thoth:secrets.json` for any other key), each also in its JSON-escaped form; a value shorter than 8 characters (after trimming) or made only of digits is not matched. git's configuration group (`GIT_CONFIG_COUNT` whose value is a decimal number N, with `GIT_CONFIG_KEY_n` and `GIT_CONFIG_VALUE_n` for every n below N) is one unit: the values of its `GIT_CONFIG_KEY_n` are setting names, not exact values, and a worker, reviewer or spec reviewer gets the whole group, or none of it when any of its values is a known exact value or holds a key format. Each secret is replaced by `[redacted:KIND]`; KIND never carries any part of the value. The exits that mask:
  - `evidence show` (content, label, detail);
  - `review packet` (stdout, `--out` and `--json`);
  - the `.agent/review-input/` files a codex or antigravity reviewer reads (`packet.md`, `evidence/<CODE>.txt`, and, new in RVI-1, `result.json`: every key and string value of the delivered result at any depth, masked whole before it is written; its masked occurrences add to that run's `review_input` event's `kinds` without naming an evidence code; a check's recorded execution error, shown in `packet.md` and at the top of its evidence file, is masked whole too and counts under that row's code);
  - `.agent/evidence-index.json` (each `label`);
  - the prompt the runner hands every worker and reviewer (the run directory's `prompt.txt` is the same text);
  - a spec reviewer's `.agent/spec-review-input/spec.json`, and the author check's `proposed.json` and `edits.json`;
  - (RFIX-1) a fix confirmer's `.agent/review-fix-input/` files (`spec.json`, `findings.json`, `edits.json`, `fix.patch`);
  - `.agent/handoff.md` (and the run directory's copy);
  - (RD-3) the document every command prints on stdout, JSON and human alike, and the error message on stderr (`{"ok": false, "error": …}` and `error: …`);
  - (RD-3) `thoth transcript` (each line masked before a step's text is cut to 300 characters);
  - (RD-3) MCP tool results, and the large results saved under `$THOTH_HOME/mcp/out`;
  - (RD-3) `report.html` (and `--out`);
  - (RD-3) the file `thoth records export` writes;
  - (RD-4) every other line thoth itself writes to stderr: a command-line parse error (with the arguments it quotes), `warning:` lines and notes such as `wrote FILE (N bytes)`, and what `thoth mcp` writes there; they keep the markers only and write no `secret_redacted`.

  (RD-4) Keys count too: every JSON exit masks each object's keys as well as its string values; a masked key keeps its value, and when two keys of one object mask to the same text the second and later ones, in the order of their original names, get `#2`, `#3`, … (the first number that names no other key). An exit that writes `secret_redacted` counts a masked key in `kinds`. (RD-4) A human line that cuts text when it is printed (`task result`'s source quotes, `spec review show`'s `after` preview) masks the whole text before cutting it, as `thoth transcript` does; the cut may fall inside a marker, never inside a secret. (BRIEF-1) So does every `brief` (see "Briefs" under `thoth wait`), JSON and human alike: the whole source, and each note or location before its 200-character preview, is masked first, and a marker's characters count toward the length.

  The stored blobs, database rows and logs are unchanged, and with nothing to mask every output is byte for byte what it was. Only exits that hand content over once write a `secret_redacted` event (see `thoth events`); the evidence index keeps the markers only, and so do the RD-3 exits (stdout, stderr, transcript, MCP results, `report.html`, `records export`), which never write `secret_redacted`. A worker, reviewer or spec reviewer starts without the two settings of kind secret (`AISTUPIDLEVEL_API_KEY`, `ARTIFICIALANALYSIS_API_KEY`) and without any other variable the masking takes for a secret; (RD-4) nor any variable, whatever its name, whose whole value is a known exact value (an environment value taken by its name, or a value in `secrets.json`); a variable that only contains one, such as PATH, stays; every other variable reaches it as before.

  Known limits: a report field holding an unterminated private-key header masks the rest of the page into one marker (over-masking, no leak); inside a run the masker sees only the run's stripped environment, so a value that exists only in the commander's environment is caught there by the formats alone, and `thoth config set-secret` is the way to have it masked everywhere.

## Commands

### `thoth profile usage [ID] [--json]`

Additive optional flag: `--refresh` (below).

Read-only report of the last quota observations already on disk. Without `ID`,
all registered profiles are listed in `profile_id` order; an unknown ID is an
error. It reads Claude `rate_limit_warning` events from registered repositories
and Codex rollout JSONL below each profile's `sessions/` directory. For Codex,
only the account's general bucket counts: `rate_limits.limit_id` `codex`, or no
`limit_id` at all; per-model reserve buckets (for example `base_model_inference`)
are skipped. Without `--refresh` it does not refresh usage or open credentials.
With `--refresh`, the user-owned `live-quota` switch and explicit flag are both
required. A disabled switch exits 1; individual update failures still exit 0
and appear in top-level `refresh` entries `{profile_id,status,error}`. Status is
`refreshed`, `unsupported`, `skipped_live_run`, or `failed`. Antigravity's
official agy supplies successful readings with source `agy_usage`; the
official codex CLI's app-server supplies codex readings with source
`codex_app_server`; the official claude CLI's local `/usage` command (`claude
-p /usage`, stream-json output) supplies claude-code readings with source
`claude_usage`. `skipped_live_run` (codex and claude-code, `error` null) means
the profile had a queued or running run, so codex or claude was not started.

With `--json`, the shape is `{"profiles":[...]}`. Each profile object has:

| field | meaning |
|---|---|
| `profile_id` | registered profile identifier |
| `provider` | provider recorded in `global.db` |
| `harness` | `claude-code`, `codex` or `antigravity` |
| `status` | profile status from `global.db` |
| `live_runs` | runs for this account with status `queued` or `running`, across registered repositories. Behaviour change (SMALL-11 (4)): a `running` run whose runner is gone (its heartbeat is older than 15 seconds and its recorded `runner_pid` is no running thoth process) is no longer counted, before any `thoth status` has settled it; the same holds for `recommend`'s live-run count and reason and for the live quota refresh's `skipped_live_run` |
| `windows` | last known quota windows, empty when no reading exists |
| `extra_buckets` | additive: a codex profile's other quota buckets (for example `base_model_inference` / `gpt-reserve`), each `{limit_id, limit_name (string or null), windows}` with `windows` in the same shape as above, ordered by `limit_id`, read from the same rollout file as `windows`; always `[]` for a claude-code profile. Informational: `recommend` ignores it |
| `quota_state` | additive: `ok`, `unknown` or `exhausted`; same definition as the `quota_state` of a `recommend` candidate (see `thoth recommend` below) |
| `peak_percent` | additive: number only when `quota_state` is `ok`, otherwise null; same definition as the `peak_percent` of a `recommend` candidate |
| `newest_observed_at` | additive: RFC 3339 UTC time of the newest reading, or null when there is none; same definition as the `newest_observed_at` of a `recommend` candidate |
| `quota_group` | additive: selected agy model group, or null for ungrouped profiles |
| `parked_group` | additive (FC-1): for a `rate_limited` profile, the agy quota group its newest `rate_limited` quota event recorded (`detail.quota_group`); null otherwise, and null when no group was recorded (no `live_quota` reading at the time) |
| `usage_not_allowed_at` | additive (SMALL-17): for a codex profile, the RFC 3339 UTC time of the live (app-server) reading that makes ordinary usage not allowed, by the rule `recommend` uses for its `ordinary usage not allowed` reason (the newest live reading says so, is at most 24 hours old and is newer than the newest rollout reading); null otherwise, and always null for every other harness |
| `plan` | additive (TIER-1): the stored subscription tier, or null; with `--refresh` it is read after the refresh, so a tier the refresh just stored is already here |
| `plan_label` | additive (TIER-1): the text Thoth writes in brackets after the account id (see Conventions), or null |

Each `windows` entry has `name`, `used_percent` (0–100), `resets_at` (RFC
3339 UTC or `null`), `observed_at` (RFC 3339 UTC), `source` (`thoth_events`,
`codex_rollout`, `codex_app_server`, `agy_usage`, or `claude_usage`), `group` (agy group or null), and
`reset_since_observed` (whether the known reset time is
not later than now). A claude-code profile's windows take, name by name, the
newer of the run-event reading (`thoth_events`) and the live reading
(`claude_usage`). Human output shows the same facts one profile per block;
additive (SMALL-17): when `usage_not_allowed_at` is set, the line `  ordinary
usage not allowed (codex app-server, read at T)` follows the block's first
line, `T` being that time.

### `thoth recommend --role implementer|reviewer [--task TASK] [--tables] [--json]`

*(2026-09-30: ranking changed to account for quota observation freshness.)*

Additive optional flag: `--model MODEL`, the model about to be dispatched; it
selects which agy model group decides each grouped profile's quota (below).

Read-only ranking advice; it never dispatches a run. The exception (additive,
QR-1): with the `live-quota` switch on, it first refreshes the agy and codex
profiles (not `logged_out` ones) whose newest reading is more than 10 minutes
old or missing, one after another, by starting agy's `/usage` or codex's
app-server as `profile usage --refresh` does, waiting at most the smaller of
`THOTH_LIVE_QUOTA_TIMEOUT_MS` and 10 seconds each; then it opens `global.db`
for writing and stores the readings (and a codex `planType`). Claude Code
profiles are not refreshed automatically, only by `profile usage --refresh`. Nothing is
refreshed with the switch off, with `THOTH_RUN_ID` set, or when nothing is due.
A refresh never changes the exit code: each failure prints `warning: live
quota refresh for ID failed: ERROR; ranking with the previous reading` (or
`; ranking without a quota reading` when the profile had none) on stderr, with
or without `--json`, and the ranking uses the stored reading. `--json` gains
`live_quota_refresh`: `{"enabled": bool, "skipped": null|"off"|"worker",
"results": [{"profile_id", "status", "error"}]}`, `status` being `refreshed`,
`failed` or `skipped_live_run` (a codex profile with a live run) and `error` a
string or null; only due profiles are listed. For either role, `TASK`
accepts a full task ID or unique prefix of at least six characters, including
tasks with no run, looked up across every registered repository; one that
cannot be resolved exits `1`.

Breaking change (RJ-1): `recommend` lists each profile's quota facts and does
not choose a profile, model or effort for you; the commander does, and gives
them to `dispatch`, `review start` and `spec review start`.

Breaking change (RJ-2): besides the account facts, `recommend` sends the three
external tables filtered by fact only, Thoth's own usage per account, model,
effort and task type, and, with `--task`, the task's reject history (all
below). It reads the three score caches once, and with `scores-auto-refresh`
on the first call of the day refreshes a missing or 24-hour-old cache first,
exactly as `thoth models` and `thoth report` do (see `thoth models`); a
failed refresh prints one `warning: automatic score refresh failed: …` line
and the old cache is used, the exit code unchanged. `dispatch`, `review start`
and `spec review start` still read no cache and never refresh.

Breaking change (CROSS-1): by default `recommend` sends one cross table
instead of three tables: each candidate lists the models the account can run
now (`models`), each with the rows of the three filtered tables whose name
matches one of the model's own names and Thoth's own usage of that account
and model; a name no table matches leaves the cell null (Thoth does not
guess) and is listed in `unmatched`. The top-level `usage` is gone (its rows
moved under the models, each exactly once), `available_models` is gone (it is
`models` now), and the three full filtered tables are sent only with
`--tables` (`tables` is null without it, as `task_history` is without
`--task`). `--tables` changes `--json` (and the MCP tool's result) only: the
human output is the same text with or without it. The caches are read and
refreshed as before; still read-only, and still nothing picks for you.

A profile is eligible when it is active (or a parked `rate_limited` profile has
a known reset after its latest rate-limit event) and is not exhausted. `exhausted` means any window is at least 95%
and has not reset, regardless of observation age. Otherwise quota is `unknown`
when there is no reading or the newest reading is over 24 hours old, and `ok`
when it is fresh. Eligible profiles are ranked by reviewer cross-provider
preference (when applicable), no live runs, `ok` before `unknown`, lower peak
usage, then profile ID. Ineligible profiles follow in profile ID order.
Additive (FC-1): a `logged_out` profile is never eligible, with the reason
`status logged_out; run `thoth profile login ID``. A `rate_limited` antigravity
profile whose `parked_group` is known and differs from the selected
`quota_group` is "parked elsewhere": it is eligible by the ordinary rules (not
exhausted), `recovered` is false, and its reasons say `parked for quota
group G; the selected group H is unaffected` instead of the `thoth profile
check` sentence. Behaviour change (SMALL-17): only when `--model` was given
and the model matches exactly one quota group, the selected one. Without a
model (and so in `thoth status`'s profiles), or with a model that matches no
group or more than one, the best group is only a guess at what a launch will
use, so the profile is not parked elsewhere: it is ineligible unless
recovered, and its reasons keep `status rate_limited; run `thoth profile
check ID`` and add `parked for quota group G; name a model of another group
with --model to use this profile`. For any
other parked profile with a known `parked_group`, only that group's windows
decide whether it has reset since it was parked.

Additive (SMALL-9a): the quota reserve. With `quota-reserve-percent` N above
0 (see `thoth config`), a candidate is also ineligible when any of the windows
that decide its `quota_state` (an antigravity profile's selected
`quota_group`, every window otherwise; a codex profile's `extra_buckets` never
count) has `used_percent` at least 100 minus N and has not reset
(`reset_since_observed` false; an unknown reset time counts as not reset, as
for `exhausted`), whatever the reading's age. Such a candidate has
`reserve_blocked` true and one more `reasons` entry, `held back by
quota-reserve-percent N: WINDOW is P% used (observed at T), at least
100-N% and not reset` (WINDOW is `NAME (GROUP)` for agy); the human output
shows it on the `reasons:` line. No reading is not a block. Every launch
command refuses a candidate that is `reserve_blocked` for the launch's task
and model (see `thoth dispatch`). With N 0 every `reserve_blocked` is false
and nothing else changes. The 95% `exhausted` rule is unchanged.

Breaking change (RJ-1): a used-up or parked profile no longer holds back the
other profiles with the same harness or provider (the `same_provider_rotation`
setting is gone); each profile is judged on its own facts only, and the
reasons never say `same-provider rotation is off`.

With `--json`, the shape is:

```json
{"role":"implementer","task_id":null,"model":null,"candidates":[...],"live_quota_refresh":{...},"score_refresh":{...},"tables":null,"unmatched":[...],"task_history":null,"quota_reserve_percent":0}
```

Breaking change (CROSS-1, replacing RJ-2's list): the top-level fields are
exactly `role`, `task_id` (the resolved full id, null without `--task`),
`model` (the supplied value, otherwise null), `candidates` (all registered
profiles in rank order), `live_quota_refresh`, `score_refresh`, `tables`
(null without `--tables`), `unmatched`, `task_history` and (additive,
SMALL-9a) `quota_reserve_percent` (the effective `quota-reserve-percent`, an
integer, 0 when off); RJ-2's top-level `usage` is gone.
Breaking change (RJ-1): `recommended`, `recommended_launch` and `selection` are
gone; the first eligible candidate is what `recommended` used to name. Each candidate has `profile_id`,
`provider`, `harness`, `eligible`, and `reasons` (facts explaining status,
quota, live runs, and ranking), plus `quota_state` (`ok`, `unknown`, or
`exhausted`), `peak_percent` (number only for `ok`, otherwise null),
`newest_observed_at` (RFC 3339 UTC or null), `quota_group` (selected agy group,
otherwise null), `parked_group` (additive, FC-1: same definition as in `thoth
profile usage`), `recovered`, (additive, TIER-1) `plan` and
`plan_label` (same definitions as in `thoth profile usage`), (additive,
SMALL-9a) `reserve_blocked` (bool: held back by the quota reserve, above),
and the cross
table's keys (CROSS-1, below): `shared`, `windows`, `models_source`,
`models_seen_at`, `models_note`, `models`, `models_excluded` and
`usage_other_models`. Breaking change (CROSS-1): RJ-2's `available_models` is
gone; the same list is `models` now. Grouped profiles use the selected
group for state, peak and eligibility. `--model` matches agy's descriptions;
zero or multiple matches fall back to the lowest-peak non-exhausted group. A
rate-limited reason tells the operator to run `thoth profile check ID` unless
the known window reset makes it recoverable for this recommendation. The
command never changes the stored profile status. Breaking change (RJ-1): a
candidate no longer has `held`, nor RJ-1's `models` (the models Thoth used to
pick for you); CROSS-1's `models` is another thing, the account's own models
with the scores that match them, and picks nothing. The plain output no longer
has the `launch:` and `selection:` lines (the decision table is still in
`thoth models`). This remains read-only and does not dispatch anything.

The cross table (CROSS-1), per candidate:

- `shared`: the account's `thoth profile set-shared` mark (false when unset).
- `windows`: the account's quota windows, equal to `thoth profile usage
  --json`'s `windows` for the same account (`[]` without a reading).
- `models_source`, `models_seen_at`, `models_note`: `thoth models --json`'s
  `models_source`, `models_seen_at` and `note` for the same account.
- `models`: `thoth models --json`'s `models` for the same account, in order,
  minus the ones whose `unavailable` is not null; one row each with exactly
  `model`, `names`, `agent_arena`, `artificial_analysis`, `ai_stupid_level`
  and `usage`, plus (additive, AGY-1 second part) `no_effort`: `thoth models
  --json`'s `no_effort` of the same model (null, or `{"seen_at", "run_id",
  "effort", "reason"}`); such a model stays listed and eligible.
- `models_excluded`: the models left out, each `{model, seen_at, reason,
  run_id}` (`[]` when none).
- `usage_other_models`: the account's usage rows of models not in `models`
  (a claude model a run proved unavailable, a model gone from the codex cache
  or the agy list), each `{model, usage}` (`[]` when none).

`names`, in a fixed order: for claude-code, `thoth models --json`'s
`score_name` of this account and model (the model the alias's newest run
reported, a trailing `-YYYYMMDD` removed), `[]` before the alias has run; for
codex and antigravity, `[model, display_name]` (one entry when they are the
same or there is no display name). No hard-coded alias table.

### `thoth config`

Precedence for every setting: environment variable, then `$THOTH_HOME/config.json` (or `$THOTH_HOME/secrets.json` for the two API keys), then the built-in default (command-line flags beat all three). When config.json is broken, the other commands run with the defaults and print one line `warning: … cannot be used` on stderr; `config list` and `config get` print nothing on stderr and `config list` and `doctor` report the problem in their output.

`thoth config list [--json]` returns four top-level keys.
- `settings`: 18 entries in a fixed order (additive, AUTO-1a: `verify-slots` last, an integer from 1 to 8, default `1`, no environment variable, settable: how many pipeline verify runs may hold a slot at once on this computer; additive, RJ-2: `arena-url` after `aa-url`; additive, SMALL-9a: `quota-reserve-percent` after `live-quota-timeout-ms`; 15 before RJ-2), each with `key`, `value`, `source` (`env`, `file` or `default`), `env` (the variable name or `null`), `settable`, `kind` (`switch`, `language`, `text`, `integer`, `path` or `secret`), `default` (a string) and `description`. The keys, with their environment variable and default: `live-quota`, `scores-auto-refresh`, `require-reason` (switches, no variable, `off`; Breaking change (RJ-1): `same-provider-rotation` is gone, see below); `language` (`THOTH_LANG`, `en`); `claude-bin` (`THOTH_CLAUDE_BIN`, `claude`); `codex-bin` (`THOTH_CODEX_BIN`, `codex`); `agy-bin` (`THOTH_AGY_BIN`, `agy`); `live-quota-timeout-ms` (`THOTH_LIVE_QUOTA_TIMEOUT_MS`, `30000`); `quota-reserve-percent` (kind `integer`, no variable, `0`: a launch is refused on an account whose deciding quota window has used at least 100 minus this number percent and has not reset, 0 turns it off; see `thoth recommend` and `thoth dispatch`); `scores-url` (`THOTH_SCORES_URL`, `https://aistupidlevel.info/api/v1/models?period=latest&sortBy=combined`), `aa-url` (`THOTH_AA_URL`, `https://artificialanalysis.ai/api/v2/language/models/free?page=`) and `arena-url` (`THOTH_ARENA_URL`, `https://huggingface.co`: the Hugging Face Hub that serves the Agent Arena dataset; a trailing `/` is ignored; the index is `BASE/api/datasets/lmarena-ai/leaderboard-dataset` and each board `BASE/datasets/lmarena-ai/leaderboard-dataset/resolve/SHA/BOARD/latest-00000-of-00001.parquet`); `machine-name` (`THOTH_MACHINE_NAME`, the host name) and `records-dir` (`THOTH_RECORDS_DIR`, `unset`); `home` (`THOTH_HOME`, `~/.thoth`; read-only); `aistupidlevel-api-key` (`AISTUPIDLEVEL_API_KEY`) and `artificialanalysis-api-key` (`ARTIFICIALANALYSIS_API_KEY`), whose `value` is only `set` or `unset`, never the key; stored with `set-secret`, source `file` means secrets.json.
- `config_file`: `path`, `exists`, `ok`, `error` (`null` when ok) and `unknown_keys` (sorted). Breaking change (RJ-1): a `same_provider_rotation` left in an old config.json has no effect and is not listed in `unknown_keys` (`doctor`'s config item stays ok and leaves it out of `stored_keys`; its `data` no longer has `same_provider_rotation`); `config get`, `set` and `unset` of `same-provider-rotation` exit `1` saying the setting was removed and has no effect, and `config set` of another key keeps it in the file.
- `secrets_file` (CFG-2): `path` (`$THOTH_HOME/secrets.json`), `exists`, `ok`, `error` (`null` when ok), `unknown_keys` (the keys in the file other than `aistupidlevel_api_key` and `artificialanalysis_api_key`, sorted), `private` (Linux: whether only the owner can read it; `null` on Windows and when the file does not exist) and `read` (the opposite of "THOTH_RUN_ID is set"). While THOTH_RUN_ID is set the file is not opened: `ok`, `error` and `unknown_keys` are `null`, `path`, `exists` and `private` are still filled, and the two keys resolve from the environment only.
- `elsewhere`: `profiles` (`count`, `null` when global.db does not exist or cannot be read; `command`) and `checks` (`null` when the working directory is not an initialized repository or its database cannot be read; otherwise `total`, `approved`, `protected_patterns`, `command`). Read-only: nothing is created or migrated.

`thoth config get KEY [--json]` returns `key` and `value` for any of the 18 keys.

`thoth config set KEY VALUE [--json]` returns `ok`, `key`, `value`, `previous`, `notice` and `shadowed_by` (the environment variable that overrides the stored value in this environment, or `null`). `previous` is `on`/`off` for a switch and the previously stored value as a string (or `null`) for the others; `notice` is `null` except when one of the three switches is turned on. Breaking change (RJ-1): `require-reason` now asks for `--reason` on every `dispatch`, `review start` and `spec review start`, not only on a launch that differs from a recommendation. Values: switches `on` or `off`; text (`claude-bin`, `codex-bin`, `agy-bin`, `scores-url`, `aa-url`, `arena-url`) a non-empty string; `machine-name` 1 to 64 characters from `A-Z a-z 0-9 . _ -`, not starting with `.` or `-` (else `invalid setting value '…' for machine-name`); `records-dir` an absolute path (else `invalid setting value '…' for records-dir: must be an absolute path`); `live-quota-timeout-ms` a whole number of at least 1; `quota-reserve-percent` a whole number from 0 to 99 (`100`, `-1`, `abc`, `5.5` and an empty value exit `1` with `invalid setting value '…' for quota-reserve-percent: a whole number from 0 to 99`; a config.json edited by hand to a number outside 0 to 99 or to a non-number reads as unset, `0`, so a bad file never refuses a launch; `notice` stays `null`); `language` `en` or `zh-TW` (any letter case, `zh_tw` too). `home` cannot be stored; the two API keys cannot be stored with `config set` (use `config set-secret`). The commander (agent) must not execute `config set`, `config unset`, `config set-secret` or `config unset-secret`, and must never ask the human to paste a key into the conversation; it may only ask a human to run them in a terminal.

`thoth config unset KEY [--json]` removes the stored value so the environment variable or default applies. It returns `ok`, `key`, `previous` (the stored value as a string, or `null`), `value` and `source` after the removal. It does not create config.json.

`thoth config set-secret KEY [--json]` (CFG-2) stores one of the two API keys in `$THOTH_HOME/secrets.json` (created readable by the owner only on Linux). KEY is `aistupidlevel-api-key` or `artificialanalysis-api-key`. The value is never taken from the command line: when stdin is a terminal it is typed at a hidden prompt (nothing is echoed), otherwise exactly one line is read from stdin (`thoth config set-secret KEY < FILE`). The value must be one line, not empty, a single token without whitespace or control characters, at most 1024 bytes; one trailing `\n` or `\r\n` is dropped. It returns `ok`, `key`, `value` (always `set`), `source` (always `file`), `previous` (`set` or `unset`: whether the file already held this key), `shadowed_by` (the environment variable when it is set and not blank in this environment, else `null`) and `path` (the absolute path of secrets.json). Refused, exit `1`, nothing written: a value given after KEY on the command line (it is not echoed back); an unknown KEY (not echoed back either); a KEY that is not a secret; THOTH_RUN_ID set; a secrets.json that is not a JSON object; a terminal whose echo cannot be switched off (use `< FILE`). No output ever contains the value.

`thoth config unset-secret KEY [--json]` removes the stored key so the environment variable, if any, applies. It returns `ok`, `key`, `previous` (`set` or `unset`), `value` and `source` after the removal. It does not create secrets.json and keeps the file (as `{}`) after the last key; it is refused while THOTH_RUN_ID is set.

While THOTH_RUN_ID is set, secrets.json is not used: a worker's thoth sees only the environment (the file is read only to mask its values in output).

### `thoth doctor [--shell powershell|cmd|bash|sh] [--json]`

New (SETUP-1). A read-only health check: it creates no directory, writes no database and changes no file.

Exit code: `0` when no item is `fail` (`warn` and `unknown` do not count); `1` when at least one item is `fail`; `1` with `{"ok":false,"error":...}` on stderr (with `--json`) when doctor cannot run at all, for example when `THOTH_HOME`, `USERPROFILE` and `HOME` are all unset. `--shell` accepts only the four values above; anything else is a usage error (exit `2`).

`--json` prints one object with `ok` (true when no item is `fail`), `version` (this thoth's version), `shell` (`powershell`, `cmd`, `bash` or `sh`: the shell the fix commands are written for), `shell_source` (`flag`, `env` or `fallback`) and `items`.

Each item has `id`, `status` (`ok`, `warn`, `fail` or `unknown`), `detail` (a string), `fix` (a string or `null`; never `null` for `fail`; several lines are separated by `\n`) and `data` (an object or `null`, per item). Items always come in this order: `state_dir`, `cli_claude`, `cli_codex`, `cli_agy`, `profiles`, one `profile:<profile_id>` per registered profile (sorted by id), `repo`, `checks`, `config`, `plugin`.

The `config` item's `data` also has `stored_keys` (the known keys present in config.json, sorted); a `cli_*` item's `data.source` is `env`, `file` or `path`. Additive (DT-3): and `machine_name` and `records_dir` (`{value, source, exists}`); the item is `warn` with a fix when records-dir is set and is not a directory; the config item's data also has `secrets_file` (CFG-2: the same object as `config list`'s without `read`) and `secrets` (set/unset with source per key), and the item is `warn` with a fix when secrets.json is unusable, has unknown keys or (Linux) is readable by other users.

`detail` and `fix` are always English. `THOTH_LANG=zh-TW` changes only the human output (without `--json`); the JSON document is the same byte for byte.

New (PANEL-3): a `profile:<profile_id>` heading names the login: `Profile claude-a (alice, Max)`, `帳號 claude-a（alice，Max）` with `THOTH_LANG=zh-TW` (see Conventions). The name comes from the email of doctor's own login check, else the stored one; doctor still writes nothing. `--json` does not change: the same items, the same `data` keys, `data.email` as before.

### `thoth setup [--shell powershell|cmd|bash|sh]`

New (SETUP-3). **For a person at a terminal only.** It asks questions on stdin and changes things when the answer is yes, so a commander or the plugin must not run it; there is no `--json` (`thoth setup --json` is a usage error, exit `2`) and no MCP tool. Without a terminal on stdin and stdout, or with `THOTH_RUN_ID` set, it exits `1` at once, touching nothing, with `error: …` on stderr and nothing on stdout.

Exit code: `0` when, after all its steps, no item is `fail` (the same items and statuses as `thoth doctor`); `1` when at least one still is, or when it refused; `2` usage error.

Answering no to "Enable it now?" ends the plugin step for this run: it does not go on to ask about an update. What a commander should do instead: run `thoth doctor --json` and, when something needs a person, ask them to open a terminal and type `thoth setup`.

### `thoth profile login [ID] [--harness claude-code|codex|antigravity] [--provider P] [--label L] [--json]`

New (SETUP-2). **For a person at a terminal only.** A commander or the plugin must not run it; there is no MCP tool for it. It opens the CLI's own login screen in the same terminal, then registers the profile if the CLI's status command says it is logged in. Exit `1` has two kinds. **Refused** (no terminal on stdin and stdout, `THOTH_RUN_ID` set, an argument rule broken, or an id that differs from a registered profile only in letter case): the login screen was not opened, stdout is empty, and stderr has one line (`{"ok":false,"error":...}` with `--json`, otherwise `error: …`). **Not logged in** (the login screen was opened and the CLI did not end logged in): with `--json`, stdout is the object below (`ok`, `logged_in` and `registered` all false) and thoth's one-line note about the login screen is on stderr; without `--json`, that note and the one human sentence (run the same command again) are both on stdout. The CLI's own screen appears in the terminal in both cases.

Exit code: `0` logged in and registered; `1` refused or not logged in (as above); `2` usage error (for example an unknown `--harness`).

With `--json`, stdout carries one object (the CLI's own screen still appears in the terminal, and thoth's one-line note about it goes to stderr):

- `ok`: true when logged in and registered.
- `profile_id`, `harness`, `provider`, `config_dir`: the profile logged in to; `config_dir` is the directory registered (or, when not logged in, the one that would have been).
- `new`: true when the profile was not registered before this run.
- `logged_in`, `registered`: both true on success (`registered` is also true for a profile that was already registered); both false when not logged in, and then nothing was written.
- `email`, `subscription_type`: what the CLI's status command reported, or null; null when not logged in.
- `account_label`: the profile's label after this run (`--label`, else for a new profile the subscription type), or null; null when not logged in.
- `cli_exit`: the CLI's exit code, or null when it had none (killed by a signal). It does not decide the result.

### `thoth retro [--days N] [--json]`

New (H10), compatible. Human output: when `reviews` is not 0, four lines follow the existing output, `by provider (reviewer vs implementer):` and one line each for `same_provider`, `cross_provider` and `unknown`: `  NAME: R reviews (PASS P REJECT J UNVERIFIED U), F findings`. Every key is present, with zeros and `[]`, when there is nothing (no `global.db` included). Human output: when `reviews` is not 0, after the provider lines, `fixed by behaviour (marks on the previous rejection): R reviews, N not recorded (before MEAS-1)`, `  yes Y no N not_fixed F unmarked U`, one `  CATEGORY: yes Y no N not_fixed F unmarked U  (blocking)` or `(advisory)` line per category, and `  rejected by SIDE: yes Y no N not_fixed F unmarked U` for each of the three sides.

### `thoth transcript RUN [--offset N] --json`
Read-only: lists what a run's worker did, from the run directory's `stream.jsonl`. It reads from byte `--offset` (default 0) and consumes only complete lines, those ending in a newline; a partial last line is left for the next call. `next_offset` is where the next call should start (pass it as `--offset`), so a caller that polls gets only the new steps. `lines` counts the consumed lines and `skipped` the ones that were not JSON objects. `reset` is true when `--offset` was past the end of the file (it was recreated or shortened): the read then started at 0. When the file does not exist yet, the exit code is 0 and `exists` is false, `size`, `offset` and `next_offset` are 0 and `steps` is empty. It writes no event and changes nothing in the run directory.

`steps[]` entries always carry nine keys: `at` (the line's first byte in the file), `kind` (`start` | `message` | `tool` | `error` | `note` | `result`), `nested` (true for a subagent's step), `text`, `tool`, `action` (`read` | `write` | `edit` | `run` | `search` | `other`, null unless `kind` is `tool`), `target` (file path, command, pattern or URL), `exit_code` and `is_error` (null when the stream does not say). `text` and `target` are whitespace-collapsed and cut at 300 characters. Claude Code and codex streams are translated; an antigravity run's lines count in `lines` but produce no steps in this version. Relied on: `exists`, `next_offset`, `reset`, `harness`, and each `steps[]` entry's `kind`, `action`, `target`, `exit_code`, `is_error`, `nested`, `text`.

### `thoth review record TASK -f REVIEW.json --json`

Additive (RES-1b): for research tasks the document checks sources instead of criteria:

```json
{"verdict":"PASS","findings":{"sources":[{"id":"S1","url":"https://example.org/page","verdict":"supported","reason":""}],"extra_findings":[]}}
```

Ids come from the latest completed implementer run's latest result, research
claims first in their result order then each claim's source order (`S1`, `S2`, …).
Both the expected list and reported sources must be nonempty. Every id must
appear exactly once, with no unknown ids; URLs must match after trimming both
ends. Source verdicts are `supported`, `not_supported`, `unreachable`; the last
two need nonblank reasons. Nonempty criteria are refused. Extra finding labels
use the usual normalization and only their evidence codes are checked.
Any not_supported means REJECT, else any unreachable means UNVERIFIED, else
PASS; a different declared verdict is refused at `consistency`. Other shape
errors use `schema`, id coverage errors `coverage`. The transaction refuses
without writes if its target differs from the target used for validation.

For a research PASS, any candidate evidence preparation happens inside that
transaction after its target check; ordinary review preparation remains
before the transaction as described below.

Settles an `in_review` task with a review made outside thoth. Relied on: `verdict`, `task_status` (`pass` | `reject` | `unverified`), `review_id`. The review file:

```json
{
  "verdict": "PASS | REJECT | UNVERIFIED",
  "findings": {
    "criteria": [
      {"id": "AC1", "verdict": "met", "evidence": ["E008"]},
      {"id": "AC2", "verdict": "unmet", "evidence": ["E005"], "note": "why", "fix_size": "S", "category": "spec_mismatch"}
    ],
    "extra_findings": [
      {"severity": "important", "note": "what", "evidence": ["E008"], "fix_size": "M", "category": "error_path"}
    ]
  }
}
```

Rules:
- every AC id appears exactly once;
- `met` cites at least one code;
- `unmet` cites a code or has a `note`;
- every cited code is evidence of this task;
- `PASS` with any `unmet` is invalid;
- `fix_size`, when present, is `S`, `M` or `L`, and `category`, when present, is one of `spec_mismatch`, `spec_error`, `test_missing`, `test_incomplete` (additive, REV-1), `test_interface`, `error_path`, `concurrency`, `platform`, `docs`, `evidence`, `check_not_run` (additive, REV-3), `files`, `security`, `other`; both are case-insensitive, a blank value or `none` counts as absent, and any other value is invalid at the `schema` stage;
- (REV-3) the report agrees with the required checks that did not run (below), or it is invalid at the `required_checks` stage.

Additive (REV-1): the categories come in two classes. Blocking (the behaviour would be wrong): `spec_mismatch`, `spec_error` (the spec needs changing, not the implementation redoing), `test_missing` (a new or changed behaviour has no test at all that would fail on the old code), `error_path`, `concurrency`, `platform`, `security`, `files`. Advisory (a note to fix later): `test_incomplete` (the behaviour has such a test, but it misses some cases or branches), `test_interface`, `docs`, `evidence`, `other`. A finding with no category counts as blocking. The reviewer prompts tell the reviewer to REJECT only for a blocking finding and to judge a criterion met when its only gap is advisory (recording that gap as an extra finding), but the verdict stays the reviewer's: a REJECT whose findings are all advisory is accepted as a REJECT (task `reject`), and a PASS with a blocking extra finding is accepted as a PASS (task `pass`); a PASS with an `unmet` criterion is still invalid whatever its category. The `verdict` event's `has_blocking_findings` (see `thoth events`) records which case it was. The `--json` keys do not change.

**Required checks (REV-3).** Additive category `check_not_run`, blocking: a check the task's spec lists under `checks` did not run on the run under review. `evidence` stays advisory and now covers every other missing evidence: a command an acceptance criterion or a constraint names, a claim without evidence, but not a check the spec's `checks` lists. A required check is an id in the task's current spec `checks`; a spec without `checks`, or with an empty array, requires none (`verify` then runs every approved check, and those are not required). A required check ran when at least one `results[]` item of the run's `verify_ran` events without `detail.at_commit` (so not `verify --at-base`) has its `check_id`, an integer `exit_code` and a null `error`; a check that ran and exited non-zero ran, and this rule does not judge it. Otherwise it did not run, for one of two reasons: `no_verify_row` (no such item names it: never verified, verified only with `--at-base`, or only another run was verified) or `did_not_complete` (items name it but none completed: refused, for example not approved, failed to run, timed out, no exit code, incomplete output). Only `verify_ran` counts: commands the worker ran, its `verification_requests` and `worker_declared` do not. When the report arrives, Thoth works out that list for the run it settles (the newest completed implementer run) and refuses the report at stage `required_checks` when (a) it has a `check_not_run` finding (an extra finding or an `unmet` criterion with that category) and its verdict is not `REJECT`; (b) the list is not empty and the verdict is not `REJECT`; (c) the list is not empty and the report has no `check_not_run` finding. When the list is empty, a reviewer's own `check_not_run` finding is taken (it is blocking, so it needs a `REJECT`). Thoth does not change the verdict or add findings; the reviewer writes one `check_not_run` extra finding per check (the note naming the check id and the reason). A research source check is not covered. The refusal is the same as for an invalid file (below): exit `1`, `review.json invalid at stage required_checks: REASON`, one `review_invalid` event with `detail.checks_not_run`, the task left `in_review`. **Breaking change (REV-3):** with a required check that did not run, a `PASS`, an `UNVERIFIED` or a `REJECT` without a `check_not_run` finding, which were taken before, are now refused; so is a `PASS` or `UNVERIFIED` carrying a `check_not_run` finding. A taken review's `verdict` event has `detail.checks_not_run` (see `thoth events`). The `--json` keys do not change.

Additive (H7a): `fix_size` and `category` on an unmet criterion or an extra finding are optional, compatible additions: a file without them is accepted and stored as before. When present they are stored normalised (`S`/`M`/`L`, lower-case category) and `review show --json` returns them in `findings`. `thoth retro` counts them.

An invalid file is refused with exit `1`, prints the failing stage and reason, writes one `review_invalid` event, and leaves the task in `in_review`. The command also refuses, writing nothing, when:
- the task is not `in_review`;
- a run is live;
- there is no completed implementer run with a candidate commit;
- it is invoked from inside a thoth run (`THOTH_RUN_ID` set);
- additive (LESS-5), for a `PASS` only: that run changed a protected `test` or `check_word` file (additive, LEAN-1: or an `inline_test` region) that no `checks approve --run RUN` approved for that run (`refusing to record a PASS for task TASK: run RUN changed protected files that nobody has approved yet: PATH (STATUS, KIND), …; read the change (thoth review packet TASK), then approve it with: thoth checks approve --run RUN --reason "WHY" (MCP: thoth_checks_approve)`); or the run has no diff evidence for its candidate and none could be recorded (`… run RUN has no diff evidence for its candidate, so its protected file changes cannot be checked`); or its newest diff evidence has no readable `protected_changes` and recording it again failed (`… run RUN's diff evidence CODE has no readable protected_changes, and recording it again failed; ERROR`; TESTGAP-2: when the row recorded again still has no readable list, the message stops after `has no readable protected_changes`). Before the write transaction a `PASS` records the candidate's diff and commit evidence when the run has none, and the diff again when the newest one is unreadable; a failure there is a `warning: ` line on stderr. `REJECT` and `UNVERIFIED` are not affected. GATE-1: a diff evidence row whose `detail.protected_changes` is an array but whose detail has no `inline_test_errors` array (written by a thoth before LEAN-1, which listed no `inline_test` change) counts as unreadable too: it is recorded again and the new row is judged; a row with that array is read as it is.

Additive (WT-1): after a `PASS` it removes the task's clean worker worktrees (not when run from inside the worktrees directory). The `--json` keys do not change; the human output gets one more line per directory, `  removed worktree PATH` or `  kept worktree PATH: REASON`, and a failure of the cleanup is one `warning: worktree cleanup failed: …` line on stderr.

Additive (MEAS-1): `findings.prior_rejection`, next to `criteria` and `extra_findings` (an edit-mode document keeps `edits` at the top level), holds the reviewer's marks on the previous REJECT's findings: an array of `{review_id, ref, fixed_by_behaviour, evidence, diff_at, note}`. `review_id` is the review being marked; `ref` an unmet criterion id (`AC3`) or `extra_findings[N]` (N from 0, as an edit binds a finding); `fixed_by_behaviour` `yes` (fixed by changing what the program does), `no` (fixed without a behaviour change: evidence or a verify added, docs, a test-only change, or the finding no longer applies, the note saying which) or `not_fixed` (still there), read trimmed in any case; `evidence` an array of codes (read trimmed and upper-cased; a blank code is no code; empty or absent is none, null is `bad_shape`); `diff_at` `PATH:LINE` in this candidate's diff, LINE a whole number from 1 (absent, null or blank is none); `note` (absent, null or blank is none). `yes` and `no` need at least one code or a `diff_at`; `not_fixed` needs a note or at least one code. **It never refuses a document**: whatever the key holds (absent, null, not an array, entries of any shape), no `review_invalid` is written because of it and the review is accepted or refused exactly as the same document without it; its codes are not part of the `citation` stage, nor of `cited`, `opened` or `unopened_citation`. When it is present and neither null nor `[]` it is stored in the record as written. The review to mark is worked out when the review arrives, for the run it settles: among the task's records whose target run has a lower attempt than that run, the newest (none: status `no_previous_reject`; a PASS or UNVERIFIED: `previous_not_reject`; a REJECT: `checked`, the findings to mark being its unmet criteria by id in document order, then `extra_findings[N]` for each of its extra findings as stored). A second review of the same attempt marks the same REJECT again; a research task's source check is never checked and stores no array. With `checked`, each expected finding gets the first failing check of: `missing` (no entry has its `ref`, trimmed), `duplicate_ref`, `bad_shape` (`evidence` not an array of strings, another field neither a string nor null), `wrong_review_id`, `bad_value`, `no_support`, `foreign_evidence` (a code that is not evidence of this task, by the citation rule above), `bad_diff_at` (not `PATH:LINE`, split at the last colon), `diff_at_not_in_diff` (PATH, backslashes read as `/`, is in no `files_changed` of a `diff` evidence row of the run under review); the line is not checked against the diff. The result is stored as `findings.prior_rejection_check` (see `thoth review show`). The verdict, the task status, every refusal above, `has_blocking_findings` and `checks_not_run` never depend on it, and `--json`'s keys are unchanged.

### `thoth spec review record TASK -f SPEC-REVIEW.json --json`
New (SR-1). Records a review of the task's current spec made outside thoth (a subagent or a human), before its first dispatch. Relied on: `verdict`, `approved`, `required_before_dispatch`, `revise_streak`, `stalled`, `spec_review_id`. The `--json` keys are exactly `task_id`, `spec_review_id`, `verdict`, `spec_sha256`, `risk`, `task_status`, `approved`, `required_before_dispatch`, `revise_streak`, `stalled`, `source` (`external`). The file:

```json
{
  "verdict": "APPROVE | REVISE",
  "criteria": [
    {"id": "AC1", "verdict": "revise", "findings": [
      {"check": "exists", "location": "src/ledger.rs:40", "note": "what to change"}
    ]},
    {"id": "AC2", "verdict": "ok", "findings": []}
  ]
}
```

`check` is one of `verifiable` (every acceptance criterion can be verified), `exists` (the files, functions, commands and tests the spec names exist in the current code), `consistent` (the criteria do not contradict each other) and `steps` ('how to test' is written as step-by-step actions); `location` is `file:line`, or `spec` for the spec text itself.

Rules:
- every AC id appears exactly once;
- `revise` needs at least one finding;
- every finding has a known check, a location and a note;
- `APPROVE` with any `revise` criterion is invalid;
- `REVISE` with no `revise` criterion is invalid.

An invalid file is refused with exit `1`, prints `spec-review.json invalid at stage STAGE: REASON`, writes one `spec_review_invalid` event and nothing else. The command also refuses, writing nothing, when:
- it is invoked from inside a thoth run (`THOTH_RUN_ID` set);
- the task is `running`, `pass`, `cancelled` or `accepted` (`accepted` is additive, DOC-1);
- the task's spec changed between the read the file was validated against and the write (`task TASK's spec changed while the spec review was being recorded (sha256 OLD -> NEW); review the new spec and record again`).

A valid file writes one `spec_review` event; the task's status does not change. The approval is bound to the spec's sha256: after `task update-spec` it no longer applies. Additive (SR-3): the event's `detail.mode` is `external`, its `edits` `[]`, `edit_count` 0, `proposed_spec` and `proposed_sha256` null, `bytes_before` and `bytes_after` the spec's size; the file never carries `edits` (an `edits` key is ignored). The `--json` keys do not change.

### `thoth spec review start TASK --profile ID [--model MODEL] [--effort LEVEL] [--reason TEXT] [--timeout DURATION] [--edit] --json`
New (SR-2). Launches Thoth's own read-only spec reviewer, a run with `role` `spec_reviewer`, against the task's current spec, and returns at once. Relied on: exit code, `run_id`, `spec_sha256`, `reviewed_commit`, `required_before_dispatch`. The `--json` keys are exactly `ok`, `run_id`, `task_id`, `spec_sha256`, `reviewed_commit`, `task_base_commit`, `risk`, `task_status`, `required_before_dispatch`, `profile`, `model`, `worktree`, `worktree_reused`, `worktree_moved`, `cleared_stale_report`, `allowed_tools`, `runner_pid`, `run_dir`, `effort_requested`, `effort`, `effort_note`, `warnings` (Breaking change (RJ-1): `auto`, `auto_reasons` and `live_quota_refresh` are gone). Additive (SR-3), edit mode: `--edit` (MCP: `edit`, boolean) lets the reviewer propose edits to the spec besides judging it; without the flag nothing changes. The refusals, their order, the worktree rule, the live-run and sha checks and `launch_choice` are those of `start`. `--json` gains `mode` in both cases (`edit` | `review`), and `spec_review_started.detail.mode` says the same; the runner picks the prompt and the output schema from it. The reviewer is still read-only: Claude's allowed tools, codex's read-only sandbox and agy's tool list are unchanged; the edits are applied by Thoth, never by the run.

The edit document is the spec review document plus `edits` (array, always present, may be empty; a document without it, or with `null`, is stage `schema`). Each edit has exactly the seven properties below, as the schema says: one left out is not defaulted and one more is refused, both stage `schema` (`edits array is malformed: …`). Each edit: `field` (`goal` | `acceptance_criteria` | `constraints` | `non_goals` | `excluded_alternatives`; anything else is refused), `op` (`replace` | `insert` | `delete`; `goal` and `acceptance_criteria` allow only `replace`, and after the edits `review_json::ac_ids` of the proposed spec must equal the task's), `at` (from 0; `insert` up to and including the list's length at that point (append); for `replace` / `delete` it names the entry the anchor is checked against first, see `anchor`; ignored for `goal`), `anchor` (Breaking change, SR-4: `replace` / `delete` name their entry by this rule. For `goal` the field is its one string. The search never crosses into another field. A review-mode run and `spec review record` parse the document as before and never read `edits`.

The runner's ingest, after the stages `started`, `schema`, `spec`, `coverage` and `spec_changed` (each still refuses the whole review: a missing or extra edit property, an APPROVE with edits, a criteria list that does not cover the criterion ids, a spec changed under the run). Breaking change (SR-4): then the edits are processed in document order against the proposal the earlier applied edits left. An edit that breaks a rule is refused alone: it changes nothing, the later edits still apply, and it is listed in the event's `refused_edits` with its original index, its field and a reason that says which rule failed (`field must be one of …`, `op 'move' must be one of …`, a criterion that is not one of the task's, a blank `reason`, a blank `text` for `replace` / `insert`, `goal` / `acceptance_criteria` with an op other than `replace`, an anchor that names no entry by the rule above, an `insert` past the end, a changed criterion id, `text carries a mask marker the stored spec does not have …`). The reason quotes the anchor whole and no cut of a spec entry, and like every other output it is masked on the way out (see Secret masking under Conventions). Before SR-4 the first such edit refused the whole review as `spec_review_invalid` stage `edits`. When at least one edit applied, the proposed spec is linted with `spec_lint` (the rules of `task create`); an error (`too_large` over 40960 bytes included) still refuses the whole review at stage `lint` and is never pending; warnings do not block. A refused review writes no `spec_review` event. A valid edit document writes one `spec_review` REVISE (`spec_sha256` the reviewed spec's, `source` `reviewer_run`, the streak as before) whose `detail` carries the keys under `events` below (`mode` `edit`, the completed `edits` under their original indices, `edit_count`, `refused_edits`, `proposed_spec`, `proposed_sha256`, `bytes_before`, `bytes_after`), even when every edit was refused: then `edit_count` is 0, `proposed_spec` and `proposed_sha256` are null, `pending_edits` stays false and the review's document and findings remain readable. An edit review never writes the task's spec. The proposed spec is serialized from the stored spec read as JSON (unknown keys keep their values): two-space indent, LF, one trailing newline, keys in the order `goal`, `acceptance_criteria`, `constraints`, `non_goals`, `excluded_alternatives`, `task_type`, `difficulty`, `checks`, `risk`, then every other key alphabetically.

### `thoth spec review confirm TASK --profile ID --model MODEL [--effort LEVEL] [--reason TEXT] [--timeout DURATION] --json`
New (SR-3). Launches the author's check of the newest edit review's edits: a run with `role` `spec_reviewer` (so `wait --run`, `cancel`, `status` and the worktree kinds treat it as `start`'s run), `mode` `confirm`, in the same `worktrees/TASK_ID-spec-review` (the same `reviewed_commit` rule). Relied on: exit code, `run_id`, `mode`, `confirms_spec_review_id`, `proposed_sha256`. The profile, model and effort are given (RJ-1; use the profile and model that wrote the spec); `--timeout` is `start`'s. The `--json` keys are `start`'s (`mode` `confirm`) plus `confirms_spec_review_id` (the edit review's id) and `proposed_sha256` (its proposed spec's). MCP: `thoth_spec_review_confirm` (`task`, `profile`, `model?`, `timeout?`, `effort?`, `reason?`, `repo?`).

It refuses with exit `1`, no run row and no event: everything `start` refuses, in `start`'s order, except that the task's status must be one `update-spec` allows (`draft`, `queued`, `reject`, `unverified`: `task TASK is 'STATUS'; spec review confirm needs draft, queued, reject or unverified, because its APPROVE replaces the spec`); and, after the live-run check, when `pending_edits` is false: `task TASK has no spec review; …` (none recorded), `task TASK's newest spec review ID is not an edit review with edits (mode M, VERDICT, N edits); …` (a REVISE of another mode, an APPROVE, or no edits), or `task TASK's spec changed after spec review ID (sha256 OLD -> NEW); the edits were proposed for the old spec, run `thoth spec review start TASK --edit ...` again` (`update-spec` ran after the review). ### `thoth spec lint FILE [--json]`
New (LESS-3), additive. Read-only: checks a spec file with the fixed rules `task create`, `task update-spec` and `spec review start` apply first; it writes nothing and works in an initialized repository. `--json` → `{"ok","bytes","errors":[{"rule","location","message"}],"warnings":[same shape]}`; `ok` is true when `errors` is empty, `bytes` is the file's size, and `location` is `goal`, `acceptance_criteria[i]`, `constraints[i]` or `checks[i]` (from 0), or null for the size rules and `invalid_spec`. Exit `1` when there is an error, `0` otherwise; stdout is the whole report either way. Without `--json` each finding is one line, `error: RULE (LOCATION): MESSAGE` or `warning: …` (no parentheses without a location), then `N error(s), M warning(s)`; with nothing found the only line is `no problems found`. A file that cannot be read fails as in `task create`. Only `goal`, `acceptance_criteria` and `constraints` are scanned (`non_goals` and `excluded_alternatives` often name what is not done). Errors:
- `too_large`: the file is over 40960 bytes, at every risk; split the task.
- `large` (Breaking change, LEAN-1: an error at `low` and `normal` risk): the file is over 20480 bytes (and at most 40960) and the spec's `risk` is `low` or `normal`, or absent (it defaults to `normal`), or cannot be read because the file does not parse (then `invalid_spec` is reported too). Low and normal risk already skip the mandatory first-dispatch spec review (SR-1 gates only `important` and `high`); LEAN-1 only adds this size rule for them. The message names the 20480-byte limit and that those risks skip the mandatory spec review, and asks to shrink the spec or split the task. Since it is an error, `task create`, `task update-spec`, `spec review start` (with or without `--edit`, on the stored spec) and `spec review confirm` (on the proposed spec) refuse with it and write nothing; the lint of a reviewer's edits and confirm's APPROVE-time lint refuse with it as their stage `lint`. `dispatch`, a rework and `review start` run no lint, so a spec stored before LEAN-1 still dispatches.
- `invalid_spec`: the spec does not parse; the message is the parse error, and only the size rules run besides.
- `ac_blank`: an acceptance criterion is blank once trimmed.
- `ac_duplicate`: an acceptance criterion repeats an earlier one once trimmed and with runs of spaces collapsed; the message names the earlier one.
- `unknown_check`: a `checks` id is not in the repository's catalogue (approved or not). Not reported while the catalogue is empty.
- `claude_write`: a clause of a field names a `.claude` folder (`~/.claude/x`, `.claude/skills/y`; not `.claude-plugin`, `.claude.json` or `CLAUDE.md`) and, outside backticks, has a write word (such as 改, 新增, 刪, edit, update, delete) and no negation (such as 不, 沒, not, never, without, and since SPECLINT-1 the read-only markers 只讀, 唯讀, 取自, `read-only`, `readonly`, `read only`). One per field; the message quotes the clause that was refused, behind the unchanged prefix `asks to write under a .claude folder`. SPECLINT-1 (a loosening: it refuses fewer specs; the rule name, the `location` values, the keys of `--json` and the message prefix did not change): a sentence (split at `。`, `；`, `;`, a new line and `. `, never inside a pair of backticks) is split again into clauses at `，` and at an ASCII `,` followed by a space or the end of the field (`、` does not split), and the write word, the negation and the name are judged inside one clause, so a source named in one clause and a write word in another no longer refuse; a negation in one clause does not cover a write in another (two exceptions: the clauses of one parenthetical aside, from the clause that opens `（`/`(` to the clause that closes it, share their negations; and a trailing negation clause, the last clause of the sentence when it has a negation word other than a read-only marker (those count only in their own clause), no name and no write word of its own, covers the clauses before it, so `.claude/skills/ 的私下版由指揮官之後自己改，這件不碰` passes while `改 .claude/x，不改 src/a.rs` is still refused). A clause that starts with the name (after spaces, a backtick, and `和`, `與`, `及`, `and` or `or`) and has no write word of its own is a continuation and takes the verdict of the clause before it, so a comma list that goes on to the folder is still refused when its first clause writes. A name inside a backtick fragment that has whitespace and a negation word is quoted text that bans the folder, not a target. A clause whose only write word is an adding word followed by a colon (`新增：`, `加入：`, `add:`) does not refuse a bare `.claude` or `.claude/` that has another list entry beside it (`、`, `，` or `,`). REVFIX-1 (a tightening: it refuses some specs that pass after SPECLINT-1; the rule name, the `location` values, one finding per field, the keys of `--json` and the message prefix are unchanged): a clause with a write word, no negation and no target of its own writes to the target of the nearest earlier clause of the sentence that has a target; when that clause names a `.claude` folder and has no write word and no negation (a read-only marker in it counts), the sentence is refused as if the write stood there, so `In .claude/skills/x/SKILL.md, replace the first line with a new heading` and `在 .claude/skills/x/SKILL.md 裡，把第一段改成新的說明` are refused again, while `Read .claude/skills/x/SKILL.md, then edit Cargo.toml` passes. A target is a `.claude` name outside a quoted ban, or a path or file name: an ASCII word, inside or outside backticks, that holds a `/` or a backslash or ends in a dot followed by letters or digits (`a.txt`, `Cargo.toml`). The message then quotes the text from the start of the folder clause to the end of the write clause. The trailing negation clause and an aside's shared negation still apply. Known limits: a bare file name is a target, so `In .claude/skills/x/, edit SKILL.md` passes; a write clause before the folder clause is judged as before.
- `unknown_test_target` (additive, SMALL-10): a `cargo test` command in a field has a `--test` word (or the `--test=` form) followed by a name that is no integration test target of the main work tree, that is, neither `tests/NAME.rs` nor `tests/NAME/main.rs` is a file there. The commands are read as scoped verify reads them (the command runs to the end of the line, a backtick or a separator such as `;`, `|`, `、` or `。`; one command may have several `--test` words), because verify appends each name to the approved test command and cargo then exits 101 before any test ran. One finding per distinct name, at its first mention (`location` is that field), in the order of first mention; the message holds the name, `no integration test target` and both file shapes. Not reported when the scanned fields name the path of such a file anywhere (`tests/NAME.rs` or `tests/NAME/main.rs`: the task creates it), and silent when the main work tree has no `Cargo.toml` at its top or that file holds `[workspace]` or `[[test]]`. Only `goal`, `acceptance_criteria` and `constraints` are read. It is a new rule name in `errors`; the keys of `--json` do not change.

Warnings:
- `large` at `important` or `high` risk: the file is over 20480 bytes (and at most 40960). Those risks are spec-reviewed before the first dispatch, so it stays a warning.
- `missing_path`: a repository path (letters, digits and `_.-/`, with a `/`, whose first part exists) is not in the main work tree; a path ending in `/` must be a folder. Not reported for a path with `new`, `create` or `新` in the 12 characters before it anywhere in the spec, nor for `/x`, `./x`, `../x`, `$X/…`, `~/…` or URLs. Fewer warnings (SMALL-17; the rule name, the message and the `--json` keys are unchanged): a path directly followed by `*` goes on over the `*` and the path characters after it and is a glob, `*` matching any run of characters inside one path part; it is reported only when nothing under the main work tree matches, and the message names the glob as written (`src/bin/fake-*.rs`). A path whose last part has no dot and that does not end in `/` (`plan/log`, `docs/low`) is checked only when it is the whole text of a backtick fragment; bare, or inside a longer fragment, it is read as a noun. A path is also new when only the words test(s), file(s), module(s), fixture(s), script(s), folder, 檔, 檔案, 測試檔 or 模組, spaces, backticks and colons lie between it and an earlier `new`, `create` or `新` of the same sentence (`new test files src/a.rs`), and when it follows a new path in the same list, separated only by spaces, backticks, `、`, `,`, `，` or the words and, or, 與, 和, 及, 或 (`新檔 a.rs、b.rs`).
- `missing_name`: an existing file followed by `的` (or `裡的`, `裡`, `中的`) and backticked names separated by `、` `,` `，` `與` `和`, or by `:name`, where the file does not contain that name as a whole word.
- `line_number`: a file name with a code or text extension followed by `:` and a number (`a.rs:12`), a backticked name followed by `:` and a number, or `第 12 行`. One per field, with the first example and the count.
- `two_dot_diff`: within 100 characters after `diff` on the same line, a two-dot range `A..B` (`git diff master..HEAD`). One per field. Fewer warnings (SMALL-17): `diff` counts only as a whole word, in any ASCII case, with no ASCII letter, digit or `_` right before or after it (`record_diff`, `different` and `diffs` are not it); and a token has its leading `(`, `[`, `（` and trailing `,`, `.`, `;`, `:`, `)`, `]`, `）`, `。`, `，`, `、` trimmed before it is tested, so a side left empty (Rust's `(..` and `..,`) is no range. The example in the message is the trimmed token.
- `powershell_in_bash`: a backticked command with `$env:`, `$null`, `-ErrorAction` or a `Verb-Noun` cmdlet, in a field that never says PowerShell or pwsh. One per field.
- `no_checks_for_document_task` (additive, SMALL-11 (3)): the spec's `task_type` is `docs` or `research`, its `checks` key is absent or an empty array, and the repository's check catalogue is not empty. `location` is `checks` (a new `location` value, additive). The message names the `task_type`, says that `verify` will then run every approved check of the repository, and asks to list the checks the task needs in `checks`. A warning, not an error: `ok` stays true and the exit code `0`, and `task create`, `dispatch` and `pipeline new` go on and show it in their `warnings[]` as `spec lint: ...`. Not reported for any other `task_type` or none, for a spec whose `checks` lists at least one id, or while the catalogue is empty. What `verify` runs does not change.

### `thoth review packet TASK [--out FILE] [--json]`
Read-only: prints everything a reviewer needs in one document, so the commander does not assemble it from `evidence list`, `evidence show` and `events`. It writes no row and no event, except one secret_redacted event when it masked something (it does **not** record `evidence_opened`), and works at any task status. Additive (RD-1): every output form is masked (see Secret masking under Conventions); the `secret_redacted` event has exit `review_packet`, no `run_id`, and `evidence` the codes of the rows whose label, output or diff had a secret, in code order. If that write fails, the output is unchanged, the exit code is `0` and stderr gets one `warning: could not record secret_redacted: REASON` line. The worker's own `summary` is left out on purpose. Relied on: exit code (`1` and an error naming the id for an unknown task) and, with `--json`, these top-level keys:
- `task_id`, `title`, `status`, `risk`;
- `runs[]` (additive): `run_id`, `role`, `attempt`, `models_used`, `subagents_spawned`, as in `status`; additive (S3-7) `effort`, the level actually sent (null when none). Each Markdown run line has ` | effort: LEVEL`, or ` | effort: -` when there is none, and ends there unless the run continued a stopped run (S3-9 handoff), in which case ` | continued from PREVIOUS_RUN (REASON)` follows it. Additive (S3-9): `continued_from`, the id of the run it continued, or null. The Markdown packet lists them under `## Runs` and adds a line starting `WARNING:` for any run that spawned subagents;
- `spec`: `goal`, `acceptance_criteria`, `constraints`, `non_goals`, `excluded_alternatives`, verbatim;
- `evidence[]`: `code`, `kind`, `exit_code`, `run_id`, `label`, `output_tail` (the last 15 lines of the stored output for `command` rows, null otherwise; RD-1: the whole output is masked first and the last 15 lines are taken from the masked text); additive (RVI-1) `execution_error`: on a `verify:` or `verify@base:` row whose check did not complete cleanly, the `error` `verify` recorded for it (refused, failed to run, timed out, output left incomplete by a descendant holding the pipe, no exit code), masked, set even when `exit_code` is `0` or the check printed output (an incomplete-output check exits `0`); null on every other row. The Markdown packet shows it as one `  execution error: TEXT` line (line breaks as spaces) right under the row's index line, before its output; a check with nothing stored, whose `output_tail` is that same error, shows `(no stored output)` after it instead of repeating it;
- `evidence[].output_stream` (additive, SMALL-11 (2)), and the stderr fallback of `output_tail`: for a `command` row whose stored stdout is empty and whose stored stderr is not, `output_tail` is the last 15 lines of that stderr, masked first like stdout (a `verify:` row records both streams; a hook-captured row has a stderr blob only when the worker's harness gave one). `output_stream` says where the tail comes from: `stdout`, `stderr`, `error` (the recorded error, as before for a failed command with nothing stored) or null (a row that is not a command, or a command with nothing stored on either stream). The Markdown packet (stdout, `--out FILE` and `.agent/review-input/packet.md`) shows, under such a row's index line, `  (stdout was empty; last lines of stderr:)` and then the tail, never `(no stored output)`; a row with output on stdout is shown exactly as before, its stderr left out; a row with nothing on either stream still shows `(no stored output)`. A codex or antigravity reviewer's `.agent/review-input/evidence/CODE.txt` for such a row starts with `[thoth: this command printed nothing on stdout; its stderr follows]` and then the whole masked stderr (after the execution error line when one is recorded).
- `protected_changes[]` (additive, P7-2): `run_id`, `code`, `path`, `status`, `kind` — one entry per protected file each `diff` row changed (`code` and `run_id` are that diff's), `[]` when none. `status` is `modified` | `deleted` | `type_changed` | `added`; `kind` is `test` | `check_input` | `check_word` | (additive, LEAN-1) `inline_test`. The list comes from the diff evidence alone (LEAN-1: no claim is needed for an entry to be listed). The Markdown packet lists them under `## Protected files changed`, placed before `## Diffs`, as `path (status, kind)`, followed by the text of each (optional) `protected_change` claim; an empty list reads `(none)`;
- `diffs[]`: `code`, `run_id`, `blob_verified`, `content` (the whole diff, never truncated); additive (SMALL-9c): `from_commit` and `to_commit` (the row's detail, where the diff starts and ends), `diff_from_rule` (`merge_base` | `run_base`, null for a row recorded before SMALL-9c) and `integrated_files` (the paths the main line brought in that the diff leaves out, masked; `[]` for an older row). In the Markdown packet (stdout, `--out FILE` and a codex or Antigravity reviewer's `.agent/review-input/packet.md`) each diff heading under `## Diffs` is followed by one line, `From START to END (start: RULE); LEFT_OUT`, with START and END as short shas, RULE `merge base with the main worktree` or `the run's base` (an older row reads `the run's base`) and LEFT_OUT `N file(s) brought in by merging the main line are left out: A, B` or `left out: none`;
- `claims[]` (`kind`, `text`, `evidence`) from the newest `result_ingested` event, and `claims_run_id` (null when there is none). Each entry is the claim as the worker wrote it, so a `research` claim (RES-1a) carries its `sources` (`[{"url","quote"}]`) and a claim written without the key has none; the Markdown packet adds one indented `  - URL — "QUOTE"` line per source under the claim's line;
- `verification_requests` (additive, SMALL-16): `[{"cmd","cwd"}]`, what the newest `result_ingested` run's result.json declared, in the worker's order, masked like the claims; `[]` when it declared none or no result is ingested. For reference only: the control plane runs the approved checks. The Markdown packet shows them inside `## Worker claims`, after the claims, as the line `Verification requests the worker declared (for reference only; the control plane runs the approved checks):` and one `- CMD (cwd: CWD)` per request (`- (none)` when empty; no such line when no result is ingested);
- `checks_not_run` (additive, REV-3): `[{"check_id","reason"}]`, the required checks that did not run on the `claims_run_id` run, by the rule under "Required checks" in `thoth review record` (`reason` `no_verify_row` | `did_not_complete`); `[]` when `claims_run_id` is null, the spec has no `checks`, or every listed check ran. In the Markdown packet (stdout, `--out FILE` and a codex or antigravity reviewer's `.agent/review-input/packet.md`) a new section `## Required checks not run` comes right before `## Diffs` (after `## Protected files changed`): one explanatory paragraph, then one line `CHECK_ID (REASON)` per entry, or `(none)`;
- `test_scope` (additive, VSCOPE-1): what the scoped checks ran. From the newest `verify_ran` event of the `claims_run_id` run that is not a `--at-base` one, one entry per `results[]` row that has a `scope`: `{"check_id"}` plus that row's `scope` keys (`mode`, `targets`, `all_tests_because`, `dropped`, `appended_args`); `[]` when `claims_run_id` is null or there is no such row. In the Markdown packet (stdout, `--out FILE`, and a codex or antigravity reviewer's packet) a new section `## Test scope` comes after `## Required checks not run` and before `## Diffs`: one explanatory paragraph (it says existing tests outside the scope run only in the whole suite), then one line per entry, `CHECK_ID: targets NAME (SOURCES), ...` (`targets (none)` without targets) or `CHECK_ID: all tests (PATHS)`, followed by `; dropped NAME (REASON), ...` when something was dropped; `(none)` without entries.
- `spec_tests_commit` and `spec_tests` (additive, SMALL-17): the test names the spec writes, looked up in the code. `spec_tests_commit` is the `candidate_commit` of the `claims_run_id` run, or null (no result ingested, or that run has no candidate); `spec_tests` is `[]` when it is null, otherwise one entry per distinct (form, target, name), in order of first mention, `{"name","form","target","status"}`. Names come from the spec's `goal`, `acceptance_criteria` and `constraints` (not `non_goals` or `excluded_alternatives`). Form `function` (target null): a whole word of lowercase ASCII snake_case with at least four parts, `[a-z][a-z0-9]*(_[a-z0-9]+){3,}`, not directly after `/ . - $ % ~` and not directly before `/`, `-` or a dot and a letter (a path, a flag, a file name). Form `filter`: in each `cargo test` command, read to its end as scoped verify reads it (a line end, a backtick or a separator; also after a word that ends in a comma), the first word that is no flag and no flag value, trailing `. , ; : )` trimmed, when it is ASCII letters, digits, `_` and `:` starting with a letter or `_` (otherwise the command has no filter); `--test NAME`, `--test=NAME`, `--bin NAME`, `--bin=NAME`, `-p`, `--package`, `--features` and, after a lone `--`, `--skip` take a value, every other word starting with `-` is a flag. Its `target` is `test:NAME` (from `--test`), `bin:NAME` (from `--bin`) or null. Lookup reads git at `spec_tests_commit` and at that run's `base_commit` (no checkout), in the tracked files ending `.rs`, `.ts`, `.tsx`, `.js`, `.mjs` or `.py`: a function is `found` when it is a whole word in a file at the candidate, `removed` when it is only at the base, `missing` otherwise; a filter is looked up the same way in its target's files (`test:NAME`: `tests/NAME.rs` and the folder `tests/NAME/`; `bin:NAME`: every `.rs` file under `src/`; null: `src/` and `tests/`), any part of a word counting as found; a filter with `::` is `not_checked`, and so is any entry git could not look up. In the Markdown packet (stdout, `--out FILE`, and a codex or antigravity reviewer's `.agent/review-input/packet.md`) a new section `## Spec-named tests` comes after `## Test scope` and before `## Diffs`: one explanatory paragraph (missing means in neither the candidate nor the run's base, removed means in the base only; a report, not a refusal), then one line per entry, `- NAME (function): STATUS` or `- NAME (filter, TARGET): STATUS` (`all targets` for a null target), or `(none)`. A report only: no command refuses, waits or exits differently because of it.
- `approvals[]` (additive, LESS-5), by event `seq`, oldest first: every `check_approved` event after the task's `task_created` event (from the main tree or any run) and every `protected_change_approved` event of this task. Each has `seq`, `ts`, `type` (`check_approved` | `protected_change_approved`), `approved_by` and `reason` (null for an event written before LESS-5), `run_id`, `check_id` and `source` (null for a protected one), `changes` (`[{"path","status","kind"}]`; `[]` for a check one) and `live_runs` (`[]` for an older event). The Markdown packet lists them under `## Approvals during this task`, after `## Worker claims` and before `## Reviews recorded so far`; an empty list reads `- (none)`;
- `reviews[]`, oldest first: `verdict`, `external` (true when there was no reviewer run), `findings`.

Without `--json` the same content is Markdown, in that order. With `--out FILE` the exact bytes that would have gone to stdout are written to FILE (UTF-8, no BOM), stdout stays empty, and stderr gets `wrote FILE (N bytes)`. There is no `summary` key anywhere.

New (RVI-1): the packet still has no worker summary (its only change is the additive `execution_error` above), but a codex or antigravity code reviewer gets the delivery next to it: `.agent/review-input/result.json` (see `thoth review start` below) holds the whole recorded result of the run under review, summary included, masked. That file is delivered prose, what the worker wrote, not execution evidence that its statements are true; the packet's evidence index stays the only source of citable codes.

Additive (MEAS-1): `reviews[].findings` (and the Markdown packet's findings block) are the stored findings, so a record with marks carries `prior_rejection` and `prior_rejection_check` (see `thoth review show`); `reviews[]` has no new key.

### `thoth resume RUN --json`
Continues an `interrupted` implementer run in its own session. The runner has already retried a transient failure twice inside the run before it is `interrupted` / `transient`; `resume` tries again by hand, and the resumed run again retries a transient failure up to twice. Relied on: exit code and `run_id`. An antigravity run is resumed with `--conversation <harness_session_id>`, the conversation id recorded when agy's `init` arrived; a run that failed before `init` (an unknown model) has none and is refused. Additive (AGY-1): the resumed launch reuses the run's stored `launch` settings, so an agy run gets the same `--effort LEVEL` again (or, for a model name that carries its level, none again); nothing is chosen anew. Additive (AGY-1, second part): a run whose effort agy refused was stored with `effort` null, and the runner also sends no `--effort` for any model recorded as taking no effort on the run's profile (`no_effort` in `thoth models`), so such a resume sends none. Additive (MODELS-1): at its model-rule step it also applies the agy list rule (the stored list only) and the Claude unavailable-model rule of `dispatch`, refusing before anything is written; with no stored agy list `warnings` gains the `was not checked` line. Additive refusal (S3-9): once a later implementer run of the same attempt has started (a handoff, see `dispatch`), resuming the earlier run exits `1` with a message naming the later run and containing `continued`; dispatch the task again instead. Breaking change (RJ-1): the runner no longer hands a run over on quota, so the only later run is one the commander dispatched. A run of a `pass`, `cancelled` or `accepted` task is refused with exit `1` (`resume needs a task that is not pass, cancelled or accepted`; `accepted` is additive, DOC-1). Additive (SMALL-9a): the quota reserve of `dispatch` applies to the run's profile, task and model (role `implementer`): refused with exit `1` after the refusals above and before the run is queued again, nothing written; with no current reading the resume goes ahead and `warnings` (`resume --json`'s array; `warning:` lines on stderr in human mode) gains the `not held back` note.

### `thoth cancel RUN --json`
Stops a `queued` / `running` run. Relied on: exit code. When it has to kill the worker itself, it first checks the pid's image against the run's recorded `worker_image`, falling back to the stem of `runs.harness_bin` for runs without one. A cancel that arrives while the runner is waiting to retry a transient failure ends the run `cancelled` at once; there is no worker to kill and nothing is relaunched. **Final for the task:** a cancelled run leaves the task `cancelled`, and a `cancelled` task can never be dispatched again, so a retry needs a new `task create`. In the rare case where the runner had already died and the worker had to be killed, the task becomes `failed` instead, which `dispatch` does accept. A run that simply takes too long stops itself at its `dispatch --timeout` (by default 1 to 4 hours by the effort sent, see `thoth dispatch`): the run and the task both become `failed`, with `interrupted_reason` `timeout`. `resume` does not accept a `failed` run; re-dispatch with `dispatch`, which writes a handoff file (see `dispatch`). A run stopped by quota is already `interrupted`, so cancelling it exits `1`; Breaking change (RJ-1): no handover run follows it any more.

### `thoth task update-spec TASK -f SPEC.json --json`
Allowed from `draft`, `queued`, `reject` and `unverified` (`queued` is additive, SR-1: a spec review that comes back REVISE finds the task still queued). Relied on: exit code. Note: the `status` key in its output is the status **before** the update. Additive (SR-1): the `spec_updated` event's `detail` carries `spec_sha256` (the new spec's), and when the newest spec review was an APPROVE of the old spec, `warnings` gains `spec review ID (APPROVE) no longer applies: the spec changed (sha256 OLD -> NEW); review the new spec again before its first dispatch`. Breaking change (LESS-3): the new spec is linted as in `task create`; a lint error exits `1` with the same `spec lint: …` error and leaves the spec and the events unchanged, and each lint warning is one more `spec lint: …` line at the end of `warnings`. Additive (SR-3): an author's APPROVE (`spec review confirm`) replaces the spec the same way, under the same statuses, and writes a `spec_updated` event too; so it counts as a spec change after a REJECT, and a rejected `important` / `high` task whose spec was replaced that way is dispatched again without the "spec unchanged since the REJECT" refusal. An `accepted` task (DOC-1) is refused like `pass` and `cancelled`.

Additive refusal (RD-2): as in `task create`, before spec lint a spec in which any line or any string value holds what looks like a secret exits `1` with the error starting `refusing: the spec contains what looks like a secret` (kinds, field paths and line numbers, never the value); the spec and the events are unchanged. (RD-4) As there, an object key that holds a secret is refused too, whether or not it is written with `\u` escapes.

### `thoth task close TASK --reason TEXT --json`
Abandons a task: `queued`, `failed`, `interrupted`, `unverified` or `reject` → `cancelled` (`queued` is additive, SR-1: a task stopped by three spec review REVISE in a row is still `queued`), with one `task_closed` event (`detail.from`, `detail.reason`). Relied on: exit code, `status` (`cancelled`), `previous_status`. It exits `1` and writes nothing from any other status, while a run of the task is `queued` / `running`, or with an empty `--reason`. Changed (WT-1): it then removes the clean worktrees of this and every other `pass` / `cancelled` task (the same sweep as `worktrees prune`, below, without its branch cleanup); the branches stay until the next `task create` or `worktrees prune`. Additive key of `--json`: `worktrees`, `{"removed":[{"task_id","path","kind","head","branch","task_status"}],"kept":[{"task_id","path","kind","reason","detail","task_status"}]}`; when the sweep failed, or was skipped because the current directory is inside the worktrees directory, it is `{"removed":[],"kept":[],"error":"…"}` and the command still exits `0` with `ok` true (the task is closed). The key is absent when `THOTH_RUN_ID` is set, where no sweep runs.

Additive (DOC-1): a docs, research or review task (spec `task_type` `docs`, `research` or `review`) is also closed from `in_review` (`detail.from` `in_review`), for a delivery that is not used; to take a delivery, use `task accept`. An `in_review` task of any other `task_type` (or none) is still refused, and the error adds that from `in_review` only a docs, research or review task can be closed (it contains `docs, research or review`). `accepted` is refused like `pass` and `cancelled`.

### `thoth task accept TASK --reason TEXT --json`
New (DOC-1). Takes the delivery of a document task: `in_review` → `accepted`, a final status (no `dispatch`, `task update-spec`, `task close`, `review start`, `review record`, `spec review start`, `spec review record` or `resume` afterwards). A document task is one whose spec `task_type` is `docs`, `research` or `review`; whether the spec lists `checks` does not matter. Nothing is written to the reviews table and no `verdict` event is written, so `thoth models` counts the run as completed but not reviewed (no `pass`, no `reject`) and its records line has `verdict` null. It writes one `task_accepted` event (`detail`: `from`, `reason`, `task_type`, and `run_id`, `result_status`, `candidate_commit` of the task's newest `result_ingested` event, each null when there is none) and the task's `status_change`. Relied on: exit code, `status` (`accepted`), `previous_status` (`in_review`), `run_id`. The `--json` keys are exactly `ok`, `task_id`, `previous_status`, `status`, `reason`, `run_id`, `result_status` (`completed` | `blocked` | null), `candidate_commit`, `worktrees`. Then it removes the clean worktrees of every finished task as `task close` does; `worktrees` has the same shape (it is always present: the command refuses when `THOTH_RUN_ID` is set). It exits `1` and writes nothing when `THOTH_RUN_ID` is set (checked first; the error names `THOTH_RUN_ID`), with an empty or blank `--reason`, when the task is not `in_review` (the error names the status), when it is a task of another `task_type` (the error says it is a code task and names `review start` and `review record`), or while a run of the task is `queued` / `running` (the live-run error of `dispatch`, starting `task accept: `). Breaking change (RFIX-2): it also exits `1` and writes nothing (no `task_accepted`, the task stays `in_review`) when a docs or review task has a pending fix (`review show TASK --json`'s `pending_fix` true, after `review start --edit`); the error says the task has a pending fix, names the edit review run, and lists, in this order, `thoth verify EDIT_RUN` and `thoth review confirm TASK --profile P --model M --effort E --reason TEXT`. A document task without a pending fix is accepted as before. Human output: `TASK accepted (in_review -> accepted)`, then the worktree text of `task close`. MCP: `thoth_task_accept` (`task`, `reason`).

### `thoth task result TASK [--run RUN] --json`
New (DOC-1). Read-only (no event): the result.json the task's worker delivered, from the task's newest `result_ingested` event, or with `--run` that run's newest one (the run must belong to TASK). It reads the event, so it works at any status, after `task accept` or `task close` too. Relied on: exit code, `summary`, `claims`, `run_id`. The `--json` keys are exactly `ok`, `task_id`, `task_status`, `title`, `run_id`, `attempt`, `role`, `profile`, `model`, `candidate_commit`, `worktree`, `ingested_at` (the event's time), `result_status` (`completed` | `blocked`), `summary` (the worker's text in full, not cut), `claim_count`, `claims` (`[{"kind","text","evidence","sources"}]`, `evidence` the claim's codes as the worker wrote them, `[]` when none; `sources` additive, RES-1a: the claim's `[{"url","quote"}]` as written, `[]` when none). It exits `1` when there is no such event (the error names the task's status, says there is no ingested result.json and points to `thoth events --task TASK --json` for `result_invalid`), and when `--run` names a run of another task. Human output: the task id, status and title; the run id, attempt, role, profile, model and candidate commit; `summary:` and the text indented two spaces; `claims (N):` and one `- KIND: TEXT [CODES]` line per claim, each source of it on its own line below, indented four spaces: `URL  "QUOTE"`, the quote cut at 120 characters plus `...` (RES-1a). MCP: `thoth_task_result` (`task`, `run`), read-only. Additive (BRIEF-1): `brief`, `brief_source` (`worker` | `summary`) and `brief_truncated`, the selected event's short conclusion (see "Briefs" under `thoth wait`; an event written before BRIEF-1 is read from its `result_json`); `summary` and `claims` stay whole, and a `task accept`ed delivery reads the same. Human output adds `brief: TEXT` before `summary:`, with `  (cut at 1000 chars; full text: thoth task result TASK --run RUN)` when it was cut.

### `thoth review start TASK --profile ID [--model MODEL] [--effort LEVEL] [--reason TEXT] [--edit | --no-edit] --json` / `thoth verify RUN --json`

Breaking change (RFIX-2): a code task's review is in edit mode unless
`--no-edit` is given. A code task is one with no `task_type`, or one that is
not `docs`, `research` or `review` (the same rule as `task accept`). With
neither flag, `review start` on a code task now behaves exactly as `--edit`
(`mode` `edit`, `fix_branch`, the `-aN-fix` worktree, the edit-mode prompt
and schema); before RFIX-2 it was a plain review. New `--no-edit` (MCP `edit`

meaning on a code task. `--edit` with `--no-edit` exits non-zero (a usage
error) and writes nothing. A `docs` or `review` task is still a plain review
with neither flag (or `--no-edit`); `--edit` on one is no longer refused and
attaches a fix through the same steps as a code task (the bounds, `thoth
verify EDIT_RUN`, the protected-change approval on the edit run and `thoth
review confirm` by another model or effort). A `research` task's review is a

naming the research task and that it cannot attach fixes), before anything
is written; with neither flag or `--no-edit` it is the source check as
before. A caller that relied on a plain review without a flag passes
`--no-edit` now.

Additive (RES-1b): a research task's reviewer checks the sources in the target
run's latest accepted result. After the in_review and live-run checks, before
any evidence preparation or other write, no research claim is refused with
exit 1 and guidance to `task result`, `task close` and `dispatch`. Claude
`allowed_tools` is `Bash,Read,Glob,Grep,WebFetch,WebSearch`; agy is its reviewer
list below plus `search_web,read_url_content`; codex's stored string is unchanged

`require-reason` switch; there is no extra same-provider rule for research.

The fix worktree must be at the fix, clean and the fix branch still at the fix; the run row's transaction re-checks the live run, the pending fix, HEAD, the branch and the verify's `seq`, and the runner checks again before the launch, then writes `.agent/review-fix-input/` (`spec.json`, `findings.json`, `edits.json` as in `review_fix_applied`, `fix.patch`; masked, see Secret masking). `--json`: `review start`'s keys with `mode` `confirm`, plus `confirms_review_id`, `fix_commit`, `fix_branch`, `fix_verify` (`{seq, ok, failures}`; `ok` when at least one check ran, none failed, and every row has `exit_code` 0 and `error` null), `implementer_provider` and `same_provider_as_implementer` (MEAS-0: `review start --json` has the same two keys now). The confirmer's document, delivered like `review start`'s (codex and agy: strict schema, `note` required): `{"verdict":"APPROVE"|"REVISE","edits":[{"index":0,"verdict":"ok"|"revise","note":"…"}]}`; a wrong shape, a `revise` without a note, APPROVE with a `revise` or REVISE without one is `review_invalid` stage `schema`, an index missing, unknown or repeated stage `coverage`, a confirmer that changed a project file or moved HEAD or the fix branch stage `worktree` (while the fix branch still points at the fix commit, Thoth puts the fix worktree back at it, untracked and ignored files outside `.agent/` and `.agents/` removed, so the next confirm can run without a new verify; the reason says whether it did); then one transaction re-checks the task is `in_review` (else stage `status`) and the newest review is still the edit review (else `superseded`), and (additive, GATE-1) before a PASS that every protected change of the fix is approved on the edit run (else stage `protected`, `source` `author_check`). An invalid confirm writes no review: the task stays `in_review` and the fix pending. APPROVE with `fix_verify.ok` is PASS, anything else REJECT, written with the task status and the `verdict` in that transaction; (REV-3) a required check that did not run on the edit review run (worked out in that transaction by the rule under "Required checks" in `thoth review record`, from the edit run's verifies) also makes it REJECT, whatever the confirmer said, and the `verdict` records the list as `detail.checks_not_run`; the confirm run's `candidate_commit` is the fix commit. The PASS record judges every criterion an edit was bound to met (an originally unmet one citing the fix's diff and verify evidence, its note naming the fix and the confirm run) and keeps only the extra findings no edit was bound to; the REJECT record keeps the edit review's criteria and extra findings and adds one extra finding per revise (`author check REVISE on fix edit N (PATH): NOTE`), one for a red verify (check id, exit, evidence code), (REV-3) one with category `check_not_run` per required check that did not run on the fix (`required check ID did not run on the verify of the fix FIX (REASON)`) and one saying the fix was not adopted. The REJECT record copies no `fix_size` or `category` from the edit review. REV-2: the PASS record keeps an unmet criterion no edit was bound to (after `size`, only an advisory one) exactly as the edit review judged it: `verdict` still `unmet`, `note`, `evidence`, `fix_size` and `category` unchanged, not written as fixed. Of the extra findings it keeps, an advisory one keeps its `fix_size` and `category`; every other one loses both (and so counts as blocking). Met criteria lose both labels as before. `review show TASK --json` lists the kept advisory findings in `advisory`, and `brief` lists the kept unmet criterion as it lists any unmet one; `findings.author_check` (`{confirms_review_id, copied_extra_findings}`) marks the record, and `retro` counts only its added extra findings, not the record itself. `dispatch` after a REJECT starts the next attempt from the implementer's candidate.

Additive (MEAS-1): the confirm's PASS and REJECT records copy `findings.prior_rejection` and `findings.prior_rejection_check` of the edit review they confirm unchanged, and the confirm's `verdict` event's `detail.prior_rejection` summarises that check; `retro` counts the marks on the edit review only.

### `thoth checks add | approve | list | remove` (additive)
The repo's catalogue of approved checks, kept in `state.db`. The commander proposes checks and approves them, with a reason (LESS-5); a person can also approve in a terminal. `verify` runs only these (see above). `add`, `approve` and `remove` exit `1` and write nothing when `THOTH_RUN_ID` is set (inside a worker or reviewer).
- `thoth checks add ID --cmd COMMAND [--shell argv|cmd|powershell|sh|bash] [--cwd PATH] [--exe-pin hash|path] [--input PATH]... --json` → `{"ok":true,"check_id","shell","cmd","cwd","inputs","status":"pending","exe_pin"}`. `inputs` are repo-relative `/` paths: the `--input` files plus the ones Thoth infers (files named in the command, and the toolchain's own such as `Cargo.lock`). An existing ID is replaced and loses every approval, even when the new definition is identical (LESS-1). `--exe-pin path` (pin the program's resolved path, not its bytes) is refused when the program lies in the repository tree, lies in a worktree, is written as a relative path, or does not resolve; that, and a value other than `hash` or `path`, exits `1` and writes nothing.
- `thoth checks approve [--run RUN] --json` → `{"ok":true,"approved":[{"check_id","fingerprint","source"}],"unchanged":["id"]}`; `source` is `main` or `run`. A check whose current fingerprint equals one of its approvals is listed in `unchanged`; every other check gets one more approval (LESS-1: earlier approvals are kept, not replaced; a check that matches only through package-info auto-accept is approved too). For each approved or unchanged check, its Cargo.toml / Cargo.lock inputs are stored in the blob store for package-info auto-accept. With nothing to do the human output is `nothing to approve` and `approved` is empty. Additive: only when an `--exe-pin path` check is refused this time does the output also have `"refused":[{"check_id","reason"}]`; a refused check is not approved, the others are, and the exit code is still `0`.
- LESS-5: `thoth checks approve [--run RUN] [--reason TEXT] --json`. **Breaking change:** with no terminal attached (stdin and stdout not both a terminal: the commander's shell, `!` in Claude Code, or the MCP tool) `--reason` is required; without it, or with a blank one, it exits `1` and writes nothing (`checks approve needs --reason when no terminal is attached …`, `--reason must not be empty`). A person at a terminal may leave it out. Additive keys: `approved_by` (`human_terminal` | `commander_cli` | `commander_mcp`), `reason` (string or null), `protected_approved` (`[{"path","status","kind"}]`: with `--run`, the run's `test`, `check_word` and (additive, LEAN-1) `inline_test` changes from its newest diff evidence that no earlier approval of that run covers, approved now and recorded in one `protected_change_approved` event) and `protected_unchanged` (paths of those changes an earlier approval already covers); both are `[]` without `--run`, and when the run has no diff evidence or its `protected_changes` cannot be read (then stderr has `warning: run RUN's diff evidence CODE has no readable protected_changes; run review start, then approve again`, with or without `--json`; GATE-1: for an edit review run the warning ends `run review confirm, then approve again`, and a row with a `protected_changes` array but no `inline_test_errors` array, written before LEAN-1, is not readable either and approves nothing). GATE-1: a reviewer fix's protected changes are approved with `--run EDIT_RUN` (the edit review run, whose newest diff evidence is the fix's); they need that approval before `review confirm` starts. Human output adds `approved by WHO; reason: TEXT` and one `approved protected change of run RUN: PATH (STATUS, KIND)` per protected change approved. Additive refusal: with `--run`, while RUN's task has a run that has not ended, it exits `1` and writes nothing (`checks approve --run RUN refuses while task TASK has a live run (LIVE_RUN is STATUS): …`); a live run of another task, and `approve` without `--run`, are not refused. The whole approval is one write transaction.
- `thoth checks list --json` → `{"checks":[{"check_id","status","shell","cmd","cwd","inputs","approved_at","approved_fingerprint","changed","exe_pin"}]}` sorted by `check_id`. `status` is `approved` | `stale` | `pending`; `changed` lists the fingerprint lines that differ for a `stale` check (e.g. `input=Cargo.toml`), else `[]`.
- additive (LESS-1): `status` is `approved` when the main tree matches any approval, exactly or through package-info auto-accept (as `verify`), `stale` when it matches none (`changed` is against the newest approval), `pending` without approvals; there are still only these three values. `approved_at` and `approved_fingerprint` are the newest approval's. Each entry also has `other_approvals` (the number of approvals besides the newest, `0` without any), `match` (`exact`, `package_info_only` or `null`), `matched_approval` (`null` or `{"fingerprint","approved_at","source","run_id"}`; `source` is `main`, `run` or `migrated` for an approval made before state.db v6) and `package_info_lines` (as `verify`). The human line ends `  (+N earlier approvals)` when `other_approvals` is above 0, and a `package_info_only` check has a next line `  auto-accepted (only package info changed): PATH:LINE, …`. `list` writes nothing.
- `thoth checks remove ID --json` → `{"ok":true,"check_id","was_approved"}`; an unknown ID exits `1`. Additive (CK-1): `was_approved` is true when the removed check was approved. Removing a check forgets every approval of it (LESS-1).
- additive (LESS-3): `thoth checks add --json` also has `hints`, an array of strings, `[]` when there is nothing to say. A `cargo test` command (`cargo` or `cargo.exe`, by any path, whose first word not starting with `-` or `+` is `test` or `t`) without `--no-fail-fast` before a lone `--` gets `cargo test stops at the first test target that fails, so later targets and their new tests never run; consider cargo test --no-fail-fast`. The human output has the same text as a last line starting `hint: `. A hint never refuses: the check is still stored as `pending`.
- additive (P7-2): `thoth checks list --json` also has `protected_patterns` (array of strings, sorted), the repo's extra protected-file patterns.
- additive (P7-2): `thoth checks protect PATTERN --json` → `{"ok":true,"pattern","added","protected_patterns"}` and `thoth checks unprotect PATTERN --json` → `{"ok":true,"pattern","protected_patterns"}`. `pattern` is the stored form (lower-cased, `/` separators); `added` is false when it was already there. A pattern is `name/` (a path segment), a file name with at most one `*` at its start or end (`*.snap`, `golden_*`), or a whole path; any other shape (`a*b`, `**/x`) exits `1`, as does `unprotect` of a pattern not in the list. Both exit `1` and write nothing when `THOTH_RUN_ID` is set. A changed file matching a pattern is reported as kind `test`.
- additive (VSCOPE-1): `thoth checks add ID --cmd COMMAND --scope cargo-test-targets --json` marks a `cargo test` check as scoped: `verify` runs it with the task's test targets appended (see `thoth verify RUN --json` above). The output also has `scope` (string, or null without `--scope`). `--scope` accepts only `cargo-test-targets`; any other value exits `1` and writes nothing. The scope is part of the approval: a scoped check's fingerprint has one more line `scope=cargo-test-targets` (right after `cwd=`), so adding, removing or changing it needs a new approval; a check without a scope fingerprints exactly as before, so existing approvals stay valid. `thoth checks list --json`: each entry also has `scope` (string or null); the human line ends `  scope cargo-test-targets` for a scoped check. The `check_added` event detail also has `scope`. state.db gains a nullable `checks.scope` column on first use (NULL for every existing check); its schema version stays 6.

### `thoth suite run [--commit REV] [--check ID]... [--test NAME]... [--timeout D] [--json]` (additive, VSCOPE-1)
Runs approved checks on a main-line commit and records the result, for the whole-suite run before pushing the main line (see `docs/phase2/usage.md`, "The suite before pushing"). REV defaults to the main worktree's HEAD. The checks run in a temporary detached checkout of REV (as `verify --at-base` uses, under the repo's `baseline-worktrees/`, removed afterwards). Without `--check`: every check in the catalogue that has no scope, in `check_id` order. With `--check`: only those, in the order given. `--test NAME` (letters, digits, `_`, `-`) is accepted only with exactly one `--check` that has a scope; that check then gets `--test NAME` appended per name, without the task rules. Any other use of `--test` exits `1`, runs nothing and records nothing; so does a catalogue with no unscoped check when `--check` is left out. `--timeout` is per check (default `120m`). Approval rules are verify's: an unapproved check or a fingerprint mismatch is a row with `error` set, not run. Records one `suite_ran` event (no task, no run) whose detail is the `--json` output: `{"commit","full","checks","tests","failures","results","ok"}`. `commit` is REV's full sha; `full` is true when neither `--check` nor `--test` was given; `ok` is true when every row has `exit_code` 0 and `error` null. Each `results[]` row: `index`, `check_id`, `shell`, `cmd` (the approved command), `cwd`, `argv` (what ran, appended arguments included; `[]` when refused), `appended_args` (only with `--test`), `exit_code`, `duration_ms`, `evidence` (always null: there is no task), `stdout_bytes`, `stderr_bytes`, `output_truncated`, `error`, `exe_pin`, `fingerprint_ok`, `approval`, `package_info_lines`, `sha256` and `blob_path` (the stored output: stdout, then a line `--- stderr ---` and stderr when there is any; both null for a row that did not run). Exit `0` when `ok`, `1` otherwise. A `suite_ran` is not a verify of any run: it never counts for the required-check rule (REV-3).

Additive (SWEEP-1): after its argument refusals and just before it makes its checkout, `suite run` sweeps the leftover baseline checkouts (see `thoth worktrees prune --json`) and gives its own checkout an owner record (`baseline-holds/NAME.hold`, locked until it returns). `--json` always has one more key, `baseline_sweep`, with the shape given there; the `suite_ran` detail carries it too and stays equal to the `--json` output. Stderr has one line per removed leftover and per failure, as for `verify --at-base`. It never changes `ok` or the exit code.

### `thoth suite show [--json]` (additive, VSCOPE-1)
→ `{"head_commit","last","last_green_commit","head_green","merges_since_green"}`. `head_commit` is the main worktree's HEAD now. `last` is the newest `suite_ran` detail plus its `ts`, or null. `last_green_commit` is the `commit` of the newest `suite_ran` with `full` and `ok` both true, or null. `head_green` is true when `last_green_commit` equals `head_commit` (a green run with `--check` or `--test` does not count). `merges_since_green` is the merge commits on HEAD's first-parent line after `last_green_commit`, oldest first, each `{"commit","subject"}`; null when `last_green_commit` is null or not an ancestor of HEAD, `[]` when there are none. The human output's first line says whether HEAD is green. Writes nothing; exit `0`.

### `thoth worktrees prune --json`
New (WT-1). Removes the clean worktrees of every `pass` / `cancelled` / `accepted` task of the repo (`accepted` is additive, DOC-1), worker and review alike, and lists what it removed and kept. A task with a `queued` / `running` run is skipped. A worktree is removed only with `git worktree remove --force`, and only when it lies under the repo's worktrees directory, has no uncommitted change outside `.agent/` and `.agents/`, and its `HEAD` is contained in some local branch; commits and evidence are never touched. Additive (branch cleanup): before git is run, every directory symlink or junction inside the worktree (found without following any link, `.git` skipped) is removed as a link entry, never its target; when an entry cannot be read, inspected or removed, nothing else is done to that worktree (no git, no recursive delete) and it is kept with reason `link_unremovable` and a `detail` naming the entry and the error. Then `git worktree prune` runs. It exits `1` and does nothing when `THOTH_RUN_ID` is set (stderr names `THOTH_RUN_ID`) or when run from inside the worktrees directory (stderr: `run worktrees prune from the main working tree, …`). Relied on: `ok`, `removed`, `kept`, `tasks_checked`; `removed[]` and `kept[]` entries have the keys listed under `task close`. `tasks_checked` counts the finished tasks with no live run. `ok` is false, and the exit code `1`, when an entry of `kept` has reason `remove_failed` or `git_error`; otherwise `ok` is true and the exit code `0`, whatever else was kept (`link_unremovable` included). Each removal and each newly kept directory is an event (`worktree_removed` / `worktree_kept`, see `events`).

Behaviour change (SMALL-11 (1)): the branch cleanup below also covers the reviewer fix branch `thoth/TASK/aN-fix` (N digits) of a `pass`, `cancelled` or `accepted` task, by the same rules: deleted when merged into the task's base branch (`merged_by` `ancestor` or `cherry`), listed in `removed_branches` and recorded as a `branch_deleted` event; kept with the same reasons (`branch_unmerged`, `branch_checked_out`, `branch_is_a_base`, `no_base_branch`) in `kept_branches` and a `branch_kept` event. The keys are unchanged: branches named `aN-fix` now appear in the existing lists. Any other name under `thoth/TASK/` (for example `a1-fix2` or `a1-fixed`) is neither deleted nor listed. This applies to `thoth task create`'s sweep too.

Additive (SMALL-11 (5)): a worktree that a running `thoth verify RUN` (not `--at-base`, not `--dry-run`) is using is kept by every sweep (the runner when a task settles, `review record` after a PASS, `task close`, `task accept`, `task create`, `worktrees prune`): it is listed in `kept` (here, and in `task close --json`'s `worktrees.kept`) with the new `reason` `verify_running`, and a `worktree_kept` event with that reason is written once (deduplicated as for the other reasons). When that verify exits, whatever its result and if no other verify is running there, it removes its task's worktrees by the same checks as the other sweeps when the task is now `pass`, `cancelled` or `accepted`, writing `worktree_removed` (or `worktree_kept`) with the additive `detail.source` `verify`; `verify --json` and its exit code are unchanged. A verify that was killed holds nothing (the hold is an operating-system file lock, released when the process ends): the next sweep removes the worktree as usual.

Additive (SWEEP-1): every prune that gets past its refusals, also when no task is finished, first sweeps this repository's `baseline-worktrees/` folder (the temporary checkouts of `verify --at-base` and `suite run`), before its `git worktree prune`, and reports it in one more key, `baseline_sweep`: `{"removed":[{"path","made_by","run_id"}],"kept":[{"path","reason","detail"}],"error"}`, both lists in path order. A checkout whose owner record (`baseline-holds/NAME.hold`) nobody holds the lock of was left by a command that is gone: it is removed with its git registration and listed in `removed`, `made_by` `suite_run` (`run_id` null) or `verify_at_base` (`run_id` the RUN of its name). `kept[].reason` is `in_use` (the lock is held, or the record cannot be opened), `remove_failed` (still there after the attempt; `detail` has the error, null for every other reason; the next sweep tries again; the human line ends ` - ` and the whole `detail`, each line break with the white space around it written as `; `), `no_owner_record` (a Thoth-shaped checkout git lists with no record, from a Thoth before SWEEP-1: never touched; the human line ends ` - remove it with git worktree remove --force PATH once no thoth older than this version is running`) or `not_thoth_checkout` (anything else in the folder: never touched). `error` is null, or the message when the folder could not be read (then both lists are empty); a missing folder is an empty result. The human output adds `  removed  baseline  PATH  (left by suite run)` / `(left by verify --at-base RUN)` and `  kept     baseline  PATH: REASON` lines after its others. None of this changes `ok` or the exit code, and no event is written for it. The same key and shape appear in `suite run --json` and `verify RUN --at-base --json`.

Additive (branch cleanup): after the worktrees, the same sweep looks at every local branch named exactly `thoth/TASK/aN` (and, SMALL-11 (1), `thoth/TASK/aN-fix`) of each of those tasks, worktree or not. It deletes one only when no worktree has it checked out, the task has a `base_branch` (`task show --json`) whose `refs/heads/` ref exists, and either the branch tip is an ancestor of that ref (deleted with `git branch -d`, checked against the base rather than the main tree's `HEAD`; `merged_by` `ancestor`) or `BASE..BRANCH` has no merge commit and `git cherry BASE BRANCH` lists only `-` lines (every commit already applied, for example cherry-picked; deleted with `git branch -D`; `merged_by` `cherry`). Remote branches, the task's base branch and any other task's base branch are never deleted. Two more keys: `removed_branches` (`[{"task_id","branch","tip","merged_by"}]`) and `kept_branches` (`[{"task_id","branch","reason"}]`, plus `detail` only for a failure). `reason` is `branch_checked_out`, `no_base_branch` (none recorded, a detached start, or the ref is gone), `branch_unmerged` (work the base does not have, a merge commit on the branch, or an inconclusive or failed check, then with `detail`), `branch_is_a_base` (another task was created from it) or `branch_delete_failed` (git refused; `detail` has its message). Neither key changes `ok` or the exit code. Each deletion writes `branch_deleted` and each newly kept branch `branch_kept` (once per branch and reason, see `events`). `task create` runs the same branch cleanup (its `--json` keys do not change); `task close`, `task accept`, `review record` and the runner do not.

### `thoth pipeline start TASK [--implementer PROFILE:MODEL[:EFFORT]...] [--reviewer PROFILE:MODEL[:EFFORT]...] --reason TEXT [--max-attempts N] [--timeout D] [--review-timeout D] [--verify-timeout D] [--verify-wait D] [--quota-threshold N] [--fold-on-reject] [--json]`

New (AUTO-1a). Starts a background pipeline that runs a code task to a short conclusion: dispatch, wait, the protected-change gate, verify, review start and the verdict. Every choice is the commander's: the two lists are ordered `PROFILE:MODEL[:EFFORT]` entries (repeat the flag; order and duplicates are kept as given). Breaking change (AUTO-1b): AUTO-1a used the first entry of each list only and stopped at a REJECT or an interruption; now the pipeline walks both lists forward (see "Continuation (AUTO-1b)" below): a REJECT is reworked on the next implementer entry, a quota or auth stop hands over to the next entry, a crash is resumed once, a timeout is retried once at twice its limit, and a reviewer that stops is replaced by the next reviewer entry. Thoth never picks, ranks or reorders an entry and takes no choice from `recommend`, external scores or pass rates: `recommend` and `profile usage` are read only as facts about the entry the list already names. `--reason` is required even when `require-reason` is off; every launch the pipeline makes carries `--reason "pipeline ID step N: REASON"` (AUTO-1b: a launch with context, or past the first entry, says `pipeline ID step N: CONTEXT; implementer|reviewer entry K of L: REASON`, CONTEXT naming the REJECT review and attempt, the stopped run, its profile and cause, or the retry).

Additive flags (AUTO-1b): `--quota-threshold N`, a whole number from 1 to 100 (anything else, `0`, `101`, a negative number, a fraction or an empty value, is refused like the other invalid values): an entry whose deciding quota window is at least N percent used is skipped. Left out (null), only `recommend`'s eligibility decides. `--fold-on-reject` (default off): at important or high risk, a REJECT's findings are appended unchanged to the spec's constraints and the task is reworked, instead of stopping for the commander's rewrite (the 2026-10-19 opt-in; below).

Entry states (Breaking change, AUTO-1b): the task may be `queued`, `in_review`, `reject`, `unverified`, `interrupted` or `failed`; any other status is still refused before anything is written. A new pipeline starts both list positions at 0, so from `reject`, `unverified`, `interrupted` or `failed` it searches from the first entry (the previous run was not launched by this pipeline): `reject` goes to the REJECT handling below; `unverified` left by the delivery is the bounded reroute (one more dispatch in the same attempt, with the preflight) while `unverified` left by a reviewer (in `thoth events --task TASK --json`, an `UNVERIFIED` `verdict` or a `review_invalid` after the `result_ingested` of the newest implementer run) stops `review_unverified` with no launch; `interrupted` with reason `quota`, `auth`, `crash` or `transient` gets a fresh dispatch (never a resume), and with any other reason stops `run_interrupted`; `failed` with reason `timeout` gets one dispatch at twice that run's `timeout_seconds` (the attempt's one timeout retry), and any other `failed` stops `run_failed`.

Refusals (exit `1`, `{"ok": false, "error": …}` on stderr with `--json`), all before any pipeline, event, run or worktree exists: THOTH_RUN_ID set; the repository not initialised; an unknown task; a docs, research or review task (the error points to `thoth task accept`); another running, non-stale pipeline for the task (named before the task's own state, with its id, step and `thoth pipeline stop TASK`); a task outside the entry states above (the error lists them); an empty list; an invalid `--quota-threshold`; an invalid entry anywhere in either list (the error names the flag and the one-based position, `invalid --implementer entry 2 of 2 ('…'): …`); `--max-attempts` below 1; a missing or blank `--reason`; an invalid duration (`45`, `5s`, `30m`, `2h`; at least 1 second). An entry has exactly two or three non-empty parts, an existing profile of a supported harness, an explicit model the profile's harness accepts (the same check as `dispatch`) and an effort from `low`, `medium`, `high`, `xhigh`, `max`, `ultra`; `auto` is refused in any part. The effort may be left out only where `dispatch` allows it: a model without an effort setting (`haiku`) or an agy model whose name carries its level.

**Stored default lists (LIGHT-1, additive).** Each list is decided on its own. A list whose flag is given is that flag's entries, exactly as before, and its stored default is not read. A list whose flag is left out is the stored default list of `thoth pipeline defaults set` (below), its entries in stored order with duplicates, used as stored (Thoth never picks, ranks, reorders or shortens it), and only when the task's risk (`risk` in `thoth status TASK --json`; a spec without risk is `normal`) is `low` or `normal`: only those tasks take the light path; an `important` or `high` risk task takes the heavy path, where the commander chooses both lists for the task in hand. The defaults file is read only when a flag is left out, so with both flags given a missing or broken file changes nothing and the start is as before apart from the four additive `settings` keys below. `--reason` stays required in every case; a stored list's reason does not replace it and is not added to the launches' reasons. A stored list is walked exactly like a flag list (positions, skips, rework, rotation and stop reasons unchanged). New refusals, each before any pipeline, event, run or worktree exists:
- A flag left out and no list of that kind stored (no file, or that list null): refused where the empty-list refusal always was (before the not-initialised and unknown-task refusals), with an error that starts `the implementer list is empty` (or `reviewer`) and names `--implementer PROFILE:MODEL[:EFFORT]` (or `--reviewer`) and `thoth pipeline defaults set`.
- A flag left out and a defaults file that cannot be read or parsed: refused at that same point, naming the file's path.
- A flag left out on an `important` or `high` risk task: refused after the task's own refusals (document task, running pipeline, entry state) and before any entry of either list is checked, so a stored entry that no longer validates is not what is reported at these risks. The error names the task's risk, the missing flag(s) and that a stored default is used only at low or normal risk. With both flags given such a task starts as before.
- A stored entry that no longer passes the entry check on this machine (its profile is not registered here, its model is no longer accepted, ...): refused where an invalid flag entry is, `invalid stored default --implementer entry K of L ('ENTRY'): WHY` (or `--reviewer`), naming `thoth pipeline defaults set` and the flag as the two ways out. Nothing is skipped: one bad stored entry refuses the start.

Defaults: `--max-attempts` is the task's `attempt_cap`, an absolute ceiling on the task's attempt number (a restart does not get a fresh allowance); `--timeout` and `--review-timeout` are `null` and then no `--timeout` is passed, so `dispatch` and `review start` keep their effort-based default (1h for none, low or medium, 3h for high, 4h for xhigh, max or ultra); `--verify-timeout` is `120m` per check (a low-parallel full suite takes 35 to 45 minutes); `--verify-wait` is `2h`, separate from it.

`--json` keys: `ok`, `pipeline_id`, `task_id`, `status` (`running`), `step` (`starting`), `settings`, `pipeline_pid`, `warnings`. `settings`: `implementers` and `reviewers` (arrays of `{"profile","model","effort"}`, `effort` null when left out), `max_attempts`, `timeout_seconds`, `review_timeout_seconds` (null when left out), `verify_timeout_seconds`, `verify_wait_seconds`, `reason` (masked), (additive, AUTO-1b) `quota_threshold` (integer or null) and `fold_on_reject` (bool), and (additive, LIGHT-1) `implementers_source` and `reviewers_source` (`flag` or `default`) and `implementers_default` and `reviewers_default` (null for a list from its flag, otherwise `{"reason","set_at"}` of the stored list used). `implementers` and `reviewers` keep their shape whatever the source. The same `settings`, with the four keys, is in `pipeline show`, in the `pipeline_started` event's detail and in the MCP results. `warnings` is an array of strings; Breaking change (AUTO-1b): AUTO-1a's "only the first implementer and the first reviewer are used" warning is gone, so it is `[]` today. A background process that cannot be started settles the pipeline at once with stop reason `spawn_failed` and the command exits `1`. A running pipeline that is stale (see `show`) is recorded as `stopped` with reason `stale` before the replacement starts.

Example, with a cross-provider reviewer at a middle model and effort first and a same-provider stand-in after it (claude-a or claude-c, never claude-b), as decided on 2026-10-27:

```
thoth pipeline start 01J... --implementer claude-b:sonnet:medium \
  --reviewer codex-a:gpt-5.6-luna:medium --reviewer claude-a:opus:high \
  --verify-timeout 120m --reason "sonnet medium fits a normal-risk change; codex reviews across providers" --json
```

What the background does, in order (each launch is an ordinary thoth command run as a child in the repository root with `--json`, no input, `THOTH_PIPELINE_ID` set and THOTH_RUN_ID and THOTH_VIA_MCP removed):

1. On entry: a cancelled task stops `task_cancelled`; `thoth review show TASK --json`'s `pending_fix` true stops `needs_fix_confirmation` before any step; an attempt above `max_attempts` stops `attempts_exhausted`; a live implementer or reviewer run is attached to (no new launch).
2. From `queued`: `thoth dispatch TASK --profile P --model M [--effort E] --reason R [--timeout D] [--allow-attempt A] --json` with the first usable implementer entry (the preflight below); a refusal stops `dispatch_refused` with dispatch's own error, except the continuations below. Completion is observed through `thoth wait --run RUN --json` and `thoth status TASK --json`. A cancelled task stops `task_cancelled`; an interrupted or failed run continues as below or stops `run_interrupted` / `run_failed` (the stop keeps the run's `interrupted_reason`, `error_text` and `next_step`); a run that is still `running` with a stale heartbeat that `thoth status` could not settle stops `runner_lost` (run id, last heartbeat, `thoth cancel RUN`). Behaviour change (SMALL-11): a run whose runner is dead is normally settled first, as interrupted with reason `crash`, by the `thoth status` the pipeline reads while it waits, so the pipeline resumes it once as for any crash (a `resume` step whose reason names the crash) instead of stopping `runner_lost`. An `unverified` delivery is dispatched once more in the same attempt (the existing reroute, with the current entry when it is still usable, else the next), then stops `unverified_twice` with the `result_invalid` reason.
3. From `in_review` (a completed implementation, or a restart): the protected gate. The candidate's diff evidence is recorded first when it is missing or its `protected_changes` cannot be read (as `review start` does); when that fails, `protected_unreadable`, never "nothing changed". Unapproved `test`, `inline_test` or `check_word` changes stop `needs_approval`: `stop.evidence` has `run_id`, `diff` (the diff evidence code) and `changes` (`path`, `status`, `kind`); `stop.next` names `thoth review packet TASK` and `thoth checks approve --run RUN --reason TEXT`. The pipeline never approves; after your approval, `pipeline start` again continues that candidate. Check inputs stay with verify's fingerprint check.
4. Verify: wait for a verify slot (step `verify_wait`; `verify_wait_timeout` lists the holders and their files), then `thoth verify RUN --timeout D --json` on the candidate, inheriting the environment the pipeline was started with (set `CARGO_BUILD_JOBS` and `RUST_TEST_THREADS` yourself; Thoth sets neither) and, on Windows, at below-normal priority. The result is read, not the exit code alone: `no_approved_checks`, unreadable output, a refused check or a check that failed to run stops `verify_blocked` with the hint; a non-zero exit, timeout, incomplete or signalled check releases the slot and tries once more, then stops `verify_failed` with both attempts' evidence codes and the failed checks. All checks need `exit_code` 0 and `error` null. `missing_since_last_verify` is reported as verify reports it.
5. Review: `thoth review start TASK --profile P --model M [--effort E] --reason R [--timeout D] --json` with the first usable reviewer entry from the reviewer position, with neither `--edit` nor `--no-edit` (Breaking change, RFIX-2: so a code task's review is in edit mode, the `review start` default, and a reviewer may attach a fix; the pipeline adds no switch for it); a refusal stops `review_start_refused`, except the continuations below. After `thoth wait --run RUN --json`, `thoth review show TASK --json` decides: a pending fix stops `needs_fix_confirmation`; PASS with a task at `pass` and non-null `merge_branch`/`merge_commit` stops `pass` with those exact targets in `stop.evidence`, or `merge_target_unavailable` when they are null; REJECT goes to the rework below (Breaking change, AUTO-1b: AUTO-1a stopped `reject`; that stop reason is no longer produced); a task left `unverified` (an invalid verdict) stops `review_unverified`; a reviewer run that ended without a verdict continues as below or stops `review_interrupted`; a cancelled task `task_cancelled`.

#### Continuation (AUTO-1b)

**Positions.** `implementer_index` and `reviewer_index` are zero-based positions in the two lists as given (duplicates included, so a repeated entry is its own position), start at 0 for every new pipeline and only move forward; the pipeline never wraps to the start of a list. A search starts at a position and takes the first usable entry at or after it. After a REJECT, a quota or auth stop, a second crash or a refused resume, the implementer search starts one past the current position; the unverified reroute and the timeout retry start at the current position. The reviewer position is kept across attempts.

**Preflight (before every dispatch, resume and review start).** `thoth recommend --role implementer|reviewer --task TASK --model M --json` (a `recommend` step), and with `--quota-threshold` also `thoth profile usage P --json` without `--refresh` (a `profile_usage` step); both have `run_id` null. The entry's candidate is the one whose `profile_id` is the entry's profile, never the one at the top: `eligible` false makes the entry unusable, and the skip reason copies the candidate's own `reasons` (`not eligible in recommend: R1; R2`). SMALL-9a's quota reserve is that same rule: a `reserve_blocked` candidate is not eligible, its `reasons` hold the reserve sentence, and the step result carries `reserve_blocked` and recommend's `quota_reserve_percent`; the pipeline has no second reserve rule. With a threshold, the profile's `windows` are filtered to the candidate's `quota_group` (all windows when recommend gives an explicit null, an ungrouped account), windows with `reset_since_observed` true are ignored, a codex profile's `extra_buckets` are never read, and the window with the highest `used_percent` decides: at or above N makes the entry unusable (`quota-threshold N: window NAME[ (GROUP)] is P% used, at or above N%`). A quota group that could not be read (recommend failed or listed no such candidate, or the candidate's `quota_group` is missing or not a string) is unknown, not null: no window decides, the threshold holds nothing back, and the `profile_usage` step warns that the group is unknown. Facts that cannot be read never hold an entry back: a non-zero exit or unreadable output is recorded with its own `exit_code` and `error` and `ok` false, an absent candidate, an unknown quota group, missing windows or malformed window fields are a `warning` on the step saying which facts were unknown and that execution was not held back; a readable candidate that is not ineligible but whose `quota_state` is `unknown` (or missing) is also a `warning` on the `recommend` step, with or without a threshold. Unknown usage is never counted as zero, and the launch command's own checks stay authoritative. `recommend` may refresh quota or score caches by its own switches (`live-quota`, `scores-auto-refresh`); the pipeline adds no refresh and never waits for a reset. CROSS-1's models and tables are not read and never change the supplied model.

**Implementer launches.** A refused dispatch whose error says `failed its auth check`, or SMALL-9a's `refusing to launch on profile …: quota-reserve-percent …` refusal, consumes that entry and the search goes on; dispatch's stuck refusal (its stderr JSON document has `stuck`) stops `stuck` with that error and `stuck` in `stop.evidence`; any other refusal stops `dispatch_refused`. A run that ends `interrupted` with reason `quota` or `auth` is handed over: the next usable entry is dispatched (the same attempt; dispatch writes `.agent/handoff.md` and its `handoff` names it). `crash` or `transient`: the first such recovery of an attempt preflights the current entry and, when it is usable, runs `thoth resume RUN --json` once (the same run and session; resume has no `--reason`, so the `resume` step records `reason`: the commander's reason and the cause); an unusable entry, a refused resume (SMALL-9a's reserve refusal included) or a second crash/transient in the attempt dispatches the next entry instead. `failed` with reason `timeout`: one dispatch in that attempt with `--timeout` twice that run's `timeout_seconds` (at most the 7-day maximum), on the current entry when usable or the next; a second timeout stops `run_failed`. Other reasons keep AUTO-1a's `run_interrupted` / `run_failed` stop; a cancelled task never restarts. Recovery never resets an attempt's reroute, crash or timeout budget. No usable entry left stops `implementers_exhausted`.

**REJECT.** `review show`'s `pending_fix` comes first and stops `needs_fix_confirmation`, even with `--fold-on-reject`. Otherwise the proposed attempt is one above the highest recorded run attempt; above `max_attempts` stops `attempts_exhausted`, whose `stop.evidence` then also has `review_id`, `unmet` (the REJECT's unmet criterion ids) and `brief`. At low or normal risk the next implementer entry is dispatched and dispatch folds the findings as it always does. At important or high risk: with `--fold-on-reject`, three latest consecutive REJECT reviews sharing an unmet criterion stop `repeated_reject` (`stop.evidence`: `criterion`, `review_ids` oldest first), whatever spec updates came between (a PASS or UNVERIFIED review ends the run of REJECTs). When the spec has changed after that REJECT (`task update-spec`, or an author's APPROVE through `spec review confirm`), the rework is dispatched and dispatch recognises the rewrite. When it has not: without `--fold-on-reject` the pipeline stops `spec_rewrite_needed` (`stop.next` names `thoth task update-spec TASK -f FILE --json`; start the pipeline again afterwards, and from `reject` it searches from the first entry); with it, the lines ordinary rework gives the worker (each unmet criterion `ID: NOTE (evidence CODES)`, each extra finding `SEVERITY: NOTE (evidence CODES)`, advisory ones after the required ones) are appended unchanged to `constraints` after one marker line `REJECT REVIEW_ID (attempt A), folded as-is by pipeline PIPELINE_ID:`, every other field kept, the result written to the pipeline file `step-NNN.spec.json` (masked) and handed to `thoth task update-spec TASK -f FILE --json` (an `update_spec` step, `run_id` null); the rework dispatch then reports `rework` true and `folded_findings` 0. A refused update (spec lint's limits, 40,960 bytes absolute and 20,480 for low or normal, or the secret refusal) stops `spec_rewrite_needed` with its `error`; nothing is replaced and nothing is appended twice. `--allow-attempt A` is added only when the proposed attempt is above the task's `attempt_cap` and not above `max_attempts`.

**Reviewer launches.** Before each review start the search skips an entry whose model equals the candidate implementer run's `model` and whose effort equals that run's `effort_requested` or `effort` in `thoth status TASK --json` (no effort on both sides matches), compared against the actual candidate every time; then the preflight. An auth or reserve refusal moves on; any other refusal stops `review_start_refused`. A reviewer run that ends `interrupted` with `quota` or `auth` moves to the next entry; `crash` or `transient` retries that entry once, and `failed` with `timeout` retries it once at twice that review run's `timeout_seconds` (at most 7 days), each retry preflighted again; a second one moves on. Other endings stop `review_interrupted`, an invalid verdict `review_unverified`, a pending fix `needs_fix_confirmation`. No usable entry left stops `reviewers_exhausted` at once (no reset is waited for). Thoth does not decide which provider or model is a middle tier: the commander puts other-provider middle entries first and claude-a / claude-c stand-ins after them (decision 2026-10-27).

**Exhaustion stops.** `implementers_exhausted` and `reviewers_exhausted` have `stop.evidence.entries`, one item per entry tried, skipped, refused or stopped in this pipeline (`entry_index` one-based, `profile`, `model`, `effort`, `outcome`, `run_id`), and `start_entry`; `summary` lists them. When the search followed an event, the stop also keeps what the stop that event used to produce said, next to that history (the same in `pipeline show` and the `pipeline_stopped` event): after a REJECT, `summary` leads with the review brief and `stop.evidence` has `reviewer_run_id`, `review_id`, `verdict`, `brief` and `unmet`, and `stop.next` names `thoth review show TASK --json`; after an implementer run stopped (quota, auth, crash, transient, timeout), `stop.evidence` has `run_id`, `interrupted_reason`, `error_text` and `next_step`, `summary` names the run and its reason (after the run's brief when it has one), and `stop.next` starts with the run's own `next_step`; after an unverified delivery, `run_id`; after a reviewer run stopped, `reviewer_run_id`, `status`, `interrupted_reason` and `error_text`.

### `thoth pipeline new -f SPEC.json [--title TITLE] [--base REF] [--implementer PROFILE:MODEL[:EFFORT]]... [--reviewer PROFILE:MODEL[:EFFORT]]... --reason TEXT [--max-attempts N] [--timeout D] [--review-timeout D] [--verify-timeout D] [--verify-wait D] [--quota-threshold N] [--fold-on-reject] [--wait D] [--json]`

New (ONE-1). The light path in one command: creates a code task from a spec file and starts its pipeline, then returns at once with the task id and pipeline id. `thoth task create` and `thoth pipeline start` are unchanged and remain the way for an existing task and for the heavy path.

Flags. From `task create`, with the same meaning and validation: `-f/--file` (required), `--title` (left out, the first line of the goal), `--base REF`. From `pipeline start`, with the same meaning, defaults and validation: `--implementer` and `--reviewer` (repeatable, order and duplicates kept; a list left out is the stored default of `thoth pipeline defaults set`, at low or normal risk only), `--reason` (required even when `require-reason` is off), `--max-attempts`, `--timeout`, `--review-timeout`, `--verify-timeout`, `--verify-wait`, `--quota-threshold`, `--fold-on-reject`. There is no TASK argument and no `--skip-spec-review`. `--wait D` takes the duration rule of `pipeline show --wait`.

Refusals (exit `1`, `{"ok": false, "error": …}` on stderr with `--json`), every one before anything is created: no task, no `task_created`, no `pipeline_started`, no worktree or branch cleanup event. When several apply, the first in this order is reported:
1. THOTH_RUN_ID set (the error names `pipeline new`).
2. `pipeline start`'s argument checks in its order: a missing or blank `--reason`, an invalid `--timeout`, `--review-timeout`, `--verify-timeout`, `--verify-wait`, `--max-attempts`, `--quota-threshold`; then an invalid `--wait`.
3. A list flag left out with no list of that kind stored, or with a defaults file that cannot be read or parsed (the texts of `pipeline start`).
4. The repository not initialised.
5. `task create`'s checks in its order: a spec file that cannot be read or does not parse (including a bad `risk`, `task_type`, `difficulty` or `checks`), a spec or title that holds what looks like a secret, any spec lint error (`spec lint: …`), a `--base` that resolves to no commit.
6. A spec whose `task_type` is `docs`, `research` or `review`: the pipeline runs code tasks only; such a task is created with `thoth task create` and taken with `thoth task accept`.
7. LIGHT-1's risk rule: at `important` or `high` risk a list flag left out (the error names the spec file, its risk, the missing flag or flags, and that a stored default is used only at low or normal risk).
8. An invalid entry in a flag list (`invalid --implementer entry K of L ('ENTRY'): WHY`, or `--reviewer`) or a stored entry that no longer passes (`invalid stored default --implementer entry K of L …`).
9. The spec review gate, below.

Each message is the one the original command gives for the same input, except that it names the spec file where the original names a task id.

**Spec review gate.** At `important` or `high` risk with both list flags given, the command refuses before creating anything: a new task has no APPROVE spec review, so the pipeline's first dispatch would be refused (`dispatch_refused`). It does not skip the gate, pass `--skip-spec-review` or run a spec review. The error names the spec's risk, says nothing was created and why, and lists the heavy-path commands in order: `thoth task create -f FILE [--title "TITLE"] [--base REF] --json` (as given); `thoth spec review start TASK --edit --profile PROFILE --model MODEL --effort LEVEL --reason TEXT --json` with a reviewer of another provider than the spec's author; `thoth wait --run RUN --json`; `thoth spec review confirm TASK --profile PROFILE --model MODEL --effort LEVEL --reason TEXT --json` by the spec's author when `thoth spec review show TASK --json` has `pending_edits` true; once `approved` is true, `thoth pipeline start TASK` with the list entries and the other `pipeline start` flags exactly as given; and, when `--wait D` was given, `thoth pipeline show TASK --wait D --json`. TASK, RUN, PROFILE, MODEL, LEVEL and TEXT are placeholders.

**Creation and start.** When every check passes, the task is created exactly as `thoth task create` with the same file, title and base would (the same task row, `task_created` event, finished-task worktree and branch cleanup and `warnings`), then the pipeline is started on it exactly as `thoth pipeline start TASK` with the passed-through flags would (the same `settings`, `pipeline_started` event and background process). Two failures can still come after the creation, and neither leaves a task without a pipeline:
- `pipeline start` refuses anyway (its inputs changed in between, for example the defaults file or a profile): the new task is closed as `thoth task close TASK --reason TEXT` would (status `cancelled`, one `task_closed` event whose reason says `thoth pipeline new` closed it because the pipeline start was refused, with that error); exit `1` with an error naming the task, saying it was closed and quoting the start error. If the close itself fails, the error says the task is still `queued` without a pipeline and quotes both errors.
- The pipeline was recorded but its start did not complete (the background process cannot be started, which settles it as stopped with reason `spawn_failed` as under `pipeline start`; or, for example, its folder cannot be created): the task stays `queued` with that pipeline; exit `1` with an error naming the task id and pipeline id and saying to run `thoth pipeline start TASK ...` again (with the flags as given).

**Output.** `--json` stdout is one document with exactly the keys `ok` (true), `task_id`, `pipeline_id`, `task_create` (the whole `task create --json` document for this task), `pipeline_start` (the whole `pipeline start --json` document), `warnings` (every entry of `task_create.warnings`, then every entry of `pipeline_start.warnings`; `[]` when both are empty) and `pipeline_show` (null without `--wait`). `task_id` equals `task_create.task_id` and `pipeline_start.task_id`; `pipeline_id` equals `pipeline_start.pipeline_id`. Without `--json`: one `warning: …` line on stderr per warning, and on stdout the human line of `task create`, then the human line of `pipeline start`. Documents and errors are masked like every output (Secret masking, under Conventions).

**`--wait D`.** After starting, the command waits as `thoth pipeline show TASK --wait D --json` does: `pipeline_show` is that command's document (`status`, `stop` with `reason`, `summary`, `next`, `evidence`, and the rest). Exit `0` once the pipeline has stopped, whatever its stop reason (read `pipeline_show.stop.reason`), and `3` when it is still running at D (`pipeline_show.status` `running`, `stop` null). Without `--json` the human output of `pipeline show` follows the two lines. The wait never stops the pipeline; `thoth pipeline show TASK` continues from there.

Exit codes: `0` started (with `--wait`, stopped), `1` any refusal or failure above, `3` still running at the end of `--wait`.

**Events.** The command adds no event type of its own: `task_created`, then the `pipeline_started` whose detail's `pipeline_id` and `settings` are those returned, then the pipeline's own events (`run_started`, `verify_ran`, `review_started`, `verdict`, `pipeline_stopped`, with pipeline steps, launch choices and evidence between them). There is no `spec_review` or `spec_review_skipped` event.

MCP: `thoth_pipeline_new` runs this command with `--json` and returns its document at once (no wait parameter); see `docs/mcp.md`.

### `thoth pipeline show TASK [--wait D] [--json]`

New (AUTO-1a). The task's newest pipeline. Exit `1` when the task has none. With `--wait D` it waits for the pipeline to stop: exit `0` once it has, `3` with the same document when it is still running at D. `--json` keys: `ok`, `pipeline_id`, `task_id`, `task_status`, `status` (`running` | `stopped`), `step` (the phase it is in, or stopped in: `starting`, `dispatch`, `wait_run`, `protected`, `verify_wait`, `verify`, `review_start`, `wait_review`, and (additive, AUTO-1b) `resume` and `update_spec`), `stale`, `stop_requested`, `settings`, `implementer_index` and `reviewer_index` (Breaking change, AUTO-1b: no longer always `0`; the zero-based list positions described under "Continuation (AUTO-1b)"), (additive, AUTO-1b) `attempts_used` (the highest attempt of any run of the task, 0 without one; not a count of launches or resumes), `pipeline_pid`, `heartbeat_at`, `started_at`, `ended_at`, `dir`, `steps`, `stop`.

- `heartbeat_at` starts equal to `started_at` and advances at least every 5 seconds while the pipeline waits for a run, a slot or a child. `stale` is true for a running pipeline whose heartbeat is more than 15 seconds old (as `status` judges runs) and whose `pipeline_pid` is not a live thoth process (a pid now used by another program counts as gone). A live thoth process with an old heartbeat is not stale.
- `dir` is the absolute path of `THOTH_HOME/repos/REPO/pipelines/ID/`: `pipeline.log` (one line per step and error, masked) and `step-NNN.stdout.json` / `step-NNN.stderr.txt` for each recorded command's output (masked).
- `steps[]`: `index` (from 1), `kind` (`dispatch`, `verify`, `review_start`), `run_id` (null without a run), `exit_code`, `ok` (a successful exit and a JSON document on stdout), `duration_ms`, `error` (null when ok: stderr's JSON `error`, else its first non-empty line), `waited_for_slot_ms` (verify only, else null), `result` (dispatch: `attempt`, `rework`, `folded_findings`, `handoff`; review start: `target_run_id`, `attempt`, and (new, RFIX-2) `mode` (that `review start --json`'s `mode`: Breaking change (RFIX-2), `edit` for a code task, since the pipeline passes neither `--edit` nor `--no-edit`); verify: `ok`, `failures`, `missing_since_last_verify`; null when stdout could not be read). Select steps by `kind`: later versions add kinds. Additive (AUTO-1b): kinds `recommend`, `profile_usage`, `resume` and `update_spec`; results: `recommend` `{role, entry, profile_id, eligible, reasons, quota_state, quota_group, peak_percent, reserve_blocked, quota_reserve_percent}` (the entry's candidate as `recommend` gave it, null fields when it could not be read); `profile_usage` `{role, entry, profile_id, eligible, reasons (both copied from the recommend step), quota_state, quota_group (the group the windows were filtered by), quota_group_known (false when recommend's quota_group could not be read; then `quota_group` and `window` are null and nothing is held back), peak_percent, threshold, window ({name, used_percent, group} of the deciding window, or null), held_back (bool, null when unknown)}`; `resume` `{run_id, warnings}`; `update_spec` `{spec_sha256 (from the `spec_updated` event's detail, null when the update failed), review_id, folded_lines, marker, file}`. Every step also has `entry_index` (the one-based list position for `dispatch`, `review_start` and `resume`, else null), `skipped` (`[{profile, reason}]`, the entries this search passed over before the launch, `[]` when none), `attempt` (the task attempt the step belongs to), `reason` (the `resume` step's recorded reason, else null) and `warning` (a preflight's unknown facts, else null). Older steps read back with `skipped` `[]` and the other four null. Do not count steps: preflight steps make totals vary.
- `stop`: null while running, else `{"reason","summary","next","evidence"}`. `summary` leads with the review brief (or the run's brief for a worker stop); full findings and evidence stay in `review show`, `evidence list` and `events`. `next` is a list of commands. Stop reasons: `pass`, `merge_target_unavailable`, `review_unverified`, `review_interrupted`, `review_start_refused`, `needs_fix_confirmation`, `needs_approval`, `protected_unreadable`, `verify_blocked`, `verify_failed`, `verify_wait_timeout`, `dispatch_refused`, `run_interrupted`, `run_failed`, `runner_lost`, `unverified_twice`, `task_cancelled`, `attempts_exhausted`, `stopped`, `stale`, `spawn_failed`, `error`, and (additive, AUTO-1b) `implementers_exhausted`, `reviewers_exhausted`, `repeated_reject`, `spec_rewrite_needed`, `stuck`. AUTO-1a's `reject` is no longer produced (a REJECT is reworked).

### `thoth pipeline defaults set|show|clear`

New (LIGHT-1). The commander's default implementer list and default reviewer list on this machine, used by `thoth pipeline start` for a list flag that is left out on a low or normal risk task (see there). The commander stores and changes them, not the human, and they are not a `thoth config` setting (`thoth config list` has no key for them). They live in the user-visible file `THOTH_HOME/pipeline-defaults.json`, one per machine and shared by every repository of that THOTH_HOME (profiles differ between machines). The three subcommands need no initialised repository and work from any directory. The file is written whole through a temporary file in the same folder and a rename, so a reader never sees half of it. Its shape: `{"implementers": LIST, "reviewers": LIST}`, each LIST null or `{"entries": [{"profile","model","effort"}], "reason", "set_at"}`. A stored list whose `entries` is empty counts as a file that cannot be parsed (in `show`, at `pipeline start` and for `clear`).

`thoth pipeline defaults set [--implementer PROFILE:MODEL[:EFFORT]]... [--reviewer PROFILE:MODEL[:EFFORT]]... --reason TEXT [--json]`: a list whose flag is given replaces that stored list whole, in the order given with duplicates kept; a list whose flag is left out stays as stored. Each list this call replaces gets the trimmed `--reason` (masked like a pipeline's `settings.reason`) and `set_at` (RFC 3339). `--json` keys: `ok`, `path` (absolute), `implementers`, `reviewers` (each null or `{"entries": [{"profile","model","effort"}], "reason", "set_at"}`, `effort` null when left out) and `replaced` (the names `implementers` and/or `reviewers` this call replaced). Refusals (exit `1`, `{"ok": false, "error"}` on stderr with `--json`, nothing written): THOTH_RUN_ID set (the error names it); neither `--implementer` nor `--reviewer` (the error names both); a missing or blank `--reason`; an invalid entry in either list, checked by the same rules and with the same error text as `pipeline start`'s flag entries (`invalid --implementer entry K of L ('ENTRY'): WHY`, or `--reviewer`); a stored file that cannot be read or parsed (the error names its path; `clear` repairs it).

`thoth pipeline defaults show [--json]`: read-only; it creates no file or folder (not even a profile database). `--json` keys: `ok`, `path`, `exists`, `implementers` and `reviewers` (as under `set`), each non-null list with one more key `invalid`: `[{"entry_index" (one-based), "entry" (PROFILE:MODEL[:EFFORT]), "error"}]` for every stored entry that fails the entry check on this machine now (`error` is why, as after `('ENTRY'): ` in the refusal), `[]` when all pass. Without a profile database every entry is listed (no such profile). A missing file is `exists` false and both lists null, exit `0`. A file that cannot be read or parsed exits `1` with an error naming the path. The human output prints each list's entries in stored order, its reason and set_at, and an `INVALID entry K (ENTRY): WHY` line for each invalid entry.

`thoth pipeline defaults clear [--only implementer|reviewer] [--json]`: removes the stored implementer list, reviewer list, or (without `--only`) both. `--json` keys: `ok`, `path`, `cleared` (the names removed; a list that was not stored is absent and the call still succeeds), `previous` (always `{"implementers","reviewers"}`, each that list as stored before in the `set` shape, null when it was not stored or the file could not be read), `implementers` and `reviewers` after the call, and `warning` (null, or a string). Refused (exit `1`) while THOTH_RUN_ID is set. On a file that cannot be read or parsed, `clear` without `--only` replaces it with one that holds no list (a later `show` returns `exists` true and both lists null) and `warning` names the parse error; `clear --only` is refused naming the path. With no file, nothing is written.

No MCP tool stores, shows or clears the defaults; `thoth_pipeline_start` uses them (see `docs/mcp.md`).

### `thoth pipeline stop TASK [--json]`

New (AUTO-1a). Refused (exit `1`) with THOTH_RUN_ID set or when the task has no running pipeline. Otherwise returns `ok`, `pipeline_id`, `status` and records `pipeline_stop_requested` (detail `pipeline_id`). The pipeline launches nothing more, lets a `dispatch` or `review start` already starting return, ends only an active verify and its descendants, frees its verify slot and settles with reason `stopped`. **No worker is cancelled**: a run it started keeps going (`thoth cancel RUN` ends one, and cancellation is final for the task). A stale pipeline is settled at once as `stopped` with reason `stale` (`status` `stopped`, no `pipeline_stop_requested`).

Restart after a stop, a stale pipeline or a stop that needs your judgement: `thoth pipeline start TASK ...` again. From `in_review` it attaches to a live implementer or reviewer run, or continues the candidate from the protected gate, without dispatching again; (AUTO-1b) from `reject`, `unverified`, `interrupted` or `failed` it continues as described under the entry states, searching both lists from their first entry.

### Pipeline ownership (additive refusal, AUTO-1a)

While a task has a live, non-stale pipeline, `dispatch`, `review start`, `review confirm`, `review record`, `resume`, `task update-spec`, `task close`, `spec review confirm` and `submit` for that task are refused before they change anything (exit `1`), with the pipeline id, its step and `thoth pipeline stop TASK`. Only the pipeline's own children (matching `THOTH_PIPELINE_ID` and no THOTH_RUN_ID) pass; a worker that inherited the id is refused. `cancel`, `checks approve`, `verify` and the read-only commands stay available; the other spec review commands keep their own rules. The MCP tools pass the refusal on as a tool error. A stale or stopped pipeline owns nothing.

### Verify slots (AUTO-1a)

A pipeline's verify holds one of `verify-slots` (setting, default `1`, 1 to 8) slots shared by every repository of this computer: `THOTH_HOME/verify-slots/slot-K.json`, K from 1 to the limit, holding `pid`, `pipeline_id`, `task_id`, `run_id`, `acquired_at`. A file whose pid is gone or now runs another program, or that cannot be read, is taken over; a live thoth owner is never. A pipeline acquires only while fewer files than the limit are live, so lowering the limit applies to new acquisitions and deletes no live file. Every normal, error and stop exit removes its own file. A manually started `thoth verify` takes no slot: on the main machine keep the default `1` and do not start a manual full suite or a worker's heavy tests while a pipeline verifies.
