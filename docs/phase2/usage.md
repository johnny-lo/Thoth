# thoth (Phase 2) — the evidence flow

Phase 1 dispatched a task to a worker and recorded whether it finished. Phase 2
adds the part that makes the answer worth anything:

```
Task → Worker → Evidence → Reviewer → Decision
```

*(2026-09-30: this tool was renamed from agentctl to thoth.)*

Read `docs/phase1/usage.md` first: everything there still applies. This document
covers what is new.

MCP entry: `thoth mcp` exposes these commands as tools while preserving their
JSON contract; see [the MCP guide](../mcp.md). `thoth guide` prints the
commander guide.

## What changed underneath

- **Every shell command a worker runs is captured**, out of band, by a Claude
  Code hook. The worker's workflow is untouched; it does not opt in and cannot
  opt out.
- **Claims and evidence are separate rows.** The worker's prose is a `claim`; the
  bytes are `evidence`; `claim_evidence` links them. A claim with no evidence
  behind it is not a finding, it is an assertion.
- **The evidence index is generated by the control plane**, written into the
  worktree as `.agent/evidence-index.json`. The worker reads it to cite codes and
  never edits it. When it creates a worktree, thoth adds `.agent/` to the
  repository's `.git/info/exclude`, so these files never show as untracked.
- **`state.db` is at schema version 2**: `tasks.attempt_cap`, `runs.harness_bin`,
  and unique `(task_id, code)` on `evidence`. A Phase 1 database migrates in
  place the first time any command opens it.
- **Blobs** live in `%THOTH_HOME%\repos\<repo_id>\blobs\<sha256>`
  (`$THOTH_HOME/repos/<repo_id>/blobs/<sha256>` on Linux; paths in this
  guide are written the Windows way, and Linux has the same layout with `/`),
  content-addressed and append-only. Phase 2 never deletes one.

New directories inside a run, for an **implementer (worker)** run only — a
reviewer run gets neither `hooks-settings.json` nor `inbox\`, because a
reviewer is never hooked (see "The reviewer" below):

```
repos\<repo_id>\runs\<run_id>\
  hooks-settings.json     what `claude --settings` was handed
  inbox\hooks.jsonl       one line per hook event, appended by `thoth hook`
  inbox\blobs\<sha256>    tool output copied at the moment the hook fired
  inbox\hook-errors.log   only exists if the hook had something to report
  inbox\.offset           the tailer's persisted byte offset (survives a resume)
```

## The loop, end to end

```
thoth task create -f spec.json --title "uploader retry"
thoth dispatch 01J... --profile claude-b --model sonnet
thoth wait 01J... --timeout 30m           # returns on in_review
thoth evidence list 01J...
thoth review start 01J... --profile claude-a --model opus --json
thoth wait --run 01K... --timeout 30m     # the reviewer run id from that --json
thoth review show 01J...
```

`thoth wait <task>` still returns on `in_review`, `unverified`, `failed`,
`cancelled` and `interrupted` — **not** on `pass` or `reject`. So it cannot wait
for a verdict: a task under review sits at `in_review`, which `wait` already
returns on immediately.

`thoth wait --run <run_id>` is the verdict handle. It blocks until that *run*
reaches a terminal status (`completed`, `failed`, `cancelled`, `interrupted`) and
prints the run's status plus, for a reviewer run, its verdict; for a spec
reviewer run, its spec review verdict (APPROVE or REVISE):

```
thoth wait --run 01K... --timeout 30m [--json]
```

Exit codes are the same as the task form: `0` terminal, `3` timeout, `1`
anything else. The `--json` document carries `status`, `role`, `verdict`,
`task_status` and `timed_out` (also `run_id`, `task_id`, `interrupted_reason`
(`quota`, `crash`, `user`, `timeout`, `auth`, `transient`, or null) and
`exit_code`) — the same key set on both paths, with `interrupted_reason`,
`exit_code`, `verdict` and `task_status` all `null` on a timeout, because a
run that has not finished has no answer for any of them yet. Additive
(AGY-1): both paths also carry `tools_unknown`, the `tools_unknown` of that
run's newest `run_usage` event (an antigravity run's agy tool names its tool
lock denied that Thoth does not know; see "Antigravity workers"), `[]` when
the run has no usage yet, when its usage has no such key (a Claude or codex
run), or when the key is not an array of strings; only the run's own newest
usage counts. When it is not empty the human output adds a second line, `agy
called tools Thoth does not know: NAME, NAME; its tool names may have
changed (AGY-1)`. A task id and
`--run` are mutually exclusive, and exactly one is required. `review start
--json` returns the reviewer `run_id` precisely so the two can be chained.

Both forms lead with a short conclusion (BRIEF-1). `wait <task> --json` adds
`run_id` (the task's last implementer run, by run id), `result_status`,
`claim_count`, `brief`, `brief_source` and `brief_truncated` from that run's
own newest delivery, all null when it has none (an earlier run's result never
stands in) and on a timeout. `wait --run <run_id> --json` adds `brief`,
`brief_source`, `brief_truncated`, `result_status` and `claim_count` on both
paths: an implementer run's delivery (`brief_source` `worker` or `summary`);
a reviewer run's own verdict (`review`, for example `REJECT: 1/2 criteria
met; AC2 unmet (fix S, spec_mismatch): the retry never fires; 1 extra
finding(s); major (fix S, test_interface): the new test asserts a constant`);
a spec reviewer run's own spec review (`spec_review`, for example `REVISE: 1/2
criteria need revision; AC1 (exists, src/lib.rs:1): ...; 3 edit(s) proposed`,
or `REVISE: 1 of 3 edits revise` for an author's check). A reviewer's
`result_status` and `claim_count` are null, and a run that reached no delivery
or judgement (or a research source check) has a null brief. A brief is at most
1,000 characters and each note or location in it at most 200, counted in
characters; everything is masked before it is cut. The human output prints
`brief: ...` under the first line and, when it was cut, where the full text
is (`thoth task result <task> [--run <run>]`, `thoth review show <task>` or
`thoth spec review show <task>`). The full rules are under "Briefs" in
`docs/adapter-usage.md`.

`thoth events --since <seq>` (watch for the `verdict` event) and
`thoth review show <task> --json` remain the polling alternatives.

## Evidence

```
thoth evidence list <task> [--json]
thoth evidence show <code> [--task <id>] [--bytes N] [--json]
```

`evidence list` is the index: one line per record with its code, kind,
`collected_by`, exit code and label. With `--json` each row also carries
(TESTS-1) `detail`, the stored detail parsed the way `show` parses it (null
when it is not JSON), and `blob_path` (string or null), so a test or a script
can read them without `show`; `list` writes no event, with or without
`--json`. `evidence show` prints the record plus the
first 4000 bytes of its stored blob; `--bytes N` raises that. It also re-verifies
the blob's digest while reading it and reports `blob_verified`.

Kinds Phase 2 produces, all `collected_by = control_plane`:

| kind | where it comes from | blob |
|---|---|---|
| `command` | a worker's Bash call, captured by the hook | the command's stdout (complete, even when the inline payload was truncated; `detail.truncated_inline: true` when the payload was cut, including when Claude Code itself shortened the output and left one of its truncation markers such as `... [N characters truncated] ...`, `... [N lines truncated] ...` or `[output truncated]`, in which case the cut part is not recoverable). For a command that failed, Claude Code sends no stdout: the blob is the text of its `error` after the `Exit code N` line (the command's output as Claude Code reported it, compiler stderr and test-harness stdout together), so `evidence show` prints that as `content`; `detail.error` still holds the full `error` text |
| `command` with a `verify: ` label | `thoth verify` re-running a declared command | the same |
| `diff` | `git diff <base>..<candidate>` when the run ends cleanly | the full patch, test files included |
| `commit` | the candidate commit | `git show --stat` |

`commit` evidence's `detail` carries exactly three keys — `sha`, `subject`,
`author_date` — the `git show --stat` text lives in the blob, not in `detail`.
`diff` evidence's `detail` carries `from_commit`, `to_commit`, `files_changed`,
`touches_tests`, `protected_changes`, `inline_test_errors` (LEAN-1), `stat`,
`protected_base` and `integration_tip`; `touches_tests` is a filename
heuristic (paths under a `tests/`, `test/`, `__tests__/` or `*.Tests/`
directory, `conftest.py`, `test_*`, `*_test.{rs,py,go,ts}`,
`*.test.{ts,tsx,js}`, `*.spec.{ts,tsx,js}`, `*Tests.cs`, `*Test.cs`; case is
ignored) that flags a diff for a reviewer's attention — the point is that
"the tests moved" is exactly the fact a reviewer must not miss.

`protected_changes` is the list the control plane works out from
`git diff --name-status --no-renames <task base_commit>..<candidate>`, keeping
only the paths whose content at the candidate also differs from the main
worktree's HEAD (the integration tip; `integration_tip` in the detail, null
when it was not used), sorted by path, `[]` when there is none:

```json
[{"path": "tests/x.rs", "status": "modified", "kind": "test"}]
```

- `status` is `modified`, `deleted` or `type_changed`. An **added** file is
  not listed, with the one exception below. Renames are not detected: a moved
  file is a `deleted` old path (plus an added new one).
- `kind` is `check_input` (the path is an input of any check in the catalogue,
  approved or not), `test` (the heuristic above, or one of the repo's extra
  patterns — see "Protected files"), `check_word`, or `inline_test` (below).
  When a path is more than one, `check_input` wins, then `test`, then
  `check_word`; `inline_test` is only looked for in a `.rs` file that is none
  of the three.
- `check_word`: the file's name, up to its first `.`, equals a word of a
  check's command taken the same way (`cargo test` gives `cargo` and `test`;
  `python scripts/check_tests_no_db.py` gives `python` and `check_tests_no_db`;
  words starting with `-` are skipped; case is ignored). A modified, deleted or
  type-changed file that is neither a test nor a check input is listed with
  this kind. This is also the only way an added file is listed: an added file
  named like a check word (`cargo.bat`, `tools/Cargo.cmd`, `docs/python.md`)
  is listed with status `added` and kind `check_word`, so a file that could be
  picked up in place of a check's program is put in front of the reviewer.
- `inline_test` (LEAN-1): an existing `.rs` file (modified, deleted or
  type-changed) whose inline test region changed. The region starts at the
  first line that, trimmed, starts with `#[` and whose attribute — the text up
  to its first `]` — is named `test` or ends in `::test` (`#[test]`,
  `#[tokio::test]`), or is a `cfg` attribute with the whole word `test`
  (`#[cfg(test)]`, `#[cfg(all(test, windows))]`) whose next text that is not
  blank, an attribute or a comment declares a `mod`; it runs to the end of the
  file. `#[latest]`, `#[attest]`, a trailing `// test` comment and
  `#[cfg(test)]` on a function do not start one. The file is read at the
  task's base and at the candidate (CRLF read as LF, bytes that are not UTF-8
  as replacement characters), and the region counts as changed when its base
  lines do not all appear, whole and in order, among the candidate's lines —
  a changed or deleted test line, tests put in another order, the region or
  the file deleted. Inserted lines alone do not count: an edit of the
  production code above the region, tests added to an existing region, a first
  region added to a file that had none, and a new source file are not listed.
  Only Rust, and only this syntax.
- `inline_test_errors` (LEAN-1) is `[{"path", "error"}]`, normally `[]`: a
  `.rs` file that could not be read at the base or at the candidate (for
  example it became a gitlink) is listed as `inline_test` anyway, never left
  out, and the reason is here.
- What counts as the task's own: a file the task itself added in an earlier
  attempt is `added`, not `modified`, since the list counts from the task's
  base, not the run's. A change that arrived through `git merge` of the main
  branch and still equals it is dropped (fast-forward or merge commit alike).
  The tip is not used, and nothing is dropped, when it cannot be read, equals
  the candidate, already contains the candidate, or does not contain the
  task's base commit (a task started on a long-lived branch that the main
  worktree's HEAD has not merged: a file put back to main's content is still
  the task's change). A diff recorded without an
  attribution (`review start` after `thoth submit`) uses the run's base and no
  tip; `protected_base` says which base was used. `files_changed`,
  `touches_tests`, `stat` and the patch still run from the run's own base to
  the candidate.
- A rework compares against the task's base, so changes an earlier attempt
  made to an existing test or check input are listed again.

The worker does not have to declare any of it (LEAN-1; ingest rule 6, which
refused a delivery that did not, is retired). The review packet, the
reviewer's prompt, `checks approve --run` and the review gate read this key.

`--task` is optional when the code is unique across the repository's tasks, and
also when `THOTH_RUN_ID` is set — which it is inside a worker or reviewer, so
a reviewer just runs `thoth evidence show E004`.

**Every open is recorded** as an `evidence_opened` event, with the reading run's
id when there is one. That is what lets `thoth review show` tell you whether
the reviewer actually read what it cited.

### Why a task goes to `unverified`

Six conditions (rule 6 is retired), checked before anything is written, so a
rejected document leaves the previous claims untouched:

| | condition | event detail |
|---|---|---|
| rule 1 | `result.json` fails schema validation | `result_invalid`, `rule: 1` |
| rule 2 | a `test_result` or `doc_reference` claim cites nothing | `rule: 2` with the claim's index, kind and text |
| rule 3 | a cited code is not evidence of this task | `rule: 3` with the claim's index and the code |
| rule 4 | a cited evidence's blob is missing, or no longer hashes to its recorded sha256 | `rule: 4` with the claim's index, the code, the blob path and the sha256 |
| rule 5 | the task is `risk: high` and a claim cites no `control_plane` evidence | `rule: 5` with the claim's index, kind, cited codes and the risk |
| rule 6 | retired (LEAN-1): it refused a protected change (`detail.protected_changes`) that no `protected_change` claim declared. No new event has it; an older one keeps its `path`, `status` and `kind` | — |
| rule 7 | the task's `task_type` is `research`, `status` is `completed`, and no claim is of kind `research` | `rule: 7` |
| rule 0 | not a rule at all: the document was fine and the *database write* failed (a busy transaction, a failed insert, a failed commit) | `rule: 0`, with `claim_kind`/`claim_id`/`code` when the failure happened on a particular row |

`rule: 0` is the one entry in that table that is not the worker's fault. The
document is not the problem, so re-`submit` the same file once the database is
free rather than rewriting it.

There is no `claim_id` in a `result_invalid` event's detail (nothing has been
written yet at that point — rejection happens before any claim or link is
inserted) — use `claim_index` (0-based) to identify which claim of the
document failed.

`completion` and `behavior` claims are exempt from rule 2: they are summaries of
the worker's own judgement, which is what a claim is for. Rule 5 applies to
every claim on a high-risk task except a `research` claim (below), including
one that cites nothing at all. A
task whose risk cannot be read (its row is missing, or the read fails) is
treated as `high` for rule 5 — fail closed — and that degradation is logged to
`runner-error.log`.

**Research claims (rule 1 and rule 7).** The claim kinds are `test_result`,
`doc_reference`, `completion`, `behavior`, `protected_change` and `research`.
A `research` claim is one factual claim of a research task's report, with the
pages it comes from:

```json
{"kind": "research", "text": "Uploads retry three times", "evidence": [],
 "sources": [{"url": "https://example.org/uploader", "quote": "The uploader retries three times."}]}
```

Rule 1 rejects a `research` claim whose `sources` is empty or missing, a source
whose `url` does not start with `http://`, `https://` or `file://` (any case)
or contains whitespace, a source whose `quote` is blank, and any other kind
that carries a non-empty `sources`; the reason names the claim number and the
field. Rule 7 rejects a research task's `completed` result.json that has no
`research` claim at all (a `blocked` one is not checked). Rule 2 does not apply
to `research` (a fetched page never becomes evidence), and neither does rule 5:
a research claim is checked by opening its sources again, not by a command's
evidence. The worker of a research task is told all this in a `## Research
claims` section of its prompt, before the result.json shape.

**Protected changes need no declaration (LEAN-1).** Rule 6 used to make the
worker say, file by file, that it changed something a check depends on, and
refused the delivery when one file was missing. It is retired: the list is
the diff evidence's `protected_changes`, worked out by Thoth, and a delivery
is never refused or rerouted for leaving a file out. A claim of kind
`protected_change` is optional and kept as written, even when it names only
some of the files:

```json
{"kind": "protected_change", "text": "tests/x.rs: the old assertion contradicted AC2"}
```

It is exempt from rule 2 (there is nothing to cite); rule 5 applies to it as
to any claim. Recording a change does not judge it: the reviewer is shown the
same list, and the commander approves each `test`, `check_word` and
`inline_test` change with `checks approve --run` before a review can start or
a PASS be recorded (see "Approval before review"). The worker is told this in
the `## Protected files` section at the end of its prompt: what Thoth records
automatically (existing test files and check inputs modified or deleted,
existing Rust files whose inline test region changed, files named like a
check word), that it does not have to declare them, and that the commander
approves them. That section lists the inputs of every check in the catalogue,
approved or not and whether or not the spec's `checks` field names it, the
check words, and the repo's extra patterns. The result.json shape it is shown
no longer has `verification_requests` (a delivery that still carries the key
is accepted; it is kept for reference only), and the prompt asks the summary
for intent, limitations and decisions, not for file lists, command logs, exit
codes or usage, which Thoth records itself. Separately,
before `## Evidence`, the worker prompt says the run is a single unattended
turn: no background commands, and checks, commit and `.agent/result.json` all
done before the turn ends.

A task in `unverified` is still re-dispatchable, and `thoth submit` still
works — fix the document and file it again.

**What the new worker is told.** A dispatch out of `unverified` reuses the same
attempt and worktree, so the previous run's commits are already there. When the
task's newest implementer run has a `result_invalid` event, dispatch copies that
event's `detail.reason` (verbatim) and `detail.rule` into the run's copy of the
spec as a `reroute` object (`previous_run`, `reason`, `rule`), next to where a
rework keeps its `rework` object; the task's own spec is not changed. The worker
prompt then gains a section, before the `result.json` contract, that says the
previous run's `result.json` was not accepted, quotes the reason, says its work
is already in the worktree so the worker should check and fix rather than start
over, and asks for `.agent/result.json` again with every `test_result` and
`doc_reference` claim citing a code from `.agent/evidence-index.json`. There is
no such section when the newest implementer run has no `result_invalid` event
(an `unverified` made by an invalid review, for example), from any other entry
status, or on a rework. A `rule: 0` rejection (a database failure) is quoted
too, since the event is the only record of why.

## The reviewer

### Source check for research tasks

For `task_type: research`, `review start` launches an independent source checker
using the usual reviewer role. The latest completed implementer run's latest
accepted result must contain a research claim; otherwise start refuses before
writing anything and points to `task result`, `task close` and `dispatch`.
The commander chooses the profile, model and effort: prefer another provider;
only when it has no quota use a stronger model or higher effort on the same
provider and explain that step in `--reason`. The existing `require-reason`
switch applies to all reviews; research has no additional same-provider gate.

Claude receives `Bash,Read,Glob,Grep,WebFetch,WebSearch`, with no Write or Edit.
Antigravity receives its normal reviewer tools plus `search_web,read_url_content`,
with no shell or writing tools. Codex keeps the recorded tool string and
`-s read-only`, adding only `-c web_search="live"` immediately after the sandbox
pair (before Windows sandbox config); it gets no `network_access` setting.
Spec reviews never receive these web additions, even for research tasks.

The prompt lists every research source as `S1`, `S2`, … in claim and source
order and asks the checker to open each URL and compare its quote with the
claim. Local `file://` pages use the harness's reading tools. The report is
`.agent/review.json` (Claude: shell redirect; codex: schema-constrained final
message; agy: `structured_output`), with this shape:

```json
{"verdict":"PASS","findings":{"sources":[{"id":"S1","url":"https://example.org/page","verdict":"supported","reason":""}],"extra_findings":[]}}
```

Each id appears exactly once with its original URL. `supported` means the
quote appears verbatim or substantially and supports the claim;
`not_supported` means the page opens but lacks or contradicts that support;
`unreachable` means it cannot be opened, times out or requires login. Both
non-supported answers need a reason. Any `not_supported` makes REJECT;
otherwise any `unreachable` makes UNVERIFIED; all supported makes PASS.
Thoth recomputes that verdict and refuses inconsistent reports. Criteria
judgements are absent (or empty): the commander judges whether the report
answers the question using `task result` and the report itself.

`review show` prints sources at the criteria table's position. `review record`
accepts this same document for a commander who checked the sources directly.
After REJECT, dispatch folds `not_supported` into rework `unmet` with the claim,
source id, URL and reason. `unreachable` becomes an extra finding before the
document's own extras, asking the worker to replace the source. PASS, REJECT
and UNVERIFIED use the usual reviews, verdict events, records and model counts.

### Starting and reading a review

The criteria-review instructions below apply to tasks other than research;
research uses the source-check prompt and document above.

```
thoth review start <task> --profile <id> --model <m> --effort <level> [--timeout 30m] [--json]
thoth review show <task> [--full] [--json]
thoth review record <task> -f review.json [--json]
```

`review start` needs the task in `in_review` with a completed implementer run
behind it, and refuses while **any** run of the task is still `queued` or
`running` (the refusal names that run, its role and its status). A refused
`review start` writes nothing and — importantly — does not touch the review
worktree's `.agent\review.json`, so it cannot delete a live reviewer's report
on its way out. It then:

1. creates `worktrees\<task_id>-a<n>-review`, a **detached** checkout of the
   candidate commit — the reviewer cannot see uncommitted work and cannot move
   any branch. If a stale `.agent\review.json` is sitting in that worktree from
   an earlier crashed review, it is deleted before the run starts (and start
   fails closed if it cannot be deleted, rather than risk ingesting it); the
   `review_started` event and `review start --json` both report
   `cleared_stale_report`. Once the task is finished, the review worktree is
   removed by the next `task create`, `task close` or `thoth worktrees prune`
   (see "Worktree cleanup");
2. launches a run with `role = reviewer` and `--allowedTools Bash,Read,Glob,Grep`
   (also passed as `--tools`, see "Worker tool lock" below) — no `Write`, no
   `Edit`, no `NotebookEdit` (a codex profile runs in codex's read-only
   sandbox instead and gets its input as files; see "Codex reviewers" under
   "Codex workers" below; an antigravity profile gets the same files, reading
   tools only and no shell; see "Antigravity reviewers" under "Antigravity
   workers" below);
3. publishes the evidence index into that worktree and hands the reviewer the
   code of the candidate diff as a must-read;
4. leaves the task in `in_review` until the verdict lands — a reviewer run
   never moves `tasks.status` except through its own verdict, so a review that
   crashes or times out leaves the task exactly where `review start` can be
   run again.

**Same-provider reviewer.** Breaking change (RJ-1): Thoth no longer raises a
same-provider reviewer's model one tier above the implementer's, and there is
no `opus` default. Give `--model` and `--effort` on the first review of an
attempt; starting the review of the same attempt again keeps the previous
reviewer run's model and effort for whatever you leave out (see "Automatic
dispatch"). Review with a profile of another provider when you can; choosing
the model is yours.

The reviewer writes `.agent/review.json`:

```json
{
  "verdict": "REJECT",
  "findings": {
    "criteria": [
      {"id": "AC1", "verdict": "met", "evidence": ["E004"]},
      {"id": "AC2", "verdict": "unmet", "evidence": ["E001"], "note": "the retry never fires", "fix_size": "S", "category": "spec_mismatch"}
    ],
    "extra_findings": [
      {"severity": "major", "note": "the new test asserts a constant", "evidence": ["E004"], "fix_size": "S", "category": "test_interface"}
    ]
  }
}
```

Criterion ids come from the spec's `acceptance_criteria`: the text before the
first `:` when it looks like an id (`"AC1: retries three times"` → `AC1`),
otherwise the 1-based position (`"prints hello"` → `AC1`).

Every unmet criterion and every extra finding may carry two labels, which
`thoth retro` counts; `fix_size` also decides whether an edit review's fix
may be bound to the finding (see "Reviewer fixes, author confirms" below):

- `fix_size`: the smallest fix that would resolve it. `S` (at most 10 changed
  lines in one file), `M` (at most about 50 changed lines, or more than one
  file, no design change), `L` (larger, or it needs a design or spec change).
- `category`: one of `spec_mismatch`, `spec_error`, `test_missing`,
  `test_interface`, `error_path`, `concurrency`, `platform`, `docs`,
  `evidence`, `files`, `security`, `other`.

Both are read case-insensitively and stored as `S`/`M`/`L` and lower-case
names; a blank value or `none` counts as absent (the codex and agy reviewers'
schema makes both required, so they send `none` on a met criterion). Both are
optional: a document without
them is accepted and stored exactly as before, and `retro` counts its findings
as `unsized` and `unclassified`. A `met` criterion needs neither. The reviewer
prompts ask for both, and also tell the reviewer that a new or changed test
which bypasses the interface (reads the database or internal state, only
compares a fixed string or the exit code, or repeats the implementation's
logic) is a `test_interface` finding. The rule after that one (TESTS-1, the
same in the Claude, codex and agy prompts) says where the whole-suite
evidence is: the implementer is told to run only the tests the spec names,
and the whole suite is the control plane's `verify`, which the index shows as
rows labelled `verify: ` with `collected_by` `control_plane`. A criterion is
not unmet or UNVERIFIED because the implementer did not run the whole suite
itself, and an implementer's cut-off or empty whole-suite output is not
missing evidence when a verify row covers the same check. Only a candidate
verify row for the same run and check that completed with usable output
counts: a `verify@base: ` row, or a failed, refused, timed-out or incomplete
verify, proves nothing; when no usable verify row exists for a check the
reviewer reports what is missing as an extra finding with category
`evidence`, without treating an existing row as success or waiving an
explicit evidence requirement.

What makes a `review.json` invalid:

- an id is missing, invented, or judged **more than once** (a document that
  answers `AC1` twice, with either answer, is rejected — its verdict would be
  decided by whichever rule read the list first);
- a criterion's verdict is anything but `met` or `unmet`;
- an `unmet` criterion cites no evidence **and** gives no note;
- a `met` criterion cites no evidence. The absence of something can be
  described; its presence has to be pointed at. This is the reviewer prompt's
  own rule ("cite at least one evidence code for each judgement"), and it is
  what stops an all-`met`, zero-citation `PASS` from settling a task `pass`
  from a reviewer that opened nothing;
- a cited code is not evidence of this task;
- the document says `PASS` while any criterion is `unmet` — a verdict cannot
  contradict its own findings;
- a `fix_size` other than S, M or L, or a `category` not in the list above,
  on any criterion or extra finding (the schema stage; the reason names the
  criterion id or `extra_findings[i]`, counted from 0).

If any of that fails, the task lands `unverified` with a `review_invalid`
event naming the stage — never `pass`.

Verdicts map to task statuses directly: `PASS` → `pass`, `REJECT` → `reject`,
`UNVERIFIED` → `unverified`.

**A verdict only applies while the task is still `in_review`.** If the task
moved on while the review was in flight — a Supervisor rerouted it, another
review landed first — the reviewer run still settles, the `reviews` row and the
`verdict` event are still written, and `tasks.status` is left exactly where it
is. The run's final `status_change` event then carries `task_status_written:
null` and `task_status_not_applied: {"intended": ..., "found": ...}`, and the
same fact is written to `runs\<reviewer_run>\runner-error.log`. Use `review
show` to read a verdict that was recorded but not applied.

A reviewer run is **not** hooked: it mints no evidence codes, so the codes it is
citing cannot shift while it reads them. Its reads still show up, through
`evidence_opened` — the runner sets `THOTH_RUN_ID` for every run, reviewer
included, which is what lets `thoth evidence show` inside a review attribute
its own opens.

`review show` prints the newest review's verdict and findings, the codes it
cited, the codes it actually opened, and a `unopened_citation` warning for the
difference. That is a warning, not a failure — the reviewer may have read the
same bytes out of the diff it was handed — but a review that cites five codes and
opened none is worth a second look.

It leads with `brief` (BRIEF-1): the newest review's short conclusion, by the
same rule as `wait --run` on a reviewer (null without a review, and for a
research source check). `findings` stay whole. Breaking change: the worker's
`claims` are left out (`null`) unless you pass `--full`, which brings back the
claim table (`[]` without a review); `thoth task result <task>` has the same
claims. The human output prints `brief: ...` under its first line and the
`claim` lines only with `--full`. The MCP tool `thoth_review_show` takes the
same switch as the boolean `full`.

### Reviewer fixes, author confirms

A REJECT whose findings are small does not have to cost a whole new attempt.
With `--edit` the reviewer may attach the fix itself; Thoth applies it where
nothing else lives, the commander re-runs the checks on it, and a model the
commander picks confirms only that fix:

```
thoth review start TASK --edit --profile P --model M --effort E --reason "why this reviewer"
thoth wait --run EDIT_RUN                # REJECT, pending_fix true
thoth verify EDIT_RUN                    # the approved checks, in the fix worktree
thoth checks approve --run EDIT_RUN --reason "why"   # only if the fix changed a protected file
thoth review confirm TASK --profile P2 --model M2 --effort E2 --reason "why this confirmer"
thoth wait --run CONFIRM_RUN             # PASS or REJECT
```

`--edit` is for code tasks; a `docs`, `research` or `review` task is refused.
The reviewer stays read-only. It answers with the usual review document plus
`edits`, each `{"path","old","new","criterion","reason"}`: `old` is text that
occurs exactly once in the file as the earlier edits left it (`""` creates a
new file), `criterion` names an unmet criterion or `extra_findings[i]`. Thoth
applies the edits in order in `worktrees/TASK-aN-fix`, a detached checkout of
the candidate that a new `review start --edit` resets, and holds the result to
fixed bounds, measured with git against the candidate:

- every edit is bound to a finding whose `fix_size` is S or M, and every unmet
  criterion has an edit (an L finding, or one without a size, is redone);
- every extra finding whose `severity` is not `minor` (trimmed, any case; an
  empty or unknown severity counts) has an edit too: a fix that leaves a
  blocking finding open is refused at stage `size`, and the task is redone. A
  `minor` finding may stay, and a confirmed PASS keeps it;
- at most 40 changed lines (added plus deleted, a replaced line counts 2) in at
  most 3 files, plain text only;
- no file that parses as a Thoth spec, before or after;
- an existing test file only gains lines, and no line holding `assert`,
  `#[test]` or `#[cfg(test)]` is deleted, no `#[ignore]` added;
- no check input and no check-word file;
- nothing under `.agent/`, `.agents/` or `.git/`, no path that leaves the
  worktree, and the reviewer itself changed no file and left HEAD alone.

These keep a fix to what a second model can judge in one sitting and away from
what the checks themselves read; anything larger is a normal rework. A fix
that fits is committed on `thoth/TASK/aN-fix` (the implementer's branch and
candidate are not touched), its REJECT is recorded without a `verdict`, and the
task stays `in_review` with `review show`'s `pending_fix` true. A fix that does
not fit is refused (`review_fix_refused` names the stage), the worktree and the
branch go back to where they were, and the REJECT settles the task as usual.

`thoth verify EDIT_RUN` runs the approved checks in the fix worktree and
records the commit they ran on (`head_commit`, `head_commit_after`) and whether
they left it clean. `review confirm` needs that verify: refused before it,
after a `--at-base` or dry run only, or when the checks moved HEAD or changed a
file. It also needs the fix's own protected changes approved on the edit run:
a fix that adds lines to an existing test file or changes an inline test region
lists them on its diff evidence (`review fix: git diff ...`, on EDIT_RUN; the
`protected_changes` entries of EDIT_RUN in `thoth review packet TASK --json`),
and `review confirm` refuses, writing nothing but that evidence, until `thoth
checks approve --run EDIT_RUN --reason "WHY"` approved them. An approval of the
implementer run does not cover the fix. The write of a confirmed PASS checks
the same again; when it fails no review is written (`review_invalid` stage
`protected`) and the fix stays pending. Then the commander picks the confirmer
by quota: another provider when
there is quota, otherwise another model or another effort. Thoth records
whether the confirmer is of the implementer's provider and refuses only the
edit review's own model at the same effort; it picks nobody and waits for no
reset. Say why in `--reason` (the quota you saw, why this provider or model).
The confirmer reads `.agent/review-fix-input/` (the spec, the findings, the
completed edits, the patch) and answers ok or revise for each edit; it does
not review again and adds no finding.

APPROVE with a green verify is PASS: `review show` then gives `merge_branch`
and `merge_commit`, the fix branch and its commit. PASS means the fix may be
merged, not that it was; the commander reads the difference and merges it
themselves. A REVISE or a red verify (or one whose output was not collected in
full) is not adopted: REJECT, with the original findings plus one line per
revise, one for the red verify and one saying to redo the work from the
original candidate; `dispatch` then starts the next attempt from the
implementer's candidate, without the fix. One edit-then-confirm chain writes
one `verdict`. A confirm that fails, is invalid or is cancelled writes no
review and can be run again. That includes a confirmer that changed a file or
moved HEAD: its answer is not read, `review_invalid` names stage `worktree`,
the task stays `in_review` with the fix still pending, and Thoth puts the fix
worktree back at the fix commit (while the fix branch still points there), so
the next `review confirm` runs on the verified fix without a new `verify`.
Not adopting a fix at all is a plain `review start` of the original
candidate, or a reroute.

### Recording an external review

```
thoth review record <task> -f review.json [--json]
```

Use this when the reviewing agent runs **outside** thoth — e.g. a commander
Claude Code session judging a task's evidence itself, rather than a Thoth
reviewer run started with `review start`. `review record` checks things in a
fixed order:

1. `THOTH_RUN_ID` must not be set in the environment `record` runs in (see
   "Properties worth keeping" below) — checked first, before the file is even
   read;
2. the file is read and validated with the same rules a reviewer run's report
   is held to (schema, then spec, then coverage of every acceptance
   criterion, then every cited code exists as evidence of this task). An
   **invalid document** writes one `review_invalid` event and stops there;
3. inside the write transaction, the **preconditions**: the task must be
   `in_review`; no run of the task may be `queued` or `running` (the same
   guard `review start` / `dispatch` / `resume` use — the refusal names the
   live run); there must be a completed implementer run to judge (`review
   record` targets the same run `review start` would), and that run must
   have a `candidate_commit` (the same thing `review start` refuses to
   review without one); for a `PASS`, every protected `test`,
   `check_word` and `inline_test` change of that run must be approved (see "Approval before
   review" under "Protected files"). The run's diff evidence is recorded
   before the transaction when it is missing or unreadable, with `warning: `
   lines on stderr when that fails.

A valid document settles the task the same way a Thoth reviewer run's verdict
does: `PASS` → `pass`, `REJECT` → `reject`, `UNVERIFIED` → `unverified`.

**Invalid is refused, not settled `unverified`.** This is the one place an
external review's handling differs from a Thoth reviewer run's: `review
start`'s runner cannot roll back a finished process, so an unusable report
there lands the task `unverified`. Here the commander is present and can fix
the file and record again, so an invalid document (step 2) refuses outright:
non-zero exit, the failing stage and reason printed, one `review_invalid`
event (`source: "external"`), and neither the `reviews` table nor
`tasks.status` touched. Because step 2 runs before step 3, an invalid
document is what gets reported (and counted) even when a precondition would
also have failed — a task that is, say, both not `in_review` and being handed
an invalid document is refused for the document, not for its status.

A **precondition** refusal (step 3) is a different thing from an invalid
document: the message names what was found, and nothing is written at all,
not even a `review_invalid` event. Only the `THOTH_RUN_ID` guard (step 1)
means the document was never read at all; a precondition refusal happens
*after* the document was read and validated — it just does not matter once
step 2 already would have refused first.

A file that starts with a UTF-8 BOM (what `Set-Content -Encoding utf8` writes
on stock Windows PowerShell 5.1) is accepted; `serde_json` would otherwise
reject it outright. A file that starts with a UTF-16 BOM (`FF FE` or
`FE FF` — what PowerShell 5.1's `Out-File` and `>` write **by default**,
which is the more common trap) is refused with a message naming the encoding
and saying to save the file as UTF-8; this is a read error, so nothing is
written either.

The recorded review has no reviewer run behind it, so there is nothing to
attribute an `evidence_opened` event to: `review show` reports `opened` and
`unopened_citation` as `null` (not an empty list — an external review's
citations were never checked against what it "opened", so reporting `[]`
would read as a clean bill of health that was never earned) and prints
`opened: n/a (external review)`. `review show --json` also carries a `source`
field on the shown review, `"reviewer_run"` or `"external"`, so a script can
tell which kind of review settled the task without guessing from
`reviewer_run_id` being `null`.

### The review packet

```
thoth review packet <task> [--out packet.md] [--json]
```

One read-only document with everything a reviewer needs, instead of running
`evidence list`, `evidence show` and `events` by hand. It works at any task
status and writes nothing to the database except one `secret_redacted` event
when it masked a secret (see "Secret masking"): no other row or event, and in
particular no `evidence_opened` (a packet is not a reviewer opening a code).
Sections, in order:

1. task id, title, status, risk, then a `## Runs` list: for each run its id,
   role and attempt, the models it used with output tokens, and the number of
   subagents it spawned (`unknown` when the run never reported a result). A run
   that continued a stopped run (see "Handoff to another worker") ends its line
   with ` | continued from <previous run> (<reason>)`, and its `--json` entry
   in `runs` has `continued_from` (the previous run's id; `null` for every
   other run). A run that spawned any subagent gets a line starting `WARNING:`;
2. the spec's goal, acceptance criteria, constraints, non-goals and excluded
   alternatives, verbatim;
3. the evidence index: code, kind, exit code, run id, label, and for `command`
   rows the last 15 lines of the stored output;
   then `## Protected files changed`: for every `diff` row, each entry of its
   `protected_changes` as `path (status, kind)` with the diff's code and run
   (`kind` may be `inline_test`, LEAN-1; no claim is needed for an entry),
   followed by the text of each optional `protected_change` claim of the newest
   `result_ingested` event; either list says `(none)` when it is empty. A
   Claude reviewer's prompt carries the same list after its rule 1, with the
   instruction to decide, file by file, whether the change weakened a check
   and to say so in its findings; codex and Antigravity reviewers read it in
   the packet;
4. every `diff` row in full (all attempts, not cut at `evidence show`'s
   4000-byte default), each headed by its code, run id and `blob_verified`;
5. the `claims` of the newest `result_ingested` event, with the run they came
   from;
   then `## Approvals during this task`: every `check_approved` event since
   the task's `task_created` (a check approval names no task, from the main
   tree or any run) and every `protected_change_approved` event of this task,
   oldest first, one line each: `- TS | check ID (SOURCE, run RUN) | by WHO |
   reason: TEXT` or `- TS | protected changes of run RUN: PATH (STATUS, KIND),
   ... | by WHO | reason: TEXT`, with `(while run X was running)` or `(while
   runs X, Y were running)` when other runs had not ended (any of them could
   have run the command itself); `unknown` and `-` for an approval recorded
   before these keys existed. A Claude reviewer's protected-file list adds `;
   approved by WHO: TEXT` to each change an approval covers;
6. every review already recorded, oldest first: verdict, whether it was
   external (no reviewer run), and its findings.

The worker's own `summary` from result.json is left out on purpose: the
reviewer judges from evidence, not from prose. Section 5 says so.

A task with no evidence, no result and no review still gets a packet, with each
empty section saying so. An unknown task id exits `1` with an error naming it.

`--json` prints the same content as one document (keys `task_id`, `title`,
`status`, `risk`, `spec`, `evidence`, `protected_changes`, `diffs`, `claims`,
`claims_run_id`, `approvals`, `reviews`; see `docs/adapter-usage.md`). `--out FILE` writes the
exact bytes that would have gone to stdout to FILE as UTF-8 without a BOM,
leaves stdout empty, and prints `wrote FILE (N bytes)` to stderr.

### Repeated findings: `thoth retro`

```
thoth retro [--days N] [--json]
```

Lists which kinds of review finding keep coming back, so a repeated mistake
can be turned into a lint rule or a check instead of being caught by review
again. `--days` is how far back to look, in whole days of 24 hours (default 7,
1 to 3650; anything else exits 2).

It runs from any directory and reads every repo registered on this machine
whose state database exists, read-only, the way `thoth report` does. It writes
nothing and records no event. With no state directory yet, it reports nothing
and exits 0.

Every review created in the window counts, whatever its verdict (a
`created_at` that cannot be read is skipped). Each unmet criterion and each
extra finding is one finding; a met criterion is not. A confirmer's record
(`source` `author_check`) repeats the criteria and extra findings of the edit
review it confirms, which are counted with that review already, so retro
counts only the extra findings the confirm added, and not as a review of its
own: one "reviewer fixes, author confirms" chain counts once in `reviews` and
in each category. Findings are grouped by
their `category` (see "The reviewer"); a finding with no category, or one
outside the list, goes to `unclassified`, which is what every review recorded
before the labels existed looks like. Each group shows how many findings it
has, in how many tasks and which ones, and how many of each `fix_size`
(`unsized` for none). A group with two or more findings, other than `other`
and `unclassified`, is marked `suggest_check`; findings are counted, not
tasks, so the same category found again in one task's rework counts. The human
output then adds `seen N times in M tasks: consider turning it into a lint rule
or a check` (N findings, M tasks).
Groups are listed with the most findings first, ties by name. With no finding
it prints `retro: no review findings in the last N days`. `--json` keys are in
`docs/adapter-usage.md`.

## Spec lint

```
thoth spec lint <file> [--json]
```

Spec reviews kept finding the same few mistakes: a criterion written twice, a
check the repo does not have, a step that writes under `.claude`, a line number
that moved, a file that was renamed. A model is not needed to spot these, so
Thoth checks them with fixed rules, and `task create`, `task update-spec` and
`spec review start` run the same lint before they do anything. An **error**
makes those three refuse (exit 1, nothing written, the message starts with
`spec lint: N blocking problem(s): `); a **warning** lets them go on and is added
to their `warnings` as `spec lint: …`. Run `thoth spec lint` yourself to see the
report before creating the task. The rules would rather miss a problem than
report one that is not there; what they do not cover is still the spec
review's job.

Only `goal`, `acceptance_criteria` and `constraints` are read; `non_goals` and
`excluded_alternatives` often name the very things not to touch. Errors:

| rule | example |
|---|---|
| `too_large` | the file is over 40960 bytes, at every risk: split the task |
| `large` (LEAN-1) | the file is over 20480 bytes (and at most 40960) and the spec's `risk` is `low` or `normal` (or absent, which is `normal`; a file that does not parse has no readable risk, so it is `normal` too and `invalid_spec` is added) |
| `invalid_spec` | the spec does not parse (the message is the parse error) |
| `ac_blank` | `"  "` as an acceptance criterion |
| `ac_duplicate` | `"AC1:  x"` after `"AC1: x"` (ends trimmed, spaces collapsed) |
| `unknown_check` | `"checks": ["ghost"]` when the catalogue has checks but no `ghost` (an empty catalogue is not checked) |
| `claude_write` | `改 .claude/skills/x/SKILL.md`, `delete ~/.claude/agents/y.md` |

`claude_write` looks at one sentence at a time (split at `。`, `；`, `;`, a new
line, `. `). The sentence must name a `.claude` folder (not `.claude-plugin/`,
`~/.claude.json` or `CLAUDE.md`), have a write word outside backticks (改, 加,
寫入, 新增, 建立, 刪, 移除, 搬, 覆蓋, 編輯, write, edit, update, create, add,
delete, remove, move, rename, replace, …) and no negation outside backticks (不,
別, 勿, 禁, 免, 無, 沒, not, never, no, don't, without). So
`plugins/、.claude/、scripts/ 不碰` and `讀 .claude/skills/x` pass.

Warnings:

| rule | example |
|---|---|
| `large` | the file is over 20480 bytes (and at most 40960) at `important` or `high` risk |
| `missing_path` | `src/gone.rs` is not in the main work tree (`新檔 src/new_one.rs`, `johnny-lo/x`, `$THOTH_HOME/x`, URLs are left alone) |
| `missing_name` | ``src/present.rs 的 `absent_fn` `` or `src/present.rs:absent_fn`, when the file has no `absent_fn` |
| `line_number` | `src/a.rs:12`, `` `name`:12 ``, `第 12 行` (not `10:30`, `host:8888` or `第 3 節`) |
| `two_dot_diff` | `git diff master..HEAD`: compares the two tips, so use `master...HEAD` |
| `powershell_in_bash` | `` `$env:FOO = 1` `` or `` `Get-ChildItem` `` in a field that never says PowerShell or pwsh |

**Why `large` depends on the risk (LEAN-1).** `low` and `normal` tasks already
skip the mandatory spec review before their first dispatch (only `important`
and `high` are gated); that is unchanged. What LEAN-1 adds is the size rule
that goes with it: a spec nobody is required to review must stay at or under
20480 bytes, so `large` is an error there, and its message asks you to shrink
the spec or split the task. At `important` and `high` the spec review reads
the spec, so `large` stays a warning. The 40960-byte ceiling (`too_large`)
holds at every risk. The lint runs where it ran before — `task create`, `task
update-spec`, `spec review start` (on the stored spec, with or without
`--edit`), `spec review confirm` (on the proposed spec), a reviewer's edits
when they are recorded, and confirm's APPROVE — and nowhere new: `dispatch`, a
rework and `review start` do not lint, so a larger spec stored before LEAN-1
still dispatches, but a spec review of it is refused until it is shrunk.

A path counts as new, and is never reported, when `new`, `create` or `新`
stands in the 12 characters before it anywhere in the spec. "Main work tree"
means the files on disk in the repository's main checkout.

Reading the report: each line is `error: RULE (WHERE): MESSAGE` or
`warning: …`, where WHERE is `goal`, `acceptance_criteria[i]`,
`constraints[i]` or `checks[i]` (counting from 0); the size rules and
`invalid_spec` have no WHERE. The last line counts them; a clean spec prints
only `no problems found`. With `--json` the same findings come as `errors` and
`warnings` arrays of `{"rule","location","message"}`, plus `ok` and `bytes`.
The exit code is 1 when there is an error, and stdout carries the full report
either way. Through MCP the tool is `thoth_spec_lint` (read-only; pass `spec` or
the absolute path of a file as `file`).

## Spec review before the first dispatch

```
thoth spec review start <task> --profile <id> --model M [--effort E] [--reason R] [--timeout T] [--json]
thoth spec review record <task> -f spec-review.json [--json]
thoth spec review show <task> [--json]
```

Before an `important` or `high` task is dispatched for the first time, someone
from the other provider reviews its spec against the current code. There are
two ways in: `spec review start` lets Thoth run the reviewer itself (see
"Thoth's own spec reviewer" below); `spec review record` takes a review made
outside (a commander's subagent, or a human). The document:

```json
{
  "verdict": "REVISE",
  "criteria": [
    {"id": "AC1", "verdict": "revise", "findings": [
      {"check": "exists", "location": "src/ledger.rs:40", "note": "there is no reject_double_spend function"}
    ]},
    {"id": "AC2", "verdict": "ok", "findings": []}
  ]
}
```

- `verdict` is `APPROVE` (the spec can be dispatched) or `REVISE` (it has to
  change first);
- `criteria[]` judges every acceptance criterion: `id`, `verdict` `ok` or
  `revise`, and `findings[]`;
- each finding has a `check`, one of the four checks: `verifiable` every
  acceptance criterion can be verified, `exists` the files, functions,
  commands and tests the spec names exist in the current code, `consistent`
  the criteria do not contradict each other, `steps` 'how to test' is written
  as step-by-step actions; a `location` (`file:line`, or `spec` for the spec
  text itself); and a `note`. A remark about a constraint or a non-goal goes
  on the criterion it affects most, with location `spec`.

**Thoth's own spec reviewer.** `spec review start` launches a read-only run
(`role` `spec_reviewer`) in `worktrees/TASK_ID-spec-review`, a detached
checkout of the HEAD of the worktree the command runs in when that HEAD
contains the task's base commit, otherwise of the base commit itself
(`reviewed_commit`), moved there again on every start: the worker merges the
branch it started from first, so stale sentences are judged against what it
will see. Its input is `.agent/spec-review-input/spec.json` (the stored spec bytes;
masked when the spec holds a secret, see "Secret masking")
and a prompt that lists the four checks and the rules: read the body of every
function the spec names, list the edge cases considered, check that every
action the spec asks for is possible in the current code, change nothing and
run nothing, and (TESTS-1) treat a spec that tells the worker to run the whole
test suite in one foreground command, or to prove the whole suite itself, as
a finding: the whole suite is the control plane's verify, so the spec should
name the tests to run and say that the whole-suite evidence is the
commander's verify (with and without `--edit`; the author check of
`spec review confirm` judges only the edits and does not carry it). The prompt lists only
the criterion ids; the criteria themselves are in the file. Its report is
`.agent/spec-review.json`: codex answers with `--output-schema`/`-o` in a
read-only sandbox, antigravity with `--json-schema`/`structured_output`, Claude
Code writes the file with a shell redirect. The runner validates it exactly as
`record` does and writes one `spec_review` event with `source` `reviewer_run`
and `reviewer_run_id` (the event's `run_id` is the run too). The task's status
never changes, whatever the run's outcome. `thoth wait --run RUN_ID` reports
the verdict in `verdict`. An invalid report writes one `spec_review_invalid`
event (stages `read`, `schema`, `spec`, `coverage`, `started`, `spec_changed`,
`write`); a spec changed by `update-spec` while the reviewer runs is refused
the same way (`spec_changed`). Breaking change (RJ-1): you give the profile,
`--model` and `--effort` every time (a spec review continues no attempt, so
nothing is kept from an earlier one; `--effort` can be left out only for a
model without an effort setting, such as haiku, or (AGY-1) an agy model whose
name ends in its level, such as `gemini-3.8-flash-high`); `auto` is
refused and nothing is picked. Prefer a profile of the provider that did not
write the spec. A crashed or
cancelled spec reviewer leaves the task where it was, and `spec review start`
can be run again (the worktree is reused); `resume` refuses a spec reviewer
run. `start` refuses, writing no run and no event, when `THOTH_RUN_ID` is set,
when the task is `running`, `pass` or `cancelled`, when any run of the task is
live, when the spec changes while it starts, when `--model` or a needed
`--effort` is missing, and when `require-reason` is on and no `--reason` is
given. Its `--json` keys are `ok`,
`run_id`, `task_id`, `spec_sha256`, `reviewed_commit`, `task_base_commit`,
`risk`, `task_status`, `required_before_dispatch`, `profile`, `model`,
`worktree`, `worktree_reused`,
`worktree_moved`, `cleared_stale_report`, `allowed_tools`, `runner_pid`,
`run_dir`, `effort_requested`, `effort`, `effort_note`, `warnings`
(Breaking change (RJ-1): `auto`, `auto_reasons` and `live_quota_refresh` are
gone).

The rules:

1. every AC id appears exactly once, and nothing else does;
2. a `revise` criterion needs at least one finding (an `ok` one may carry
   findings as suggestions);
3. every finding has a known check, a location and a note;
4. `APPROVE` with a `revise` criterion is invalid;
5. `REVISE` with no `revise` criterion is invalid;
6. an invalid file is refused with exit 1 and one `spec_review_invalid` event
   (`stage` `schema`, `spec` or `coverage`, the `reason`, `source:
   "external"`); nothing else is written.

Preconditions, which refuse and write nothing: `THOTH_RUN_ID` must not be set
(a run does not review its own spec), and the task must not be `running`,
`pass` or `cancelled`. A file with a UTF-8 BOM is accepted and a UTF-16 one is
refused, the same as `review record`. If the task's spec changes between the
read the document was validated against and the write (an `update-spec` in
between), the record is refused the same way: the review judged the old spec.
A valid document writes one `spec_review` event and leaves the task's status
alone.

**The approval is bound to the spec.** Every spec review records the sha256 of
the stored spec bytes (`tasks.spec`, exactly as given to `task create` or
`task update-spec`). `task update-spec` changes that fingerprint, so an
earlier APPROVE no longer applies: `update-spec` warns, and the new spec needs
a new review. `task update-spec` is allowed on a `queued` task for exactly
this: a REVISE finds the task still queued.

**The gate.** An `important` or `high` task that has not been dispatched yet
(no implementer run of any status) is refused by `dispatch` unless the newest
spec review is an APPROVE of the current spec. The refusal names the task, the
risk, the current spec's sha256 and why (no spec review is recorded, the
newest is REVISE, or the newest APPROVE is for an older spec), and writes
nothing — no run, no event, no worktree. `--skip-spec-review REASON`
dispatches anyway and records a `spec_review_skipped` event on the new run
with the reason; the flag is accepted on any dispatch and always recorded.
`low` and `normal` tasks are not gated, and neither is any dispatch after the
first (a rework is not re-gated; `spec review show` and `dispatch --json`'s
`spec_review.approved` still show whether the current spec is approved).
`dispatch --json` carries `spec_review`: `{required, approved, skipped,
spec_review_id}`. A dispatch whose task's spec or risk changes while it is in
flight (an `update-spec` after the gate read it) is refused when it goes to
write the run: no run, no event, the status unchanged, and the worktree it
created is removed; dispatch again so the gate sees the new spec.

**Three REVISE in a row stop.** After 3 REVISE with no APPROVE between them,
`dispatch` refuses every dispatch of the task — whatever its risk, first or
not — and `--skip-spec-review` does not apply. The refusal names the reviews.
Recording an APPROVE of the current spec, or `task close`, ends it.
`update-spec` does not reset the count (every REVISE is followed by a spec
change anyway).

`spec review show --json` always has the same keys: `task_id`, `risk`,
`task_status`, `spec_sha256` (the current spec's), `review_count`,
`required_before_dispatch`, `approved`, `revise_streak`, `stalled`,
`pending_edits` (SR-3, below), and
`newest` (`null`, or `spec_review_id`, `verdict`, `spec_sha256`, `current`,
`created_at`, `seq`, `source`, `reviewer_run_id`, `document`, and SR-3's
`mode`, `edit_count`, `proposed_sha256`). `record --json`
has `task_id`, `spec_review_id`, `verdict`, `spec_sha256`, `risk`,
`task_status`, `approved`, `required_before_dispatch`, `revise_streak`,
`stalled`, `source`.

### Reviewer edits, author confirms

```
thoth spec review start TASK --profile PROFILE --model MODEL [--effort EFFORT] --edit [--json]
thoth spec review show TASK [--proposed-out FILE] [--json]
thoth spec review confirm TASK --profile PROFILE --model MODEL [--effort EFFORT] [--reason TEXT] [--timeout 30m] [--json]
```

A full review that comes back REVISE over small, obvious things (a wrong
name, a missing step, a scope line that was forgotten) costs a whole new
round. SR-3 lets the reviewer fix those itself and the author of the spec
confirm the fixes, instead of re-reviewing everything:

1. `spec review start --edit` runs the same read-only reviewer, with one more
   section in its prompt: besides judging every criterion it may list
   `edits`, each one `field` (goal, acceptance_criteria, constraints,
   non_goals or excluded_alternatives), `op` (replace, insert or delete; the
   goal and a criterion can only be replaced, and a replaced criterion keeps
   its id), `at` (the entry's position after the earlier edits), `anchor`
   (the first 10 characters of the entry it changes, counted without the
   whitespace at either end, so a wrong `at` is caught), `text`, `criterion`
   (the AC it serves) and `reason`; every edit carries all seven, `""` or
   `0` when one does not apply, and nothing else. A change the
   reviewer is sure of goes in `edits`; a question only the author can answer
   stays a finding. The reviewer writes no file: Thoth applies the edits to
   the stored spec, lints the result like `update-spec` would, and keeps it
   as the *proposed spec* inside the REVISE event (`mode` `edit`), together
   with the list of what changed (`edits`, `edit_count`, `bytes_before`,
   `bytes_after`, `proposed_sha256`). An edit that breaks a rule (a field
   that cannot be edited, an anchor that does not match, a criterion id that
   changed, a blank reason, a text that carries a mask marker the stored
   spec does not have, copied from the masked spec the reviewer read) or a
   proposed spec the lint refuses is a
   `spec_review_invalid` (stage `edits` or `lint`) and no verdict. With edits,
   REVISE is the verdict even when every criterion is `ok`; an APPROVE
   proposes no edits. The task's spec is untouched at this point.
2. `spec review show` says `pending_edits: true` when the newest spec review
   is such an edit REVISE of the current spec, and lists the edits one per
   line. `--proposed-out FILE` writes the proposed spec to a file, so the
   commander can read it, or edit it by hand and `task update-spec` it.
   `dispatch` of a gated task says the edits await the author check.
3. `spec review confirm` launches the author (use the profile and model that
   wrote the spec) as another read-only run of the same role, in the same
   worktree, with `spec.json`, `proposed.json` and `edits.json` in
   `.agent/spec-review-input/`. It judges only the edits, against the code
   they name, the rest of the spec and the original intent, `ok` or `revise`
   with a note each; it does not review the whole spec again and adds no
   findings. The author's APPROVE makes Thoth replace the task's spec with
   the proposed spec in one transaction (the same statuses and lint as
   `task update-spec`, a `spec_updated` event with `source` `author_check`)
   and record a `spec_review` APPROVE bound to the new sha256, so the gate
   lets the task go. The author's REVISE records a REVISE and leaves the spec
   alone; the commander then edits by hand (`show --proposed-out`,
   `task update-spec`, `spec review record`) or runs `start --edit` again.
   `confirm` refuses when `pending_edits` is false (no review, a review
   without edits, or a spec changed since the review) and when the task's
   status does not allow `update-spec`.

**Streak.** An edit review's REVISE and the author's REVISE each count one;
any APPROVE (the author's included) resets it; the limit of 3 and
`--skip-spec-review` are unchanged.

**Time.** Both commands take `--timeout` (default 30m). A spec over 20 KB
reviewed with a max-class effort can take longer: give `--timeout 2h`.

**Whether to send the edits to the author at all** is the commander's call,
not Thoth's: the event records `edit_count`, `bytes_before` and
`bytes_after`, and the commander decides from them to run `confirm`, or to
start a full review again when the edits amount to a rewrite.

**Briefs** (BRIEF-1). `spec review show --json` and `wait --run` on either
run carry the review's short conclusion as `brief`: an edit review's ends in
`; N edit(s) proposed` (`REVISE: 0/2 criteria need revision; 3 edit(s)
proposed`), and an author's check counts its answers (`REVISE: 1 of 3 edits
revise`). The human `spec review show` prints `brief: ...` under its first
line and keeps every criterion, finding, edit line and author answer below it
whole.

## Rework after a REJECT

```
thoth dispatch <task> --profile <id> --model <m> --effort <level> [--allow-attempt N]
thoth task update-spec <task> -f new-spec.json [--json]
```

`dispatch` now accepts a task in `reject`, and that is the one entry status that
**increments `attempt`**:

- a new worktree, `worktrees\<task_id>-a<n>`, on branch `thoth/<task>/a<n>`,
  branched from the **previous candidate commit** — the work is kept, the
  conversation is not;
- the run's copy of the spec gains a `rework` object (`attempt`,
  `previous_run`, `previous_attempt`, `previous_candidate`, `unmet`,
  `extra_findings`) naming the attempt the findings really came from, and the
  worker prompt gains a `## Previous attempt was rejected` section listing
  them and asking the worker, for each finding that changes behaviour, to add
  a test that fails first, run it on its own so the failing run is captured,
  then fix and run it again (findings that change no behaviour are exempt).
  The task's own spec is untouched;
- `attempt` may not exceed `tasks.attempt_cap` (default 2). Past that, `dispatch`
  refuses and tells you to raise the implementer tier or hand the task back.
  `--allow-attempt N` overrides that for **one dispatch** and writes nothing, so
  the next one is gated again; outside the reject path `--allow-attempt` is
  accepted on the command line but silently ignored — it only ever does
  anything on a dispatch out of `reject`. To change the cap for good:
  `UPDATE tasks SET attempt_cap = 4 WHERE task_id = '01J...'` in
  `repos\<repo_id>\state.db`;
- at `risk: important` or `risk: high` the findings are **not** folded
  automatically. `dispatch` refuses and sends you to
  `thoth task update-spec <task> -f new-spec.json`, which is allowed while the
  task is `draft`, `queued`, `reject` or `unverified`, validates the new document, updates
  `tasks.risk` to match, and records a `spec_updated` event;
- **that refusal is not permanent.** `task update-spec` never moves the task off
  `reject`, so a dispatch that only checked risk and status would refuse the
  same important/high task forever (trial 20's first important-risk REJECT).
  Instead, once the task's newest `spec_updated` event is newer than the newest
  REJECT `verdict` event it is meant to answer, `dispatch` proceeds exactly like
  a low/normal rework — attempt + 1, a new worktree from the previous
  candidate, the attempt cap and `--allow-attempt` still apply — but folds no
  findings, because the Supervisor's rewrite replaces them rather than sitting
  alongside them (the excluded alternative: folding on top of a rewrite could
  put back a finding the Supervisor dropped on purpose). A REJECT recorded
  *after* that `spec_updated` (a second rejected attempt) refuses `dispatch`
  again until the next `update-spec` answers it in turn. `dispatch --json`
  reports which of the two happened in `folded_by`: `"control_plane"` for the
  mechanical fold, `"spec_rewrite"` for this path, `null` outside a `reject`
  dispatch;
- a rework that folds zero findings through the mechanical (`control_plane`)
  path — no REJECT review recorded, or its findings are empty/unreadable —
  still dispatches — it is not worth refusing over, the Supervisor may have
  rewritten the spec instead — but it prints a warning (to stderr in human
  mode, in `--json`'s `warnings` array otherwise) so it does not happen
  silently. A `spec_rewrite` rework folds zero findings by design and does not
  warn;
- **the rework needs `--model` and `--effort`.** Breaking change (RJ-1): the
  rework no longer steps up one level from the previous run on its own. It is
  a new attempt, so like a first dispatch it is refused without `--model` and
  (unless the model has no effort setting, or is an agy model whose name ends
  in its level) `--effort`; choose them yourself,
  for example a higher effort or a stronger model than the rejected run's. A
  dispatch out of `unverified` is not a rework: it is the same attempt and
  keeps the previous run's model and effort for whatever you leave out.

### Stuck

Automatic rework stops after the same reason appears in three consecutive
post-`spec_updated` REJECT reviews: an acceptance criterion judged `unmet`, an
identical extra finding, or the same non-zero `result.json` refusal rule.
Finding notes are compared exactly after trimming, Unicode lowercasing,
collapsing whitespace, removing evidence-code tokens such as `E004`, and
removing a trailing `.`, `。`, or `;`; this is not fuzzy matching. Rule `0` is
a database failure and never counts. Event `seq`, not timestamps, determines
the order.

Dispatch refuses a stuck `reject` or `unverified` task before creating a run or
worktree. Rewrite it with `thoth task update-spec TASK -f new-spec.json`, or
close it with `thoth task close TASK --reason ...`; the newer `spec_updated`
event resets the counter. `--allow-attempt` cannot bypass this guard.

## Abandoning a task

```
thoth task close <task> --reason TEXT [--json]
```

Closes a task nobody will carry on with: `tasks.status` goes from `queued`,
`failed`, `interrupted`, `unverified` or `reject` to `cancelled`, and one
`task_closed` event records `from` (the previous status) and `reason`. A
`queued` task has never been dispatched (for example one stopped by three spec
review REVISE in a row), so it has no run and no worktree; closing it only
cancels it. The task then drops
out of `thoth status` and the report counts it as 已取消 instead of 需要處理.
It refuses (exit 1, nothing written) from any other status, while a run of the
task is still `queued` or `running` (the same wording as the other live-run
guards), and when `--reason` is empty. `--json` prints
`{"ok": true, "task_id", "previous_status", "status": "cancelled", "reason"}`.

`task close` then removes the clean worktrees of this task and of every other
`pass` or `cancelled` task (see "Worktree cleanup"); the branches stay. A
worktree with uncommitted changes is kept, listed in the output (`--json`:
`worktrees.kept`) and recorded in a `worktree_kept` event. `cancel` stays a
run-level command.

A docs, research or review task (below) is also closed from `in_review`, for
a delivery nobody will use (`task_closed`'s `from` is `in_review`). Any other
`in_review` task waits for a review, and `task close` refuses it with a line
saying that from `in_review` only a docs, research or review task can be
closed.

## Taking a document task's delivery

```
thoth task result <task> [--run RUN] [--json]
thoth task accept <task> --reason TEXT [--json]
```

A document task is one whose spec `task_type` is `docs`, `research` or
`review`: what it delivers is a document (a spec, a research report, a review
verdict), not code to review. Whether its spec lists `checks` does not matter.
Its run ends like any other, and the task waits in `in_review`.

`task result` prints what the worker delivered: the task's newest ingested
result.json (or, with `--run`, that run's; the run must belong to the task),
read from its `result_ingested` event. It shows the run (id, attempt, role,
profile, model, candidate commit), the worker's `summary` in full under
`summary:`, and `claims (N):` with one `- KIND: TEXT [CODES]` line per claim.
`--json` prints `{"ok", "task_id", "task_status", "title", "run_id",
"attempt", "role", "profile", "model", "candidate_commit", "worktree",
"ingested_at", "result_status", "summary", "claim_count", "claims"}`, each
claim `{"kind", "text", "evidence"}`. It writes nothing and works at any
status, after the task is closed too. With no ingested result.json (a
`queued` task, or one whose only result was refused) it exits 1 and points to
`thoth events --task TASK --json`, where a refused one is a `result_invalid`
event.

It also leads with the delivery's brief (BRIEF-1): `--json` adds `brief`,
`brief_source` (`worker` when the worker's result.json has a non-blank string
`brief`, otherwise `summary`) and `brief_truncated`; the human output prints
`brief: ...` above `summary:`, and when the brief was cut at 1,000 characters,
a line naming this command for the full text. Ask a document task's worker
for a brief that names the documents it wrote; the summary and claims are
still shown whole, before and after `task accept`.

`task accept` takes the delivery: `in_review` → `accepted`, with one
`task_accepted` event recording the reason and the run whose result.json was
taken. It is not a review: nothing goes into the reviews table and no
`verdict` event is written, so `thoth models` counts the run as completed but
not reviewed, and the run's records line has `verdict` null. An `accepted`
task is finished: it drops out of `thoth status`, the report lists it as
已收件 among the finished tasks (it is in none of the overview counts), and
`dispatch`, `task update-spec`, `task close`, `review start`, `review record`,
`spec review start`, `spec review record` and `resume` refuse it. `task
accept` then sweeps the worktrees as `task close` does. It refuses (exit 1,
nothing written) inside a run (`THOTH_RUN_ID` set: a worker does not take its
own delivery), with an empty `--reason`, from any status but `in_review`, for
a task of another `task_type` or none (review it with `review start` /
`review record`), and while a run of the task is `queued` or `running`.
`--json` prints `{"ok", "task_id", "previous_status", "status": "accepted",
"reason", "run_id", "result_status", "candidate_commit", "worktrees"}`.

An external REJECT recorded with `thoth review record` folds into the next
attempt exactly the same way a Thoth reviewer run's REJECT does.

Evidence codes keep counting across attempts: a task's sequence is per task, not
per attempt, so `E001` always means the same bytes. Because attempt 2's
worktree is branched from attempt 1's candidate rather than starting fresh,
attempt 2's `diff` evidence is **incremental** — it is a diff against the
previous candidate, not against the task's original base — while attempt 1's
evidence stays fully citable (evidence codes are per task and continue across
attempts, so nothing about a later attempt invalidates an earlier code).

`thoth status <task>` (the single-task form; the no-argument list does not
carry these fields) shows `attempt` and `attempt_cap`, both in `--json` and as
a `[attempt <n>/<cap>]` suffix on the human line's first line. For a task with
no runs yet, `attempt` is `null` in `--json` and the `[attempt ...]` suffix is
simply omitted from the human line. Each run row carries its `role`
(`implementer` or `reviewer`) in `--json` and as the column after the attempt
on the human line — a Phase 2 task has both kinds, and they are not
interchangeable.

## Worktree cleanup

A worker worktree holds a full checkout plus whatever the worker built in it
(a cargo `target/` makes it several GB), and a finished task never uses it
again. Thoth removes those directories itself; the branch, its commits and
every piece of evidence (`blobs/`, `runs/`, `state.db`) stay.

**What qualifies.** Only tasks whose status is `pass`, `cancelled` or
`accepted` and that have no `queued` / `running` run. The worktrees of
`draft`, `queued`, `running`, `in_review`, `reject`, `unverified`,
`interrupted` and `failed` tasks are never touched, because a rework or a
resume continues in them (and `resume` refuses a run of a `pass`, `cancelled`
or `accepted` task). Each candidate is a
`runs.worktree` of the task, and is removed only when all of these hold:

- it lies under this repo's worktrees directory (`outside_worktrees_dir`
  otherwise);
- `git status --porcelain` shows nothing outside `.agent/` and `.agents/`
  (`uncommitted_changes` otherwise; the detail lists the lines, up to 20);
- some local branch contains its `HEAD` (`unreachable_head` otherwise - a
  commit only that directory reaches would be lost with it).

A git command that fails on the directory keeps it as `git_error`. When all
three hold, Thoth runs `git worktree remove --force` and nothing else: it
never deletes a directory itself, never deletes a branch or a commit, and
never runs `git gc`. A directory that no longer exists is skipped without an
event; every sweep ends with `git worktree prune`, so git forgets it.

A spec reviewer's worktree (`kind` `spec_review`) is removed with the worker
worktrees when the task is `pass`, `cancelled` or `accepted`; until then each
`spec review start` reuses it.

**When.**

- The runner, right after it settles a run that left the task `pass` (a
  reviewer's PASS) or `cancelled` (`cancel`): that task's worker and spec
  review worktrees only. The review worktree stays, since whoever is waiting
  on the review may still be reading it.
- `review record`, after a PASS: that task's worker and spec review
  worktrees. The human
  output adds one `removed worktree PATH` or `kept worktree PATH: REASON`
  line each; the `--json` keys do not change.
- `task close`, `task accept` and `task create`: every finished task of the
  repo, worker and review worktrees alike. `task create` is the catch-up: it removes the
  review worktrees and anything an earlier sweep had to keep.
- `thoth worktrees prune [--json]`, whenever you like, from the main working
  tree: the same full sweep, listing what it removed and kept. It exits `1`
  when something was kept for `remove_failed` or `git_error`.

None of these sweeps runs when `THOTH_RUN_ID` is set (a worker or reviewer
must not remove other tasks' worktrees; `worktrees prune` refuses), or when
the command's current directory is inside the worktrees directory (`task
close --json` then reports `worktrees.error`; `worktrees prune` refuses).

**Events.** Each removal writes `worktree_removed`; each kept directory writes
`worktree_kept` with its `reason`, but only once per path and reason - a
directory kept for the same reason again (every `task create` looks at it)
adds no new event. `thoth events --task TASK` or `thoth worktrees prune
--json`'s `kept` shows what is waiting for you.

**Windows file locks.** A file still held open (an editor, a dying process)
makes `git worktree remove --force` fail: the directory is kept as
`remove_failed`, and the next sweep tries again. If git managed to delete
part of the directory first, the next sweep sees the missing files as deleted
and keeps it as `uncommitted_changes`. Either way, close whatever holds the
files and run `git worktree remove --force PATH` yourself, then
`thoth worktrees prune` (or `git worktree prune`).

**Uncommitted changes.** Commit them on the task's branch, delete them, or
drop them together with the directory with `git worktree remove --force PATH`.
Thoth itself never forces a dirty directory away.

**After removal.** `thoth verify RUN` on a removed worktree exits 1 with
`the worktree for run ... is gone`; run it with `--at-base`, or run the checks
in the main working tree after merging the branch. `thoth checks approve --run
RUN` fails as well, with git's message that it cannot run in a directory that
does not exist; run `thoth checks approve` in the merged main working tree
instead.

## Properties worth keeping

These are guarantees, not incidental behaviour. Changing any of them should be
a deliberate decision:

- **A live worker cannot approve itself.** While a task is `running`,
  `dispatch`, `review start`, `task update-spec`, `submit` and `review record`
  for that live run all refuse it — so a worker that runs `thoth` inside
  its own worktree (it has `Bash`, and nothing sandboxes it) cannot move its
  own task forward. `review record` additionally refuses outright whenever
  `THOTH_RUN_ID` is set at all (not just when it names *this* task's run):
  that variable is only ever in the environment of a process the runner
  itself launched (a worker's or reviewer's `claude`), so seeing it means
  `review record` is being run from inside one, most likely by that same
  process on its own task via `Bash`. This is a guard against **accidental**
  use, not a security boundary — Thoth has no sandbox, and a process can
  simply unset the variable before invoking `thoth` — but it costs nothing
  and catches the mistake it is aimed at. `spec review record` refuses the
  same way.
- **One live run per task.** While any run of a task is `queued` or `running`,
  `dispatch` refuses, `review start` refuses, `review record` refuses,
  `resume` refuses for every *other* run of that task, and `submit` refuses
  while a **reviewer** run is live. Each refusal names the run that is in the
  way, its role and its status, and each is checked inside the write
  transaction it protects, so two commands racing cannot both win. This is
  what keeps two workers out of one worktree and stops two settles from
  deciding one task's status between them.
- **A verdict is only applied to the state it judged** — see "The reviewer"
  above.
- **The reviewer cannot write.** A detached worktree plus
  `Bash,Read,Glob,Grep`, with no `Write`/`Edit`/`NotebookEdit`.
- **`thoth hook` never fails a run.** It always exits 0, prints nothing,
  opens no database.

## Decisions

```
thoth decision add "worktrees live outside the repo" [--file PATH] [--json]
```

Appends `- YYYY-MM-DD: <text>` to `decisions.md` in the repository root, creating
the file with a heading if it does not exist, and records a `decision_added`
event. It does **not** commit — that is your call.

Every harness loads `AGENTS.md` natively, so `AGENTS.md` has to reference
`decisions.md` for these to reach a worker. If there is no `AGENTS.md`, the
command warns once and still records the decision.

## Selective verification

```
thoth verify <run> [--dry-run] [--timeout 600s] [--at-base] [--json]
```

(2026-09-30, P7-1b: `verify` no longer runs the commands a worker declares.)

**What runs.** Only checks from the repo's approved catalogue (see "Approved
checks" below). If the task's own spec (the task's, not the run's copy) lists
ids under `checks`, those run, in spec order; if it lists none, every check in
the catalogue runs, in `check_id` order. Nothing supplied on the command line
and nothing a worker wrote is ever executed. Each check runs in the run's own
worktree, in its `cwd`, and is recorded as `command` evidence with a
`verify: ` label, `collected_by = control_plane`, and a `detail` carrying
`event: control_plane_rerun`, `blob_source: control_plane`, `argv` (the
argument vector actually sent), `program` (the absolute path of the file that
was run; `null` on a refused row), `check_id`, `shell`, `fingerprint` and
`approved_at` (those of the approval that matched; when none did, the newest
approval's), `fingerprint_ok`, `inputs_checked`, `exe_pin` (`hash` or `path`),
`approval` (`null`, or `{"match","fingerprint","approved_at","source","run_id"}`
of the approval that matched, `match` being `exact` or `package_info_only`) and
`package_info_lines` (`[{"path","line","approved","now"}]`, `[]` unless
`package_info_only`); a `package_info_only` row also has `auto_accepted: "only
package info changed"`, and a `powershell` check also carries `script`, the
text actually sent before encoding. `results[]` in `--json` carries the same
`approval` and `package_info_lines` on every row (see "Package-info
auto-accept" under "Approved checks").
`fingerprint_ok` and `inputs_checked` are always `true` or `false`, never
`null`: a check refused before its fingerprint was compared (unknown id, not
approved, unsafe `cwd`, unavailable shell) has `false` for both.
`fingerprint_ok` is `true` when an approval matched exactly and also for
`package_info_only`, where it means "differs from that approval only in the
allowed package-information lines". Read the
list with `--dry-run` first if you want to see it without running anything (a
dry run executes nothing and records nothing: no evidence rows, no `verify_ran`
event; each row there has `would_refuse`, a `reason` when it would, and
`fingerprint_ok`).

`verify` refuses a run that is not terminal (`queued` or `running`): nothing is
executed or recorded for a run that might still change.

**The five shells.** Each check runs with the shell it was added with:

- `argv`: no shell at all. The line is split on whitespace; a pair of double
  quotes groups words and is removed; there is no backslash escaping. On
  Windows the program must resolve (bare, `.exe`, `.cmd`, `.bat`, in that
  order) to a file ending in `.exe`; anything else is refused ("... is not an
  .exe ...; name the .exe itself, or use shell cmd for this check"). Windows
  starts `<path>.exe` in place of any path that does not end in `.exe`, so an
  approved `tool` or `tool.cmd` would lose to a `tool.exe` or `tool.cmd.exe`
  added beside it; and a batch file only runs through `cmd.exe`. The
  program that runs is the file the fingerprint resolved (a path relative to
  the check's `cwd`, or a name looked up on `PATH`), sent as an absolute path,
  so `detail.argv[0]` is that path. A program that resolves to nothing is
  refused. One split serves the fingerprint, the inferred inputs and the run
  alike (P7-1b, AC13): the program is the split's first element. So when the
  program's path has a space, use shell `argv` and put the path in double
  quotes: `"./my tool.exe" --version` runs `./my tool.exe`, and that is the
  file the `exe=` line pins. Writing the program with or without quotes pins
  the same `exe=` line, and a line without quotes fingerprints exactly as
  before. A double quote that is never closed is refused by `checks add` and
  by `verify` (`... has a double quote that is not closed`).
- `cmd` (Windows only), `powershell` (Windows only, `powershell.exe` 5.1),
  `sh`, `bash` (Linux only): the command must be one program and plain
  arguments, and thoth hands the shell the program as an absolute path (see
  "A shell check is one program and plain arguments" below). For
  `powershell` the exit code is the script's own `exit`, or the last native
  program's `$LASTEXITCODE`.

A check whose shell this platform does not have is refused (`check X uses shell
powershell, which is not available on linux`).

**A shell check is one program and plain arguments** (P7-1b, AC14,
2026-10-01). Thoth does not try to predict how `cmd`, `powershell`, `sh` or
`bash` would parse a command line; it gives them nothing to parse.

- *Grammar.* The command (blank is refused) may hold only ASCII letters and
  digits, space, tab, and `.` `_` `-` `/` `\` `:` `=`; the program word (up to
  the first space or tab) may not hold `=`. Anything else - `&` `|` `;` `<`
  `>` `^` `%` `!` `$` `` ` `` `(` `)` `[` `]` `{` `}` `*` `?` `"` `'` `~` `#`
  `@` `,` `+`, a newline, any non-ASCII character - is refused by `checks
  add` (exit 1, nothing written) and, for a row that got into `state.db` some
  other way, by `verify`, with `a shell check must be one program and plain
  arguments: '^' (U+005E) is not allowed ...`. The plain-word rule below is
  checked first and keeps its own message.
- *The program is an absolute path.* The program word is resolved once, by the
  fingerprint (`exe=`), and that file is what runs; it is never resolved again,
  and the shell never sees the word. `detail.program` records the path. What
  is sent:
  - `cmd`: `cmd /D /V:OFF /S /C ""%THOTH_CHECK_PROGRAM%" ARGS"` (one raw
    string after `cmd`), with the path in the child's `THOTH_CHECK_PROGRAM`.
    `/S` strips exactly the outer pair of quotes and leaves the quoted path, so
    a space, `&`, `^`, `'`, `(` or `%` in it is just text.
  - `powershell`: the encoded script `$ErrorActionPreference='Stop'; &
    $env:THOTH_CHECK_PROGRAM ARGS; if ($null -ne $LASTEXITCODE) { exit
    $LASTEXITCODE }` (UTF-16LE base64, `-NoProfile -NonInteractive
    -ExecutionPolicy Bypass -EncodedCommand`). The call operator never appends
    an extension and never consults an alias or function, so `sort` runs the
    pinned `sort.ps1`, not `Sort-Object`.
  - `sh`, `bash`: `sh -c '"$0" "$@"' PATH ARG...` (the arguments split on
    whitespace), so `test` runs the pinned `test` file, not the built-in.
  So `.\x/tool.cmd` runs `x\tool.cmd` (cmd alone would split at the `/` and
  run `x.bat`), `echo.cmd hello` runs the `echo.cmd` that was pinned (cmd alone
  runs its built-in `echo`), and `.\to^ol.cmd` is refused by the grammar.
- *Refused programs.* A program word that resolves to no file is refused
  (`program not found: ...`): a shell's built-in command (`call`, `cd`, `exit`
  in cmd; `exec`, `exit` in sh) is not a program. On Windows the resolved file
  must be one the shell runs itself - `cmd`: `.exe`, `.com`, `.cmd`, `.bat`;
  `powershell`: `.exe`, `.com`, `.ps1` - since anything else (a `.vbs`, an
  extensionless file) would be opened through its file association, and what
  started would not be the pinned file. A `powershell` check that resolves to
  a `.cmd` or `.bat` is refused with `use shell cmd for this check` (PowerShell
  hands a batch file to cmd, which expands any `%` in its path). PowerShell's
  call operator reads `[`, `]` and `` ` `` in a path as a wildcard or escape,
  so a `powershell` program whose absolute path holds one is refused. Each of
  these rows has `fingerprint_ok: false`, even when the fingerprint matched.
- *Need shell syntax? Write a script and approve the script.* For example:
  `cmd`: `.\ci\test.cmd` holding `cargo test 2>&1 && cargo clippy`;
  `powershell`: `.\ci\test.ps1` holding `if (Test-Path Cargo.toml) { cargo test }`;
  `sh`: `./ci/test.sh` holding `cargo test | tee out.txt`;
  `bash`: `./ci/test.sh` (with `#!/bin/bash`) holding `[[ -f Cargo.toml ]] && cargo test`.
  The script is a path program, so it is pinned by its bytes like any other
  executable; an argument with a space or another character outside the list
  needs shell `argv` instead.

This changed how `cmd` and `powershell` checks run, and their `exe=` lines may
differ from before; no repository had approved a check in either shell yet.
`argv`, `sh` and `bash` fingerprints are computed exactly as before.

Two limits to know. `cmd` hands a batch file its arguments split on `=` as
well as spaces, so `.\tool.cmd --flag=1` reaches the batch file as `--flag`
and `1`. And an `argv` check whose program is itself a shell (`cmd.exe /c
...`, `sh -c ...`) pins that shell, not what follows: the text after it is
parsed by that shell and none of the rules above protect it, so whoever
approves such a check has to read it as shell code.

Every check's process also gets `PATH` without its empty or relative entries
(such as `.`), and on Windows `NoDefaultCurrentDirectoryInExePath=1`; a
`hostname.bat` a worker leaves in the worktree never replaces the approved
`hostname`, and a script the check runs does not pick up programs from its
`cwd` either.

**The fingerprint sees what the shell sees** (P7-1b, AC12). Two rules keep the
program the fingerprint pins and the program the shell runs the same file:

- *One search list.* A bare program name is looked up along one list: `PATH`
  with its empty and relative entries dropped, order kept. The fingerprint's
  `exe=` lookup (every shell) and the check's child process use that same
  list. A relative entry such as `.` or `bin` would otherwise be read against
  thoth's own directory when fingerprinting and against the check's `cwd` when
  running, so a file a worker adds in a later absolute directory could run
  while `fingerprint_ok` stays true. With a `PATH` of only absolute entries
  nothing changes, so existing `argv`, `sh` and `bash` approvals stay valid.
- *A plain program word.* For `cmd`, `powershell`, `sh` and `bash`, the
  fingerprint takes the command's first word, up to the first whitespace, as
  the program, and that word must not contain a double quote, single quote, backquote
  or `$`, nor (in `sh` and `bash`) a backslash: the shell would read those
  before choosing the program (`"./my tool" arg` runs `./my tool`, while the
  fingerprint looked for `"./my`). `checks add` refuses such a command (exit 1,
  nothing written: `the program name must be a plain word ...; use shell argv
  for this check, or remove the quotes`), and `verify` refuses a row that got
  into `state.db` some other way. Quotes elsewhere in the line are refused too,
  by the grammar below; to run a program whose path has a space, use `argv`
  and put the path in double quotes (see `argv` above), where the quoted first
  word is the program itself.

**Which file a `cmd` or `powershell` check runs** (probed on Windows 11,
2026-09-30). The fingerprint's `exe=` line pins the file found by the order
below, and that file, by absolute path, is what runs:

- In one directory, a name written with an extension is tried as written
  first, then with each `PATHEXT` entry appended. A name without one is tried
  only with each `PATHEXT` entry appended, in `PATHEXT` order (`.COM` before
  `.EXE`, `.BAT` before `.CMD`); `cmd.exe` never runs an extensionless file.
  PowerShell tries `name.ps1` ahead of the `PATHEXT` entries and, for a name
  without an extension, the extensionless file last.
- A bare name (no path separator) is looked up along the absolute `PATH`
  entries in order; the first directory holding any candidate wins. So with
  `tool.com` and `tool.exe` in one `PATH` directory, `cmd` runs, and `exe=`
  pins, `tool.com`; PowerShell pins `tool.ps1` over `tool.exe`. Neither shell
  looks in the check's `cwd`: PowerShell never does, and a same-named `.bat`,
  `.cmd`, `.ps1`, `.exe` or `.com` there does not run.
- A program with a path separator (`.\gradlew.bat`, `.\scripts\test.ps1`)
  must be written with its extension, one the shell runs itself (a `PATHEXT`
  entry, or `.ps1` for `powershell`), and the file must exist; otherwise the
  check is refused ("program '.\gradlew' must be written with its extension
  ..."). Written in full, exactly that file runs: `.\tool.exe` beside
  `tool.com`, `tool.exe.com` or `tool.exe.bat` still runs `tool.exe`. Without
  the extension, a `tool.bat` added beside an approved `tool.cmd` would run in
  its place; with an extension outside `PATHEXT`, `cmd.exe` hands the file to
  its file association (a `.txt` opens Notepad).

On Linux, `sh`, `bash` and `argv` run a path program as the named
file (no extension is ever appended) and a bare name from the first absolute
`PATH` entry holding an executable file of that name, which is what the
fingerprint resolves; relative `PATH` entries are dropped from both, as above.

**Fingerprint.** Before a check runs, its fingerprint is computed again on the
tree it is about to run in, the same way `checks approve` computed it. It must
equal one of the check's approvals, or differ from one only in package
information (see "Package-info auto-accept"); otherwise the check is refused
with the lines that differ from the newest approval and the command that would
accept the change, for example `fingerprint mismatch for check test:
input=Cargo.toml; if this change is intended, approve it with: thoth checks
approve --run 01J... --reason "WHY"` (with the real run id). A worker that
edits a check's input file in any other way therefore cannot get that check
run until the edited file is approved. A check added with `--exe-pin path`
compares the program's path and not its bytes (see "Approved checks").

**Refusals.** Each of these becomes a recorded row with `exit_code: null` and
an `error`, counts as a failure, shows `REFUSED` in the human exit column, and
does not stop the batch:

- the id is not in the catalogue (`check X is not in this repository's check
  catalogue`);
- the check is not approved (`check X is not approved; approve it with: thoth
  checks approve --reason "WHY"`);
- a `cwd` that is absolute, has a drive/UNC/root component or contains `..`
  (only a direct write to `state.db` can put one there; it is checked
  lexically, before it is joined onto any path), or a `cwd` that does not exist;
- the shell is not available on this platform;
- a shell check whose program word is not plain (see above), or an `argv`
  check with a double quote that is not closed;
- a shell check that is not one program and plain arguments, whose program is
  not found, resolves to a file its shell does not run itself, or (for
  `powershell`) resolves to a batch file or a path holding `[`, `]` or `` ` ``
  (see "A shell check is one program and plain arguments");
- the fingerprint does not match;
- an `argv` program that does not resolve to an `.exe` (Windows);
- a `cmd` or `powershell` program with a path separator that is not written
  with a runnable extension, or does not exist.

If there is nothing to run at all (the catalogue is empty, or none of the ids
the spec lists is in it), `verify` runs nothing, records nothing and exits 1
with `no approved checks for this repository; add them with thoth checks add
... then approve them with: thoth checks approve --reason "WHY"`; `--json` has the usual
key set with empty `results`, `failures: 0`, `ok: false` and `reason:
"no_approved_checks"`.

**What the worker declared.** The `verification_requests` in the worker's
`result.json` are listed as `worker_declared` (each `{cmd, cwd}`) in `--json`,
in the `verify_ran` event, and on the human output after the results under
`worker declared (reference only):`. They are never run and get no evidence
row. They are read from the run's own `result_ingested` event when it holds a
readable `result_json`, with the worktree's `.agent/result.json` as the
fallback (and a warning when both exist and disagree, or when the event has no
readable document); when neither exists the list is `[]` with a warning.

**`--at-base` (baseline).** Runs the same approved checks, with the same rules,
`--timeout` and output caps, in a temporary detached worktree checked out at
the task's `base_commit` (under `<THOTH_HOME>/repos/<repo>/baseline-worktrees/`,
never inside the run's worktree). The fingerprint rule is narrower there: the
base checkout's input files are not read (it predates the candidate's edits by
design). For each approval, the sha256 compared with it is computed from the
check's current `shell=`, `cmd=` and `cwd=` lines, the `exe=` line resolved in
the base checkout, and the `input=` lines that approval recorded; the check
runs when one approval matches and is refused when none does, including an
approval that no longer matches its own record. The row's `detail.inputs_checked` is `false`. Each is recorded as `command`
evidence whose label starts `verify@base: ` and whose `detail` also carries
`at_commit` (the base sha); the `verify_ran` event and the `--json` output gain
the same `at_commit` key. The temporary worktree is removed afterwards, also
when a check fails or times out. `--at-base --dry-run` lists the checks and the
path they would run in, and executes and records nothing (its `fingerprint_ok`
is `false`: there is no checkout to compare yet). Use it when a reviewer must
judge "this failure was already there before the worker started": cite the
`verify@base: ` codes next to the plain `verify: ` ones.

**Per-check timeout.** `--timeout` (same duration syntax as `dispatch` /
`review start`, default `600s`). A check still running at its deadline is
killed and recorded as failed with `error: "timed out after <N>s"`.

**Incomplete output.** If a check exits but a descendant process it started
still holds the output pipe open a couple of seconds after it exited, the
check is recorded as a failure, even when the exit code was 0, with an
"output may be incomplete" error. See "Known limitations": that descendant is
not killed.

**Output size cap.** Each stream is capped at 8 MiB. Past that the pipe keeps
being drained (so a noisy command never blocks) but the bytes are dropped, and
the row reports `output_truncated: true` in `--json`, `[output truncated]` on
the human line, and `detail.truncated_inline: true` on the evidence row (the
same key a hook-captured row uses for "what is stored is cut short"). This is
**not** a failure: the command ran to completion and its exit code means what
it says, so `error` stays empty and the exit status of `verify` is unaffected.
It is a warning that the blob is a prefix.

Exit codes shown for a check with no numeric exit code: `REFUSED` (any refusal
above), `ERROR` (spawn failed), `TIMEOUT`, `INCOMPLETE`, `SIGNALLED`
(terminated with no exit code and none of the above applies). Each `--json`
result carries `check_id` and `shell`; `source` is `approved checks (spec)` or
`approved checks (all)`. The command exits 1 if any check failed, was refused
or timed out, or if there was nothing to run; the task's status is never
changed. The exit codes are for you to judge.

This is what it means for a High Risk claim to need `control_plane`
evidence: run `verify`, then have the worker (or `thoth submit`) cite the new
code.

## Approved checks

A repo can have a catalogue of approved checks. The commander approves them
(with a reason), and so can a person at a terminal. It lives in
`repos/<id>/state.db` (table `checks`), not in the repo, so a worker cannot edit
it. The idea is that a repo may *propose* what to run but cannot *authorise* it.

```
thoth checks add test --cmd "cargo test" --cwd .
thoth checks add py --cmd "python scripts/check_tests_no_db.py" --shell argv
thoth checks add plugin-validate --cmd "claude plugin validate plugins/thoth" --exe-pin path
thoth checks list
thoth checks approve --reason "the spec's AC3 asks for the py check"
thoth checks remove py
```

- `add` records the command, `--shell` (`argv` by default, or `cmd`,
  `powershell`, `sh`, `bash`), `--cwd` (relative to the repo root; the same
  rules as `verify`: no absolute path, drive or `..`) and the input files. Inputs
  are the `--input` files plus the ones inferred: any word of the command that is
  a file under the cwd, and the toolchain's own files (`cargo` → `Cargo.toml`,
  `Cargo.lock`, `build.rs`, …; `npm`/`pnpm`/`yarn`/`node` → `package.json` and the
  lockfiles; `python`/`pytest` → `pyproject.toml`, `conftest.py`, …; `go`;
  `dotnet` → its props files and any `.sln`/`.csproj`/`.fsproj` in the cwd). Only
  files that exist are listed. Adding an ID that exists replaces the row and
  forgets every approval it had, even when the new definition is identical;
  `remove` forgets them too.
- A `cargo test` check without `--no-fail-fast` gets one more line from `add`,
  `hint: cargo test stops at the first test target that fails, …` (`hints` in
  `--json`): cargo stops at the first failing test target, so a later target's
  new tests never run and a reviewer cannot see whether they pass. It is only a
  reminder; the check is stored, pending, either way.
- `add --exe-pin hash|path` chooses how the program is pinned. The default,
  `hash`, pins its resolved path and the sha256 of the file. `path` pins its
  resolved absolute path only (the `exe=` line is `exe=<path>|path-only`); it is
  for a program outside the repo that updates itself (Claude Code's automatic
  update replaces `claude`, which would otherwise need a new approval after every
  update). `--exe-pin path` is refused (exit 1, nothing written) when the
  program lies in the repository tree or in any worktree (a worker can edit it
  there), when it is written as a relative path such as `../tools/x` (each tree
  would find another file), or when it does not resolve now. The option is part
  of the fingerprint, so adding a check again with it clears the approval and
  it is approved again; a changed path (another `PATH` folder, say) still
  makes it stale. The cost: a program replaced in place goes unnoticed by this
  check.
- `approve` is not interactive and approves **every** check whose current
  fingerprint is not already one of its approvals, printing what it pinned.
  The commander approves with `--reason TEXT`, which says why the approval is
  right; without a terminal it is required, and `approve` without it exits 1
  and writes nothing (a blank reason is refused too). A person at a terminal
  may leave it out. Who approved is recorded as `approved_by`:
  `commander_mcp` when the command runs as the MCP tool `thoth_checks_approve`'s
  child process, `human_terminal` when stdin and stdout are both a terminal,
  `commander_cli` otherwise. A command typed with `!` in Claude Code has no
  terminal, so it counts as `commander_cli`. When something was approved the
  output ends with `approved by WHO; reason: TEXT` (`-` without a reason);
  `--json` adds `approved_by`, `reason`, `protected_approved` and
  `protected_unchanged`. Everything one `approve` reads and writes happens in
  one database transaction. A check keeps every approval it was given (table
  `check_approvals`); a new one is added beside the earlier ones, never in
  their place, and any one of them that matches is enough. The fingerprint (sha256) covers: the
  shell, the command text, the cwd, the executable (its resolved path and the
  sha256 of its bytes, or, for a check added with `--exe-pin path`, its resolved
  absolute path alone) and every input file's sha256 (a missing file is pinned as
  missing). An executable inside the repo is named by its tree-relative path so
  the same file fingerprints alike in the main tree and in a worktree. It also
  stores the tree's `HEAD` commit. Approve checks each `--exe-pin path` check
  again with its own `PATH` and does not approve one whose program does not
  resolve, lies in the repository or a worktree, or is named by a relative path;
  it prints `not approved ID: REASON`, approves the rest and still exits 0.
- `approve --run RUN` reads the files from that run's worktree instead of the main
  tree. Use it when the check's inputs exist only in a worker's candidate (a new
  test file, say) and you have reviewed them there. The run must be `completed`,
  `failed`, `cancelled` or `interrupted`. The main tree's own approval stays,
  so `list` shows the check `stale` only when the main tree matches none of its
  approvals (for example when it was never approved from the main tree and the
  run's change is not merged yet). It also approves that run's protected
  `test`, `check_word` and `inline_test` changes (see "Protected files"): those not covered by
  an earlier approval of the same run are listed under `protected_approved`
  (`approved protected change of run RUN: PATH (STATUS, KIND)` on the human
  output) and recorded in one `protected_change_approved` event; those already
  covered are listed under `protected_unchanged`. When the run's newest diff
  evidence has no readable `protected_changes` (recorded before the key
  existed, or damaged), nothing is approved for it and stderr says `warning:
  run RUN's diff evidence CODE has no readable protected_changes; run review
  start, then approve again`. While the run's task has a run that has not ended,
  `approve --run` exits 1 and writes nothing (`checks approve --run RUN refuses
  while task TASK has a live run ...`): a run of the same attempt reuses that
  worktree, so its files may still be changing. A live run of another task does
  not block it, and `approve` without `--run` is never blocked; but every
  approval records, as `live_runs`, the ids of all the repo's runs that had not
  ended, and the review packet shows them.
- `list` compares the **main tree** as it is now with every approval:
  `approved` (one matches, exactly or through package-info auto-accept),
  `stale` (none does; it names the lines that differ from the newest) or
  `pending` (none given). It notes `(+N earlier approvals)` when a check has
  more than one. `list`, `thoth doctor` and `verify` say `pinned by path only`
  for a check added with `--exe-pin path`; `list`, `doctor` and `thoth setup`
  judge `stale` the same way `verify` does.
- With `THOTH_RUN_ID` set (inside a worker or reviewer) `add`, `approve` and
  `remove` refuse and write nothing.
- A task spec may list ids in `checks`; ids that are missing or not approved only
  produce a warning at `task create`. `verify` then runs exactly those ids (or
  the whole catalogue when the spec lists none) and refuses any that is missing,
  unapproved or no longer matches its fingerprint; see "Selective
  verification". The worker's prompt lists the approved checks that apply, in a
  `## Checks the control plane will re-run` section. Under the list the
  section tells the worker to run the tests the spec names before it finishes
  (its `verification_requests` are kept for reference only), and then
  (TESTS-1) that the evidence for the whole test suite comes from the control
  plane's verify of those checks, not from the worker: it runs the tests the
  spec names, each as its own foreground command, never starts a whole-suite
  run that cannot finish within one command's time limit, and when the spec
  asks for the whole suite runs it in parts that each finish, keeping each
  part's output. The same two sentences are in the Claude, agy and codex
  prompts; they name no tool, since Thoth serves any language's repo.

### The tests-no-db check

Tests must check behaviour through the interface, not by opening the
database. `scripts/check_tests_no_db.py` makes a machine catch the usual
slip (TESTS-1): it scans every `.rs` file under `tests/` (subdirectories
included) and counts, per file, the lines that are not a `//` comment and
contain `rusqlite`, `Connection::open`, `state.db` or `global.db` as a plain,
case-sensitive substring (one hit per line at most; a path string or an
assertion that quotes a token counts too). `scripts/tests_db_allowlist.txt`
lists, one `path count` per line (`#` comments and blank lines skipped,
paths relative to the repo root with `/`; a path is normalised before it is
compared or checked for duplicates, so `tests/common/./mod.rs` or
`tests\common\mod.rs` is `tests/common/mod.rs` and the same file under two
spellings is a duplicate; a count is ASCII digits only, so `²` or a
fullwidth `１` is refused), how many such lines each file is allowed today.
A file not listed must have none; a listed file may not have
more; a listed file with fewer is also red, with a message to lower its
number (the allowlist only goes down); a listed file that does not exist, a
missing allowlist, a malformed line, a duplicate path, a count that is not a
non-negative integer, a path outside `tests/`, an unreadable or non-UTF-8
test file, a directory under `tests/` that cannot be listed (a partial scan
is never green), or no `tests/` directory are all exit 1 with the path and
the reason (a bad allowlist line names the allowlist and its line number).
Red output is one line per file (path, actual, allowed), up to five
offending lines with their number and text, and `FAIL: N file(s)`; green is
one `ok:` line. `--print-counts` prints the current counts in allowlist
format and exits 0 without reading the allowlist or writing anything: the
commander uses it to build the initial list and to check a diff after a
merge. `--root DIR` (default: the parent of `scripts/`) and `--allowlist
PATH` (default `scripts/tests_db_allowlist.txt`; a relative path is taken
from `--root`) are the only other options. The script changes no file,
touches no git and needs only Python 3's standard library;
`python scripts/test_check_tests_no_db.py` runs its own tests.

It is an ordinary catalogue check, added and approved by the commander on
each machine (a worker cannot add checks inside a run):

```
thoth checks add tests-no-db --cmd "python scripts/check_tests_no_db.py" --shell argv --input scripts/tests_db_allowlist.txt
thoth checks approve --reason "tests-no-db: allowlist as of TESTS-1"
```

(`python3` on Linux where `python` is not on PATH.) `checks list --json`
then shows the check's `inputs` as the script itself (worked out from the
command) and the allowlist, so a worker that changes the allowlist has
touched a protected file and the change needs the commander's approval; the
counts can only be lowered, and a rise means a new violation to remove, not
an entry to add.

### Package-info auto-accept

A version bump should not need another approval. When no approval matches a
check exactly, `verify` (and `list`, `doctor`, `setup`) still accepts it when
its fingerprint differs from one approval only in package information:

- in `Cargo.toml`, lines of the `[package]` table (not `[workspace.package]`,
  not `[dependencies.x]`) that assign one of `version`, `description`,
  `license`, `license-file`, `authors`, `repository`, `homepage`,
  `documentation`, `readme`, `keywords`, `categories` a one-line double-quoted
  string or a one-line array of them, with nothing after it (not even a
  comment), the same key on both sides;
- in `Cargo.lock`, the `version = "X"` line of a `[[package]]` block that has
  no `source = ` line (a package of this workspace);
- CRLF versus LF is not a difference (cargo rewrites Cargo.lock with LF).

The two files must have the same number of lines and hold no `"""` or `'''`;
the program, the command, every other input and every other line must be
unchanged. Anything else — a dependency, features, `build`, `links`,
`edition`, `[profile]`, `[patch]`, `.cargo/config`, the toolchain files — is
refused as before and needs `thoth checks approve`. The rule is fixed text
comparison, line by line; nothing judges whether a change looks harmless.

The comparison needs the approved bytes of the file. Thoth stores a copy of
each Cargo.toml / Cargo.lock input in the repo's blob store (`repos/<id>/blobs/`,
named by its sha256 and verified against it before use) when `approve`
approves or confirms a check, and when a `verify` matches exactly. Approvals
made before this version kept no copy: auto-accept starts to apply to them
after the first exactly-matching `verify` or `approve`. Until then, a refusal
whose only differences are such files says `package-info auto-accept needs the
approved copy of PATH, which is not stored (approvals made before this version
keep none); approve once more`.

An auto-accepted row in `verify` shows `auto-accepted (only package info
changed): PATH:LINE, …` (or `line endings only`), and its evidence carries
`auto_accepted`, `approval` (with `match: "package_info_only"`) and
`package_info_lines`. `--at-base` never auto-accepts: it does not read the
input files.

### Protected files

Thoth works out from each candidate diff which existing test files and check
input files were modified or deleted, records them on the diff evidence
(`protected_changes`, see "Evidence") and shows them to the reviewer (the
packet's `## Protected files changed` and the reviewer's prompt). Since LEAN-1
the worker does not declare them: a delivery is not refused for leaving one
out (rule 6 is retired), and a `protected_change` claim is optional. What
counts:

- test files, by path (the `touches_tests` heuristic);
- the input files of every check in the catalogue, approved or not;
- files named like a word of a check's command (`check_word`), which also
  covers a file that is *added*;
- (LEAN-1) existing Rust source files whose inline test region was changed or
  deleted (`inline_test`; the rule is under "Evidence");
- the repo's own extra patterns:

```
thoth checks protect "fixtures/"
thoth checks protect "*.snap"
thoth checks unprotect "*.snap"
```

A pattern has one of three shapes; anything else (`a*b`, `**/x`) exits `1`:

| pattern | matches |
|---|---|
| ends with `/` — `fixtures/` | any path one of whose segments is `fixtures` |
| no `/`, at most one `*` at the start or the end — `*.snap`, `golden_*`, `Makefile` | the file name: `a/b.snap`, `golden_x.txt`, `a/Makefile` |
| anything else — `data/expected.json` | exactly that path |

Patterns are stored lower-cased with `/` separators (paths are compared the
same way), unique and sorted, as a JSON array under the key
`protected_patterns` of `state.db`'s `meta` table — not in the repo, so a
worker cannot edit them. A file matching one is a `test` in
`protected_changes`. `checks list` prints them on a `protected patterns:` line
(`--json`: `protected_patterns`). `unprotect` of a pattern that is not in the
list exits `1`. With `THOTH_RUN_ID` set both commands refuse.

**Approval before review.** `review start` and a PASS `review record` refuse
while the run under review (the newest completed implementer run) changed a
`test`, `check_word` or `inline_test` file that nobody has approved for that
run: `refusing to
start a review of task TASK: run RUN changed protected files that nobody has
approved yet: PATH (STATUS, KIND), ...; read the change (thoth review packet
TASK), then approve it with: thoth checks approve --run RUN --reason "WHY" (MCP:
thoth_checks_approve)` (`refusing to record a PASS for task TASK: ...` for
`review record`). Nothing is written. Before judging, both record the
candidate's diff and commit evidence when the run has none (a run whose diff
the runner failed to record, or one brought to `in_review` by `thoth submit`),
and record the diff again when the newest one has no readable
`protected_changes`; when the diff still cannot be recorded they refuse (`run
RUN has no diff evidence for its candidate, so its protected file changes
cannot be checked`, or `... has no readable protected_changes, and recording it
again failed`). An approval belongs to its run: a rework run with the same
change needs its own. REJECT and UNVERIFIED records need no approval.
A diff evidence row with a `protected_changes` list but no
`inline_test_errors` list was written by a thoth before inline tests were
looked for, so it is not readable either: these gates record that run's diff
again and judge the new row, and `checks approve --run RUN` approves nothing
from it (with the same warning). `review confirm` gates a reviewer fix the same
way on the edit review run (see "Reviewer fixes, author confirms"): the fix's
protected changes are approved with `checks approve --run EDIT_RUN`, and an
approval of one of the two runs does not cover the other.
`check_input` changes are not gated here: `verify`'s fingerprint comparison
already refuses a changed check input, and package-info auto-accept lets a
version-only change through.

Limits: inline tests are detected only in Rust files and only with the
attributes described under "Evidence" (no other language's inline tests, no
configurable syntax); and nothing here judges whether a test became weaker,
or approves anything by itself — that is the reviewer's and the commander's
job. A list Thoth cannot read is never taken for an empty one.

## `thoth hook` (internal)

`thoth hook` is a hidden subcommand. You never run it: the adapter writes a
per-run `hooks-settings.json` pointing at this executable's absolute path, and
Claude Code invokes it for every `Bash` `PreToolUse`, `PostToolUse` and
`PostToolUseFailure`. It reads the payload on stdin, appends one line to the
run's inbox, copies any `persistedOutputPath` file immediately, and **always
exits 0 without printing anything** — a hook that printed would be telling the
worker what to do, and a hook that failed could change the run's outcome. This
never happens for a reviewer run (see "The reviewer" above).

`thoth hook --agy-pre` is the one documented exception to "never prints to
stdout". It is agy's `PreToolUse` hook (see "Antigravity workers", the tool
lock): agy reads the hook's stdout as its decision, so it prints exactly one
JSON line, `{"decision":"allow"}` or `{"decision":"deny","reason":"..."}`. It
still opens no database, reads no environment variable and always exits 0, and
a payload or policy file it cannot use is a deny whose reason says why, never
`{}` or silence.

`--settings` merges with your own user-level settings, so your personal
`PreToolUse` hooks still run inside worker sessions. That is deliberate: what
gets recorded is the command that actually ran, rewrites included.

## Troubleshooting

**A run failed with `command line too long:`.** Claude and codex get the
prompt on stdin, so their command lines stay short (`prompt.txt` in the run
dir is still the full text that was sent). Agy still takes the prompt on the
command line. Any harness whose command line is over 30,000 UTF-16 units is
not started: the run is settled `failed` and its `error_text` starts with
`command line too long:` and gives the length. For a long agy prompt, dispatch
the task to a claude or codex profile instead (W3, 2026-10-06).

**The evidence index is empty and the worker says so.** The hook appends to
`inbox\hooks.jsonl` and the runner drains it once a second, so the index can lag
a captured command by a second. The worker prompt tells a worker to re-run a
command if the index is still empty when it finishes. Check
`inbox\hook-errors.log` and `runs\<run_id>\runner-error.log`.

**A task went `unverified` with `rule: 4`.** A blob was edited or deleted after
capture. Blobs are content-addressed and append-only, so this means something
outside thoth touched `repos\<repo_id>\blobs\`. The evidence row is still
there; the bytes behind it are no longer trustworthy.

**`evidence show E001` says the code exists on more than one task.** Codes are
per task. Pass `--task <id>`, or run it from inside a worktree where
`THOTH_RUN_ID` is set.

**`review start` says there is no completed implementer run.** The task reached
`in_review` some other way — most likely `thoth submit` against a run that was
`interrupted` or `failed`. Re-dispatch so a run completes, or review the branch
by hand.

**A reviewer's verdict never arrived.** `thoth wait <task>` cannot wait for
one — use `thoth wait --run <reviewer_run_id>` (see above). If that times out,
check `thoth status <task>` for the reviewer run's heartbeat, and
`runs\<reviewer_run>\prompt.txt` plus `stream.jsonl` for what it was told and what
it did.

## Known limitations

**Without a sandbox, `collected_by = control_plane` protects against mistakes,
not against a malicious worker.** The worker's environment carries
`THOTH_INBOX_DIR`, its tool list carries `Bash`, and the inbox is an ordinary
file — so a worker that wanted to could append a hand-written line claiming a test
suite passed, and the runner would record it as `control_plane` evidence and let
the worker cite it. Nothing in Phase 2 stops that. `collected_by` is
`control_plane` on **every** evidence row Phase 2 writes, hook-captured ones
included — it does not by itself distinguish a control-plane re-run from a
hook-captured worker command. The discriminators today are `detail.event`
(`control_plane_rerun` vs. the hook's `PostToolUse`/`PostToolUseFailure`),
`detail.blob_source` (`control_plane`/`persisted`/`inline`), and the
`verify: ` label prefix.

This is deliberate, not an oversight. The filesystem half of the
Single-Writer guarantee belongs to a sandbox, and Phase 2 has no sandbox (see "Phase 2
limits"). Read the trust marker as what it actually claims: *the control plane, not
the claimant, wrote this row from what it observed.* That is what makes it useful
against a worker that is confused, over-optimistic or sloppy — which is the
failure mode evidence is meant to catch — and it is not a defence against a worker that is
hostile. `thoth verify` is the one thing here that a worker cannot influence at
all: the control plane runs those commands itself, in its own process.

The sandbox lands in a later phase; until then, dispatch work you would be willing
to run yourself (the same rule `docs/phase1/usage.md` already states for
filesystem access).

Eight smaller ones worth knowing:

- **An attempt 2 (or later)'s `diff` evidence is incremental, not
  cumulative.** It is a diff against the previous attempt's candidate, not
  against the task's original base — see "Rework after a REJECT" above.
- **A test file that exists on the main branch but not at the task's base,
  and that the task then edits, counts as added** (not in
  `protected_changes`).
  `protected_changes` counts from the task's base commit, where that file does
  not exist yet, and its content differs from the main branch's, so it is
  neither dropped nor listed as `modified`.
- **Keep criterion prefixes unique in a spec.** `acceptance_criteria` entries
  become ids from the text before the first `:`, so `"Build: compiles"` and
  `"Build: no warnings"` both become `Build`. The *reviewer* side is checked —
  a `review.json` that judges one id twice is rejected — but the spec side is
  not, and two criteria sharing an id cannot be answered separately. Write
  `"AC1: ..."`, `"AC2: ..."` or otherwise distinct prefixes.
- **`thoth decision add` run from inside a worktree writes the MAIN
  repository's `decisions.md`.** The repo root resolves to the main tree, not
  the worktree, so a worker that records a decision writes it where the
  Supervisor will see it — which is usually what you want, but it does mean
  the file is not in the worktree's own diff, and the write is not isolated
  from whatever else is happening in the main tree.
- **`--allow-attempt` is silently ignored outside the reject path.** Passed
  on a dispatch that is not a rework, it is accepted on the command line and
  does nothing — see "Rework after a REJECT" above.
- **`verify` does not kill a descendant process a declared command leaves
  behind.** A command that exits but leaves a child still holding its stdout
  pipe open is detected (see "Incomplete output" above) and the request is
  marked failed, so `verify` never hangs waiting for a pipe that will not
  close — but the leftover process itself keeps running. There is no Job
  Object containment for `verify` yet (Phase 1's worker Job Object does not
  cover this path), and deliberately no cgroup on Linux either, to keep the
  two platforms alike. On a *timeout*, Linux kills the command's process
  group as well as its live descendants, so a backgrounded child that stayed
  in the group goes too.
- **`verify` runs a check with the shell the check declares**, never a
  platform default: `argv` (no shell) anywhere, `cmd` and `powershell` on
  Windows, `sh` and `bash` on Linux; any other combination is refused. A
  shell check is one program and plain arguments (no quotes, no shell
  syntax), and the shell receives the program as an absolute path, so cmd's,
  PowerShell's and sh's own parsing never chooses the program; shell syntax
  belongs in an approved script. The evidence detail records the argv that
  was sent (`detail.argv`) and the file run (`detail.program`).
- **Evidence rows and blobs are append-only.** There is no `gc`, so a long-lived
  repository accumulates both.

## Phase 2 limits

No Presenter, no Auditor, no automatic cross-provider audit, no hooks for codex or gemini,
no `PreToolUse` wrapper, no `gc` (worktrees, blobs and evidence rows are all
append-only), no daemon, no sandbox. `thoth verify` is manual: nothing runs it
automatically on a High Risk task yet.

## Worker tool lock, and the usage events

A worker (implementer or reviewer) gets **only** the tools named in
`--allowed-tools` (default `Bash,Read,Write,Edit,Glob,Grep`; a reviewer gets
`Bash,Read,Glob,Grep`) and **no MCP servers**. The Claude Code adapter passes
the list twice: `--allowedTools` (auto-approve) and `--tools` (the real
whitelist of built-in tools), plus `--strict-mcp-config` with no `--mcp-config`,
so the account's claude.ai connectors are not loaded. Without this a worker
could launch subagents (the `Agent` tool), browse (`WebFetch`, `WebSearch`),
schedule (`Cron`) and use the account's MCP tools. When a task truly needs one
more tool, add it: `--allowed-tools Bash,Read,Write,Edit,Glob,Grep,WebFetch`.
An empty `--allowed-tools ""` skips both flags (unverified harness behaviour).
A research task's implementer (spec `task_type` `research`, and no other type)
is stored with `WebFetch` and `WebSearch` appended to the given list (not twice
if already there; an empty list stays empty), so it can read the web for its
sources; still no MCP servers. Its reviewers do not get them.
Claude is launched with `-p` and no prompt argument: the prompt goes to its
stdin, which the runner closes once it is written (W3, 2026-10-06).

The first two events come from the result line of every run that reaches one;
the runner writes the third as an implementer run settles:

| event `type` | when | `detail` |
|---|---|---|
| `run_usage` | once per run, when the result event arrives | `models`: object model id → output tokens (null when the harness gave no `modelUsage`); `subagents_spawned`: integer (null when the harness gave no `subagent_stats`) |
| `subagents_spawned` | additionally, only when `subagents_spawned` > 0 | `spawned`: the count; `note`: a fixed sentence |
| `run_quota` | written by the runner for every implementer and every reviewer run (since DT-1) of a claude-code or codex profile, after the stream ends and before the run's final `status_change`, whatever the outcome (completed, failed or interrupted; a resumed run writes another, and readers take each run's newest). Never for an antigravity run | `window`: always `five_hour`; `start_percent`, `end_percent`: the first and last reading of that window during the run, in percent; `points`: `end_percent` minus `start_percent`, in percentage points; all three are numbers rounded to two decimals, or all three null when either end has no reading or the two readings have different reset times (the window reset mid-run; reset times up to 600 seconds apart count as the same window, because codex shifts the reset time by a few seconds at the start of a window, and only one end having a reset time counts as different); one reading counts as both ends, so `points` is 0. `source`: `claude_stream` (the `five_hour` entry of `windows` in the run's own `rate_limit_warning` events, `utilization` × 100) or `codex_rollout` (the `used_percent` of the 300-minute window of the general bucket - `limit_id` `codex` or absent - in the `token_count` lines of the rollout file under `<config_dir>/sessions/` whose name contains the run's thread id). Since DT-1 three more keys, none of the five above changed: `seven_day`: an object with `start_percent`, `end_percent` and `points`, the same numbers for the weekly window (the `seven_day` entry of `windows` for Claude, the 10080-minute window of the general bucket for codex; judged on its own, so a five-hour reset mid-run does not null the weekly numbers); `reliable`: a boolean; `unreliable_reasons`: an array of strings, `[]` when `reliable` is true, in this order: `shared` (the operator marked the run's profile with `thoth profile set-shared`), `shared-check-failed` (the mark could not be read), `overlap:<run_id>` (once for each other Thoth run of the same account, in any registered repo, any role and any status, whose time interval overlaps this run's; a run with no end time counts as still running; ordered by run id), `overlap-check-failed:<repo_id>` (that repo's state database exists but could not be looked at, opened or queried - a repo whose state database does not exist is skipped - or, for the run's own repo, the run's own row could not be re-read for its start time; counted against the run). A run with `reliable: false` keeps its numbers; readers decide. A rough estimate, see below |

`run_quota` is a rough estimate, not a meter: codex reports `used_percent` as
whole percents, and any other work on the same account during the run (another
run, the user's own session) counts toward the same window. `thoth models`
sums each run's newest `points` into `quota_points` (see "Model inventory and
scores"); since DT-1 it only counts the runs whose newest event is `reliable`,
and the weekly `seven_day.points` the same way into `quota_points_weekly`.

### Token kinds

Since DT-1 each run's `runs` row also keeps every token kind its harness
reported, besides `input_tokens` and `output_tokens`: `cache_read_tokens`,
`cache_write_tokens`, `reasoning_tokens` and `total_tokens`. A kind the harness
did not report is NULL, not 0. What each harness calls them, and what contains
what:

| harness | `input_tokens` | `cache_read_tokens` | `cache_write_tokens` | `output_tokens` | `reasoning_tokens` | `total_tokens` |
|---|---|---|---|---|---|---|
| claude-code (`result` event `usage`) | `input_tokens`, which holds neither cache kind | `cache_read_input_tokens` | `cache_creation_input_tokens` | `output_tokens` | `output_tokens_details.thinking_tokens`, a part of `output_tokens` | input + cache read + cache write + output |
| codex (`turn.completed` `usage`) | `input_tokens`, which already holds the cached part | `cached_input_tokens`, a part of `input_tokens` | `cache_write_input_tokens` | `output_tokens` | `reasoning_output_tokens`, a part of `output_tokens` | input + output |
| antigravity (`result` `usage`) | `input_tokens` | `cache_read_tokens` | always NULL (agy reports none) | `output_tokens` | `thinking_tokens`, a part of `output_tokens` | input + output |

`total_tokens` counts no token twice. For codex `cache_write_input_tokens` is
left out of it: in every recording it is 0
(`tests/fixtures/codex/exec-commit-in-worktree.jsonl`), which cannot show
whether OpenAI counts it inside `input_tokens`, and leaving it out never counts
a token twice. When both `input_tokens` and `output_tokens` are missing (a
failed codex turn carries no usage) `total_tokens` is NULL; otherwise a missing
kind counts as 0.

A resumed run has several results, and the harnesses disagree on what a result
covers. Claude's `usage` covers only the turn that produced the result, so
every result is added to the columns
(`tests/fixtures/stream-sample.jsonl`: `num_turns` 4 and a `cache_read` about
four times that of one assistant message). Codex's `turn.completed` and
antigravity's `result` are the whole thread's or conversation's totals so far,
across `exec resume` and `--resume` too, so the later one replaces the earlier
(`tests/fixtures/codex/exec-resume.jsonl` reports 213 output tokens after
`exec-ok-and-failing-command.jsonl`'s 146 for the same thread, because it adds
67; `tests/fixtures/antigravity/e6-resume-background-command-stream.jsonl`
likewise continues `e5`'s total). A kind a result does not carry leaves the
column as it was.

Model names are information, not violations: a normal run shows a little haiku
next to the requested model (Claude Code's own background work). Spawned
subagents are the signal. Neither event ever changes a run or task status; the
commander judges. `status TASK --json` shows the same numbers as `models_used`
and `subagents_spawned` on each `runs[]` entry (null when unknown).

### Effort

`dispatch` and `review start` take `--effort low|medium|high|xhigh|max|ultra`.
Thoth turns it into the harness's own setting, lowered to what the model
supports, and records the requested level, the level sent and the reason on the
run (`status`, the `run_started` event and the review packet show them):

- Claude Code: `--effort LEVEL`, placed right after `--model MODEL`, on a fresh
  run and on a resume. Haiku does not support effort, so nothing is sent and a
  warning says so.
- Codex: `-c model_reasoning_effort="LEVEL"`, placed right after `-m MODEL`
  (so before any `resume`), for workers, resumes and reviewers. The supported
  levels come from that account's `models_cache.json`; a model not listed there
  is sent the level as given, with a warning.
- Antigravity (AGY-1): agy's own `--effort LEVEL` (`low`, `medium`, `high`,
  `xhigh`, `max`; `ultra` is lowered to `max`), placed right after
  `--model MODEL`, before `--dangerously-skip-permissions`, on a fresh run, a
  resume, a reviewer and a spec reviewer. A model name that ends in one of
  those levels (`gemini-3.8-flash-high`, `gpt-oss-120b-medium`; trimmed,
  any letter case) already is that effort, and agy refuses the pair
  (`--model X conflicts with --effort=Y`), so no flag is sent for it: the
  level is taken from the name, `--effort` may be left out (`effort` is
  recorded as that level, `effort_requested` null, and the note says
  `effort high is carried by the model variant gemini-3.8-flash-high`), and
  a `--effort` that differs is lowered to it with the usual note (`max is not
  supported by gemini-3.8-flash-high; using high`). Any other name
  (`claude-sonnet-4-6`) sends the flag and, like every other model, needs
  `--effort` on the first launch. Whether agy accepts the flag for such a
  name is still to be confirmed on a real run.

The note can be non-null even when the level sent equals the level requested: that means Thoth could not confirm the model supports it (for example no `models_cache.json` for codex, or a Claude model not in Thoth's table). A `launch` key written into a task's own spec is ignored: every run's spec gets its own `launch` from Thoth, and an invalid level stored there is treated as absent.

`resume` takes no `--effort`; it reuses what the run was started with. The level
recorded is the one Thoth sent: if the harness lowers or ignores it again,
Thoth cannot see that.

Breaking change (RJ-1): `--effort` left out is no longer worked out by a rule.
The first launch of an attempt is refused without it (unless the model has no
effort setting, haiku, or (AGY-1) is an agy model whose name ends in its
level); a reroute in the same
attempt keeps the `effort_requested` of the newest run of that role and
attempt (see "Automatic dispatch"). `--effort auto` is refused. `--effort
LEVEL` is used as written. `resume` is unchanged.

## Codex workers

A profile registered with `--harness codex` (setup: docs/phase1/usage.md,
"One-time setup") runs implementer tasks with `codex exec --json` instead of
Claude Code. Everything around the run is the same: the worktree, the prompt,
`.agent/result.json` and its ingest rules, diff and commit evidence, `wait`,
`resume`, `cancel`, review. What differs:

**The command.** A fresh run is

```
codex exec --json -m <model> -s workspace-write -c approval_policy="never"
  --disable multi_agent --disable apps --disable browser_use --disable computer_use
  --ignore-user-config -C <worktree> -
```

with `CODEX_HOME` set to the profile's directory. The prompt arrives on stdin
(`-` tells codex to read it there). `--ignore-user-config` keeps
a `config.toml` in the profile directory from adding MCP servers or tools back;
the login is still read from `CODEX_HOME`.

On Windows the launch also carries `-c windows.sandbox="unelevated"` (before `-C`, and before `resume` on a resumed run), because `--ignore-user-config` leaves codex on Windows with no sandbox implementation, so it would reject every command and write.

A research task's implementer (spec `task_type` `research`, and no other type;
fresh, resumed or retried) also gets `-c
sandbox_workspace_write.network_access=true -c web_search="live"` right after
the sandbox pair (`-s workspace-write`, or `-c sandbox_mode="workspace-write"`
on a resume) and before the Windows pair: the sandbox's network is on and codex's
hosted web search answers live. The writable area is unchanged. A codex
reviewer keeps `-s read-only` without them. The two keys were checked offline
against codex-cli 0.154's config parser; a real run over the network is still
to be confirmed.

**A codex worker never commits; thoth commits on its behalf.** The
sandbox's `workspace-write` mode lets the worker write inside its worktree,
but a linked worktree keeps its own index and `HEAD` in the main
repository's `.git/worktrees/<name>/`, which stays read-only regardless of
`--add-dir` or `writable_roots` — codex protects a working tree's own git
metadata even when the rest of the tree is writable. So the codex prompt
(unlike Claude Code's) tells the worker to leave its changes uncommitted, and
after a clean exit, before the diff and commit evidence are recorded, thoth
runs `git add -A` then `git commit` in the worktree itself (outside the
sandbox) when there is anything to commit. The message names the task's title
and the run id. It commits under the repository's own configured identity
(`user.name`/`user.email`, repo-local or the user's global config), or
`-c user.name=thoth -c user.email=thoth@localhost` when neither is
configured. With no changes, nothing is committed and the candidate is the
base commit, exactly as an unchanged Claude run. If the worker committed
anyway, thoth commits only what is left (or nothing). A failure to commit
is logged to `runner-error.log` and leaves `candidate_commit` unset, exactly
like any other failure to resolve a candidate.

**The model.** A codex run needs a codex model: `dispatch` (and `resume`) on a
codex profile refuses `haiku`, `sonnet`, `opus`, `fable` and any `claude-*`
name, and lists the codex models (`gpt-6-astra`, `gpt-5.6-sol`,
`gpt-5.6-terra`, `gpt-5.6-luna`, `gpt-5.5`). Breaking change (RJ-1): there is
no default model; the first dispatch of an attempt names one, e.g. `--model
gpt-5.6-luna`, with `--effort` (see "Automatic dispatch"). Always naming the
model is also deliberate: codex's default model once produced no output for 5
minutes.

**`--allowed-tools` does not apply.** Codex's tools are fixed by the sandbox
and the disabled features above; the flag is accepted and recorded on the run
row, and ignored.

**Evidence comes from the stream, not from hooks.** A codex run writes no
`hooks-settings.json` and has no inbox. Each finished `command_execution` item
on codex's `--json` stream becomes one `command` evidence row as it arrives, so
`.agent/evidence-index.json` is current before the worker writes result.json:

- label: the command as codex ran it (e.g. `/bin/bash -lc 'cargo test'`);
- blob: `aggregated_output`, stdout and stderr together;
- `detail.exit_code`: codex's real exit code (not parsed from an error text);
- `detail.status`: `completed` or `failed`; `detail.event`:
  `"codex_command_execution"`; `detail.blob_source`: `"stream"`;
  `detail.tool_use_id`: codex's item id; `detail.session_id`: the thread id;
- `detail.truncated_inline`: true when the output holds codex's own
  `... N bytes omitted ...` marker.

The session id is codex's `thread_id` (from `thread.started`), recorded as
soon as it arrives, so `resume` works even when the run stops before its turn
ends. `resume` relaunches `codex exec --json -m <model> -c
sandbox_mode="workspace-write" ... -C <worktree> resume <thread_id> -`, with the resume
prompt on stdin: every option comes before the `resume` subcommand, because `exec
resume` rejects `-C` and `-s` after it, and the sandbox is a `-c` value in
place of `-s`.

**Outcomes.** `turn.completed` with exit 0 goes through the normal result.json
ingest. `turn.failed`, or an `error` event without a later `turn.completed`,
settles the run `failed` with codex's error text in `runs.error_text`. An error
whose text contains one of the transient markers (`TRANSIENT_MARKERS`, among
them `stream disconnected before completion`, the string codex prints when its
stream drops; not recorded, the fake's text is synthetic) is retried by the
runner itself (`exec resume <thread>` when `thread.started` had named the
thread, else the same prompt again; see docs/phase1/usage.md "Temporary
problems"), and only after two failed retries is `interrupted` / `transient`,
which `thoth resume` continues. A run that ends in error
and is not a quota stop also gets the runner's login check (`codex login
status`): when it prints `Not logged in` the run is `interrupted` / `auth` and
the profile `logged_out` (see docs/phase1/usage.md "Quota interruptions"; the
real codex's logged-out wording is unverified, and an unrecognised one only
leaves the run `failed`). A `turn.*` event outranks any `error`; among `error` events the newest counts,
so a transient error followed by a usage-limit error is a quota stop. When
that text names a usage limit (`usage_limit_reached`, `rate_limit_reached`,
`UsageLimitExceeded`, "hit your usage limit", or status 429, besides the
patterns Claude runs use) the run is `interrupted` with reason `quota`
instead, and the profile is parked `rate_limited` as for Claude.

**Usage.** `run_usage` for a codex run has `models` = {requested model:
`turn.completed`'s `output_tokens`} (codex's stream names no model; null when
the turn failed), `subagents_spawned` = the number of collab/subagent items
seen (expected 0), and an extra key `unexpected_item_types`: the sorted item
types other than `agent_message`, `reasoning`, `command_execution`,
`file_change`, `error` and `todo_list` (an MCP tool call, a web search, a
collab call); a research task's implementer run, whose web search is on,
does not count `web_search`. A subagent count above 0 adds the usual `subagents_spawned`
event; neither changes a status.

**`run_started`** carries `harness` for every run, and `session_id` is null
for a fresh codex run. `worker_image` (the image name of the worker pid, which
`cancel` checks) is read right after spawn for a Claude run and sits on
`run_started`. For a codex run it cannot be: the npm `codex` is a
`#!/usr/bin/env node` launcher whose pid reads `codex` right after spawn and
`node` about half a second later. So a codex run's `run_started` has
`worker_image` null, and the image is read when `thread.started` arrives (the
launcher has settled by then) and recorded as `worker_image` on that
`harness_init` event, normally `node`.

Known limits:

- **Usage-limit detection is a guess.** No codex usage-limit error could be
  triggered while this was built; the markers come from strings in the codex
  binary, in the shape of an ordinary codex error. If a real one looks
  different, the run settles `failed` rather than `interrupted`/`quota`.
- **A command the sandbox blocks may leave no evidence.** When codex was
  denied a write it did not report the command on its stream at all, so
  "tried and was blocked" can be missing from the evidence.
- **Very long output keeps only its head and tail** (about 1 MiB), with the
  marker above; `truncated_inline` says so.
- **codex once hung on its default model**, which is one reason the model is
  always explicit; a run's `--timeout` is the backstop.
- **The ChatGPT account's quota is shared** with your own use of codex on the
  same account.

### Codex reviewers

For research tasks this is a source check with the source-check schema and
`-c web_search="live"`, retaining the read-only sandbox (see "Source check for research tasks").

`review start TASK --profile codex-a --model gpt-5.6-luna` runs the review on
codex. The model rule is the implementer's: a Claude name, or no `--model` at
all, is refused before anything is created. Everything outside the reviewer
process is unchanged: the detached review worktree, the stale-report clearing,
the task staying `in_review`, and the ingest of `.agent/review.json` with every
rule listed under "The reviewer" above.

**It cannot run thoth.** The reviewer runs in `-s read-only`, and SQLite
cannot open a WAL database there (it has to create the `-shm` file), so
`thoth evidence show` fails inside it. So before launching it the runner
writes its input into the review worktree:

- `.agent/review-input/packet.md`: the same Markdown `thoth review packet
  TASK` prints;
- `.agent/review-input/evidence/<CODE>.txt`: the whole stored blob of every
  evidence row the packet lists (non-UTF-8 bytes shown as U+FFFD; masked when
  it holds a secret, see "Secret masking"), and nothing else. The directory is emptied first, so a reused review worktree never shows
  the previous review's files.

The prompt tells it to read those files and the worktree's own files, not to
run thoth, to judge every criterion exactly once, and to cite a code from
the packet's index for every `met` criterion.

**Its verdict is its final message.** The launch is:

```
codex exec --json -m <model> -s read-only -c approval_policy="never"
  --disable multi_agent --disable apps --disable browser_use --disable computer_use
  --ignore-user-config --output-schema <run dir>\review-schema.json
  -o <review worktree>\.agent\review.json -C <review worktree> -
```

with `CODEX_HOME` set to the profile's directory. The prompt arrives on stdin
(`-` tells codex to read it there). On Windows the reviewer launch also carries `-c windows.sandbox="unelevated"` (before `-C`, and before `resume` on a resumed run), because `--ignore-user-config` leaves codex on Windows with no sandbox implementation, so it would reject every command and write.
`review-schema.json` is a
strict JSON Schema of `review.json` (no extra keys, every property required,
`verdict` one of `PASS`/`REJECT`/`UNVERIFIED`, criterion `verdict` one of
`met`/`unmet`), and codex itself — outside the sandbox — writes the final
message to the `-o` file. Because the schema requires `note`, a codex review
always carries one, often `""`; an empty note is treated exactly like a
missing one (so an `unmet` criterion still needs a code or a non-empty note).
`fix_size` and `category` are required too, on every criterion and every extra
finding, each either one of its listed values or `"none"` (the schema holds no
empty enum value, because Gemini rejects one); a `met` criterion carries
`"none"` for both. `"none"` (any case, surrounding spaces ignored), `""` and an
omitted field are all read as absent, so nothing is stored.
The schema only shapes the document: a malformed or uncited report still
settles the task `unverified` with `review_invalid`.

A codex reviewer's own commands (its `cat`s) are not recorded as evidence,
the same as a Claude reviewer's. Because it reads files instead of running
`evidence show`, it records no `evidence_opened` events, so `review show`
reports every code it cited under `unopened_citation`; for a codex review that
warning says nothing about whether it read them. A reviewer run cannot be
resumed, on either harness.

Cross-harness works both ways: a claude-code implementer can be reviewed by a
codex reviewer and a codex implementer by a claude-code reviewer.

## Antigravity workers

A profile registered with `--harness antigravity` (setup: docs/phase1/usage.md,
"One-time setup") runs implementer tasks with Antigravity CLI (`agy`,
`THOTH_AGY_BIN`, default `agy`). As with codex, the
worktree, `.agent/result.json` and its ingest rules, diff and commit evidence,
`wait`, `resume` and `cancel` are unchanged. What differs:

**The command.** A fresh run is

```
agy -p <prompt> --output-format stream-json --model <model> [--effort <level>] --dangerously-skip-permissions --print-timeout <N>s
```

with the worktree as cwd and stdin `/dev/null`. `--effort <level>` is there
only for a model name that does not end in its level (AGY-1; see "Effort").
Unlike claude and codex, agy's
prompt is still on the command line (agy's `-p` always takes the next token);
when the command line is over 30,000 UTF-16 units the run is settled `failed`
at once, before agy is started. No environment variable is set
for agy and `HOME` is left untouched: agy keeps its login in the system keyring
and has no variable that moves its data directory. The profile's `config_dir`
(normally `~/.gemini/antigravity-cli`) is used only to find the transcript
below. The prompt is Claude Code's: agy can commit in a linked worktree,
so the worker commits its own work and thoth commits nothing
on its behalf. There is no `hooks-settings.json` and no inbox; the tool lock
below uses agy's own workspace hooks instead.

**The print timeout.** Every agy launch (fresh, resume, reviewer) carries
`--print-timeout <N>s`, where N is the run's `--timeout` in seconds plus 300
(a 1800 s run gets `2100s`). The extra 300 s lets thoth's own limit fire first:
thoth's timeout keeps the full record and kills the whole process tree, while
agy's own expiry quietly hands back partial output. agy below 1.2.6 defaults
to a 5-minute limit; from 1.2.6 on the default is no limit. If agy's limit
still expires (it prints `[agy] print timeout after ... returning partial
output` on stderr and exits 0 with a SUCCESS result), the run settles like a
thoth timeout: run and task `failed`, `interrupted_reason` `timeout`,
`error_text` carrying agy's line and a note that it is agy's limit, no
`result.json` read and no `result_invalid`. `dispatch` re-dispatches it in
place like any timeout.

**The model.** The account's own list is the rule (MODELS-1): Thoth keeps no
written-down agy model list. `agy models`, which every login check already
runs (`profile check`, `profile login`, `dispatch`, `review start`, `spec
review start`), prints `Fetching available models...` and then one
`id<TAB>display name` line per model the account can use; each of those
checks stores that list on the profile (`global.db` schema 4,
`profiles.models` as JSON `[{"model","display_name"}]` and
`profiles.models_seen_at`), keeping the stored one when the check read no
such line, and a failed write is one `warning:` line on stderr. `thoth
profile check ID` is the way to read it again by hand; `thoth models` shows
it with the time it was read (`agy_models`). `dispatch`, `review start`,
`spec review start` and `resume` still refuse the four Claude aliases
(`haiku`, `sonnet`, `opus`, `fable`), an empty name and every codex model at
their model-rule step, now listing the stored slugs (or `no model list
stored; run `thoth profile check ID``). Then, right after the login check
(before the stuck check, the attempt cap, the worktree, the run row and every
event; for the two review commands before the review worktree and the run
row), the model is compared against the list the check just read, or the
stored one when it read none, trimmed and without regard to letter case: a
model outside it exits 1 with the list and `run `thoth profile check ID` to
read the list again`, and nothing is written. With no list at all the launch
goes ahead and warns `no model list for ID; model MODEL was not checked`;
agy then rejects a name it does not know (below). `resume` has no login
check, so it uses the stored list only. The string sent to agy is the one
given. `--allowed-tools` feeds the tool lock below.

**The tool lock.** Before every launch (dispatch and resume) the runner writes
two files in the worktree and deletes a third:

- `.agents/hooks.json`, agy's workspace hooks file, which maps each hook name
  to its event config:

  ```json
  {"thoth-tool-lock":{"PreToolUse":[{"matcher":"*","hooks":[
    {"type":"command","command":"\"<absolute thoth path>\" hook --agy-pre","timeout":10}]}]}}
  ```

  On Unix the thoth path is the only quoted token on the command line (agy
  runs it through `sh -c`). On Windows the command is the thoth path with **no
  quotes**, then ` hook --agy-pre`: agy 1.2.14 cannot run a hook command that
  starts with a quoted program, so every tool call errors and agy ends with the
  misleading `invalid UTF-8` (`agent executor error: ... string_value contains
  invalid UTF-8`, exit 3), unrelated to thoth's hook output. agy 1.2.14 also
  cannot run a path containing a space, so thoth must live in a path without
  spaces. If the path has a space, thoth first tries the 8.3 short path
  (`GetShortPathNameW`); if that still has a space (or short names are
  disabled), `dispatch` and `resume` fail before agy starts, with a message
  containing `agy cannot run a hook whose path contains a space`.
- `.agent/agy-hook.json`, the policy:
  `{"run_id":"<run>","role":"implementer","allowed_tools":[...]}`.
- `.agent/agy-hook-denials.jsonl` is removed, so the file holds only this
  launch's denials.

`.agents/` is added to the repository's `info/exclude` next to `.agent/`, so
neither reaches `git status`, the diff or the commit. The runner checks this
again before writing hooks.json on every launch, a resume included, so a
worktree made before the lock existed gets the line too (append-only; a
failure is logged to the run's `runner-error.log` and leaves `.agents/` untracked).

The allow-list is `runs.allowed_tools` split on `,` (trimmed, empties dropped).
For an antigravity profile, `dispatch` stores `AGY_IMPLEMENTER_TOOLS`
(`run_command, command_status, send_command_input, read_file, view_file,
list_dir, find_by_name, grep_search, write_file, edit_file, write_to_file,
replace_file_content, multi_replace_file_content, sed_file, finish, wait,
wait_5_seconds`) when
`--allowed-tools` is left at its default (`Bash,Read,Write,Edit,Glob,Grep`,
Claude's names), and any other value verbatim; so to give one more tool, pass
the whole list plus that tool (e.g. `...,wait_5_seconds,invoke_subagent`).
AGY-1: agy 1.4.4 renamed its file tools without a changelog entry
(`view_file` became `read_file`, parameter `Path`; `write_file` and
`edit_file` are read from the binary's tool source names and still to be
confirmed on a real run), while its `init.tools` still lists the old names.
Both generations stay on the lists: this is an allow-list, so a name agy no
longer has grants nothing, and a machine still on agy 1.4.2 keeps working.
Names are matched exactly, never expanded as aliases. A write, edit or shell
name found later may be added to the implementer list only, never to the
reviewer or research lists.
`resume` reuses the row's value; a row that still holds Claude's default
(dispatched before the lock existed) gets `AGY_IMPLEMENTER_TOOLS` in the
policy, while the row itself is left as it is. `dispatch --json` and
`status TASK --json` show the stored `allowed_tools`.

A research task's implementer (spec `task_type` `research`, and no other type)
is stored with `search_web` and `read_url_content` appended to that list (not
twice if already there; an empty list stays empty), so the policy lets it
search and read web pages. `browser_subagent` and `invoke_subagent` stay off
the list, and reviewers keep `AGY_REVIEWER_TOOLS`.

For every tool call agy runs `thoth hook --agy-pre` with the call on stdin.
A tool on the list is allowed; anything else, or a payload or policy the hook
cannot use, is denied with a reason, and agy skips that call. AGY-1: a denied
name that Thoth does not know at all (not in `AGY_KNOWN_TOOLS`, the table of
every agy tool name Thoth has seen: the recorded `init.tools`, the three agy
added later, and the 1.4.4 file tools) gets the reason `Thoth tool lock: the
tool NAME is not a tool Thoth knows; agy may have renamed its tools, so update
Thoth's agy tool table (AGY-1); this run's allow-list is (…)`, so a rename
shows up on the first denied call instead of after an UNVERIFIED review; a
known name off the list keeps `… is not on this run's allow-list (…)`; a
payload or policy the hook cannot use keeps its own reason. The table only
recognises names; it never produces or widens an allow-list. Each denial is
appended to `.agent/agy-hook-denials.jsonl` (`received_at`, `run_id`, `tool`,
`known_to_thoth` (whether the name is one Thoth knows; false without a usable
name), `reason`, `step_idx`, `conversation_id`). After agy's stream has
ended, and before the diff and commit evidence and result.json ingest, the
runner writes one `tool_denied` event per line (`detail`: `tool`,
`known_to_thoth`, `reason`, `step_index`, `conversation_id`, `received_at`;
a line written by an older hook without the boolean gets it recomputed from
its name) and puts the count in `run_usage`'s `tools_denied` (0 when none;
Claude and codex runs have no such key) and, beside it, `tools_unknown`: the
distinct unknown names among this launch's denials, sorted, `[]` when none
(the count still counts every denial). `wait --run` shows `tools_unknown`
(see "The loop, end to end"). A denial never changes a status.

**Evidence comes from the stream, exit codes from the transcript.** Each
`step_update` with `step_type: "tool"`, `tool_name: "run_command"` and
`state: "DONE"` is one command. The stream carries its output but not its exit
code, so the runner reads the code from agy's own transcript,
`<config_dir>/brain/<conversation_id>/.system_generated/logs/transcript_full.jsonl`
(the conversation id comes from the stream's `init` line, or on a resume from
`runs.harness_session_id`):

- a `GENERIC` line with the same `step_index` whose content says
  `The command exited with code N.`, or
- for a command agy moved to a background task (the `GENERIC` line says
  `Tool is running as a background task with task id: <conv>/task-<step>`), a
  later `SYSTEM_MESSAGE` line containing
  `Task id "<conv>/task-<step>" finished with result:` and the same sentence.

The sentence is read only where agy writes it: for a foreground command, in the
header of the `GENERIC` line (the text before the first `\nOutput:`, never the
command's own output), and for a background task, only when it comes right after
that task's own `Task id "<conv>/task-<step>" finished with result:` marker with
nothing but whitespace in between (the closing quote keeps `task-4` apart from
`task-40`, and other tasks' markers in the same message are skipped). A
background step's `GENERIC` line is never parsed, because its `Task Description:`
is the command's own text; `N` must be an optionally negative integer followed
by `.`, otherwise that occurrence yields nothing.

A finished command whose code is not in the transcript yet is **pending**: it
has no evidence row yet. The runner re-reads the whole transcript once a
second while anything is pending and records each command as soon as its code
appears, in step order, then republishes `.agent/evidence-index.json`. Once
the stream has ended it reads the transcript one last time; a command still
without a code is recorded with `exit_code: null`, and one
`command_exit_code_unknown` event is written for it (`detail`: `code`,
`step_index`, `cmd`, `note`). All of this happens before the diff and commit
evidence and before result.json is ingested. Rows are never updated after they
are written.

Each row: `kind: "command"`, `collected_by: "control_plane"` (the transcript is
written by the harness, not by the worker's own account), label = the
`CommandLine`, blob = `tool_info.output` byte for byte, and `detail`:

- `cmd`: the full `CommandLine`; `cwd`: the worktree;
- `event`: `"antigravity_command"`; `step_index`: agy's step number;
- `exit_code`: the code, or null; `exit_code_source`: `"generic"`,
  `"background_task"` or null; `status`: `"completed"` for 0, `"failed"` for
  non-zero, null when unknown;
- `session_id`: the conversation id; `blob_source`: `"stream"`;
- plus the keys every stream row has (`tool_use_id` null,
  `truncated_inline` false, `duration_ms`/`stderr_sha`/`error` null).

Codex rows carry `step_index` and `exit_code_source` as null.

**Session and image.** `runs.harness_session_id` is null after `dispatch` and
set to the conversation id when `init` arrives, so a run stopped mid-way can
still be resumed. `harness_init` carries that `session_id` and the model agy
resolved, and (AGY-1) `tools`, the tool list agy's `init` line reported, as
written (order and repeats kept), with `tool_count` its length; both null when
the line has no usable list (missing, null, not an array, or an element that
is not a string; an empty array is `[]` and `0`), and always null for Claude
and codex runs. It is a record for comparing agy versions later, nothing more:
agy 1.4.4 still reports the pre-rename names there while its model calls
`read_file`, so it is never compared with the allow-lists or used to build
one. `run_started` has `harness: "antigravity"`, `session_id` null for a
fresh run, and `worker_image` read right after spawn (agy is one native
process, normally `agy`), which is what `cancel` checks; cancel needs nothing
else.

**Outcomes.** They follow the ordinary rules. A `result` line with
`status: "SUCCESS"` and exit 0 goes through result.json ingest. `ERROR`, or a
non-zero exit of agy itself, is a harness failure: `failed`, with agy's
`error` text in `runs.error_text`. An unknown model gives exactly that
(`invalid model selection ...`, exit 1, no `init`, so no session and nothing to
resume). A non-zero exit of a command inside the run is only evidence, never a
failure (E2). No `result` line at all is `interrupted` / `crash`. When the
error text contains `RESOURCE_EXHAUSTED` or `quota exceeded` (the strings in
agy's binary; **untested**, since no real quota failure could be triggered),
the run is `interrupted` with reason `quota` and the profile is parked
`rate_limited`, as for Claude. The parking records which quota group the
model belongs to (`quota_group`); the other group's models stay usable (see
"Quota groups on a parked antigravity profile"). Four real agy failures are
`interrupted` / `transient`, not `failed`: `There was a network issue
connecting to the server, please try again.` (agy exit 3), `Eligibility check
failed: ... TLS handshake timeout` (exit 1, no `init`, so nothing to resume:
dispatch again), and `The stream was interrupted. Please continue the task you
were working on.` (exit 0, with a partial `response`); the recorded lines are
in `tests/fixtures/antigravity/fc1-*`. The runner retries these in the same
run - `--conversation <id>` when `init` had named the conversation (the network
issue, the interrupted stream), the same prompt afresh when it had not (the
eligibility failure) - and the run is `interrupted` / `transient` only after
two failed retries. The runner's login check for agy is
`agy models`: only `Please sign in to use Antigravity` makes a run
`interrupted` / `auth`; a check that fails for another reason (the network)
changes nothing. The runner's check stores no model list; the five commands
named under "The model" do.

**Usage.** `run_usage` has `models` = {requested model: the sum of every
step's `usage.output_tokens` on this launch's stream} (not the result line's
usage, which spans the whole conversation on a resume), `subagents_spawned` =
the number of distinct tool steps named `invoke_subagent`, `define_subagent` or
`browser_subagent`, `tool_names` = the sorted distinct tool names seen,
`tools_denied` = the number of tool calls the tool lock denied, and (AGY-1)
`tools_unknown` = the sorted distinct denied names Thoth does not know (`[]`
when none). A
subagent count above 0 adds the usual `subagents_spawned` event; neither
changes a status. `runs.input_tokens`/`output_tokens` come from the result
line. `status TASK --json` shows `models_used` and `subagents_spawned` as for
any run.

**Resume.** `resume RUN` relaunches the same command with the resume prompt
and `--conversation <conversation id>` appended; agy continues the same
conversation, and its step numbers continue too.

Known limits:

- **The transcript wording is undocumented, and agy updates itself** in the
  background (`~/.gemini/antigravity-cli/updater`). Parsing is lenient; a
  miss is `exit_code: null` plus `command_exit_code_unknown`, never a failed
  run. A transcript that cannot be read at all is one line in
  `runner-error.log`.
- **The tool lock is a guard rail, not a sandbox.** An implementer holding
  write tools (`write_file`, `run_command`, ...) could edit or delete
  `.agents/hooks.json` or the policy file and lift the lock for its later
  calls; `tool_names`, `subagents_spawned`, `tools_denied` and `tools_unknown`
  still show what it used. The lock does not look inside `run_command`'s
  command line either.
- **agy renames tools without saying so** (AGY-1: 1.4.2 to 1.4.4 moved
  `view_file` to `read_file`, with nothing in `agy changelog`), and there is
  no way to read its current tool names without spending model quota
  (`init.tools` is stale, `agy --help` and `agy plugin validate` list none).
  The lists therefore hold both generations, the hook names an unknown name
  on its first denial (`known_to_thoth`, `tools_unknown`), and
  `harness_init.tools` keeps what agy reported for later comparison.
- **The `cmd /c` path on Windows is unverified** until agy is tried there; the
  hook command is written to survive `cmd /c`'s quote handling, but only the
  Linux `sh -c` path has run against the real agy.
- **One agy account per machine user**, shared with your own agy sessions and
  their quota.
- **A command whose code is not yet in the transcript is not yet in the
  index** when the worker looks at it; a background command appears once it
  finishes.
- **A command can still forge another background task's completion.** One that
  deliberately prints a completion message for ANOTHER background task inside
  its own output can still mislead the parser, because the transcript is plain
  text. `thoth verify` (the control plane re-running the checks) is the
  backstop.

### Antigravity reviewers

For research tasks this is a source check with `search_web,read_url_content`
added and the source-check schema in `--json-schema` (see "Source check for research tasks").

`review start TASK --profile agy-a --model gemini-3.8-flash-low` runs the
review on agy. The model rule is the implementer's: a Claude alias, an empty
name or a codex model is refused with the account's stored list, and a model
outside the list the login check just read is refused right after that check
(MODELS-1), in both cases before any run row, worktree or event is written.
Everything outside the reviewer process is
unchanged: the detached review worktree, the stale-report clearing, the task
staying `in_review`, and the ingest of `.agent/review.json` with every rule
listed under "The reviewer" above.

**It has no shell at all.** `review start` stores `runs.allowed_tools` =
`AGY_REVIEWER_TOOLS` (`read_file, view_file, list_dir, find_by_name,
grep_search, finish, wait, wait_5_seconds`; AGY-1: `read_file` is agy 1.4.4's
name for `view_file`, and no write, edit, shell, subagent, task or message
name of either generation is ever on this list), and the runner writes the
tool lock described above
into the review worktree: `.agents/hooks.json` and `.agent/agy-hook.json` with
`role: "reviewer"` and that list (`.agents/` excluded as for an implementer).
So it cannot run tests, thoth or git, and cannot write or edit a file. Any
attempt is denied; each denial is a `tool_denied` event on the reviewer run,
and its one `run_usage` carries `tools_denied` and `tools_unknown`. A spec
reviewer (`spec review start`) gets the same list, never the research tools.

Its input is the codex reviewer's: before launching, the runner writes
`.agent/review-input/packet.md` (the `review packet` Markdown) and
`.agent/review-input/evidence/<CODE>.txt` (the whole stored blob of every row,
masked when it holds a secret: see "Secret masking"),
emptying the directory first. The prompt tells it to read those files and the
worktree's own files, that it has no shell and cannot write files, not to run
thoth, and gives the same five rules as the codex prompt.

**Its verdict is the result line's `structured_output`.** The launch is:

```
agy -p <prompt> --output-format stream-json --model <model>
  --dangerously-skip-permissions --json-schema <run dir>\review-schema.json
```

with the review worktree as cwd and no `--conversation`. `review-schema.json`
is the same strict schema the codex reviewer gets. agy has no output-file flag,
so when the `result` line has `status: "SUCCESS"`, agy exited 0 and the line
carries a `structured_output` object, the runner writes that object (pretty
JSON) to `.agent/review.json` and ingests it with the unchanged rules. A
result without `structured_output` writes nothing, and the ingest records
`review_invalid` with `stage: "read"`; the task settles `unverified`, as for
any malformed report.

Its `read_file` steps are not evidence. Because it reads files instead of
running `evidence show`, it records no `evidence_opened` events, so `review
show` reports every code it cited under `unopened_citation`, which (as for
codex) says nothing about whether it read them. `wait --run` reports its
`verdict` and `task_status`. A reviewer run cannot be resumed.

Cross-harness works both ways: a claude-code implementer can be reviewed by an
agy reviewer and an agy implementer by a claude-code reviewer.

`thoth profile set-shared ID on|off [--json]` marks a profile as one a human
also works in (their own terminal on the same account), so the quota points
measured on it are not a run's own. It is for the human operator only: it
exits 1 and writes nothing while `THOTH_RUN_ID` is set, and exits 1 for an
unknown profile; any value other than `on` or `off` is a usage error (exit 2).
`--json` prints `{"ok":true,"profile_id":ID,"shared":bool,"previous":bool}`;
`profile list --json` carries `shared` on every profile, and the plain
`profile list` line of a shared profile ends in ` shared`. The mark is stored
in `global.db` (schema version 2). From then on a run on that profile writes
`run_quota` with `reliable: false` and the reason `shared`; `thoth models`
leaves its points out of `quota_points` and `quota_runs`, and the `usage`
rows of `thoth recommend` (RJ-2) average them only when the group has no
reliable run at all, with `estimate_reliable: false`, so a shared account
still gets a number that is marked as not its own. Mark the profile you also
use yourself (typically `claude-a`); Thoth cannot see work done outside it.

Subscription tier (TIER-1). `global.db` schema 3 adds two columns to
`profiles`: `plan` (the account's subscription tier, lower case, for example
`max`, `pro` or `plus`) and `plan_seen_at` (when Thoth last saw it, RFC 3339
UTC); both are null until a tier is seen. Thoth stores the tier only where it
already writes the database and already has the tier in hand: Claude's
`subscriptionType` from the login check that `profile login`, `profile check`,
`dispatch`, `review start` and `spec review start` run anyway, and codex's
`planType` from the app-server answer that `profile usage --refresh` reads
(and, with `live-quota` on, the automatic refresh below). agy reports no tier. A check that fails, reports logged out, leaves the field
out or reports something that is not 1–32 of `a-z 0-9 . _ -` keeps the stored
tier. Storing is best effort: when the write fails, one line `warning: could
not store the plan of ID: ...` goes to stderr and the command's result and exit
code do not change. Schema 4 (MODELS-1) adds `models` and `models_seen_at` the
same way, for an antigravity profile's model list (see "Antigravity workers",
"The model"). The read-only commands (`profile usage` without
`--refresh`, `recommend`, `status`, `report`, `doctor`, `models`) never migrate
`global.db`; on a schema 2 database they work as before, with no tier, and on
a schema 3 one with no agy model list. One
exception: with `live-quota` on and at least one profile due for the automatic
refresh (below), `recommend` opens `global.db` for writing (which
migrates a schema 2 database; Breaking change (RJ-1): the launch commands no
longer do, since `--profile auto` is gone), store the new readings and, when a codex query
succeeds, its `planType`. What a
person reads writes the account as the id plus a bracket text: the tier with
its first letter upper-cased, else the profile's `--label` (control characters
removed, at most 32 characters), else just the id. The CLI uses half-width
brackets (`claude-a (Max)` in `profile list`, `profile usage`, `recommend`,
`status TASK` and the `dispatch` / `review start` / `spec review start`
lines); the report page and doctor's and setup's Traditional Chinese output use
full-width ones (`claude-a（Max）`). Commands to copy, warnings, reasons and
every `--json` id keep the bare id; `profile list`, `profile usage` and
`recommend` `--json` gain `plan` and `plan_label` (`profile list` also
`plan_seen_at`). Known limits: the report page shows this computer's stored
tier for an account id, so an account of another computer in the shared
records folder that has the same id shows this computer's tier, and one this
computer does not know shows just the id. And until a tier is stored, an
account that `profile login` created without `--label` shows the lower-case
label it saved automatically (for example `claude-a (max)`), because
`profile login` stores the raw subscription type as `account_label`; the next
`profile check`, `dispatch` or other check that stores the tier turns it into
`claude-a (Max)`.

Login name (new, PANEL-3). Schema 5 adds `login_name` and
`login_name_seen_at` to `profiles` the same way, so a person can tell
claude-a, b and c apart. The same five login checks store, when they report
logged in with an email, the part of the email before the first `@` (trimmed,
control characters removed, at most 32 characters) and the time; never the
whole email. No `@`, nothing before it, no email (codex and agy report none
today), a failed check or a logged-out one keeps the stored name; the next
check with a name overwrites it, so an account that changed login changes
name. A failed write is one line `warning: could not store the login name of
ID: ...` on stderr; nothing else changes. The read-only commands above still
never migrate; on a schema 4 database they work as before, with no names. The
name is written before the bracket text only in three places: doctor's and
setup's profile headings (`Profile claude-a (alice, Max)`, `帳號
claude-a（alice，Max）`; doctor uses the email its own check just saw, else the
stored name), the report page's account block (`claude-a（alice，Max）`; the
decision table there, which may hold other computers' rows for the same id,
does not), and the Thoth panel. `profile list --json` gains `login_name` and
`login_name_seen_at`; every other output, every `--json` id, `thoth models`
and the shared records folder stay without it.

Three read-only commands, added after Phase 2. None of them reads
credentials or calls a network service itself. `profile usage` without
`--refresh` and `report` only read: they use what Thoth or the harness already
wrote to disk, so every number is "as of the last run on that account". Two
things refresh: `profile usage --refresh`, and, when the `live-quota` switch is
on, `recommend`, which first runs the automatic refresh described below (on
`--refresh`, agy, codex and Claude Code connect to their providers themselves;
the automatic refresh asks only agy and codex; Thoth stores the readings). A window whose reset time has passed shows
`reset_since_observed: true` and counts as 0% when ranking.

- `thoth profile usage [ID] [--refresh] [--json]`: each profile's last known quota
  windows (`five_hour`, `seven_day`, ...), its live runs and its status.

    every registered repo. Each event's `windows` array holds every window

    "Claude Code refresh" below); for each window name, the newer of the

    observed later supplies `windows` (the rollout line's `timestamp` against

    codex_app_server`, rollout windows `codex_rollout`. `extra_buckets`

    `skipped_live_run` (codex and Claude Code, below) or `failed`; a profile failure

    stderr while it waits, so a chatty agy cannot stall on a full pipe; the
    reads end at the same deadline. A `failed` entry's `error` is the first of
    these that applies:

      found, could not be resolved, or did not start.

    - `not signed in`: stdout or stderr contains `Please sign in` (the
      `agy models` wording, assumed for `/usage`).
    - `exited with code N: ...`: agy exited with code N; the first 200
      characters of its stderr follow.
    - `not JSON`: stdout is not one JSON object.
    - `reported status S`: the top-level `status` is `S`, not `SUCCESS`.
    - `did not answer /usage; agy 1.1.11 or newer is required`:
      `command.name` is not `usage` or `command.data.groups` is not an array.
    - `no quota buckets`: no bucket has a non-empty `id` and a numeric
      `remaining_fraction`.

    Successful readings are `live_quota` events in `global.db`. Old agy may
    treat `/usage` as an ordinary prompt, so Thoth validates the response.
    Signed-out detection via `Please sign in` follows `agy models` and has not
    been verified against real `/usage`. Git Bash may path-convert `/usage`
    into a real prompt; use PowerShell/cmd or `MSYS_NO_PATHCONV=1`. Thoth passes
    argv directly and is unaffected.

    may change. A profile with a queued or running run is not asked
    (`skipped_live_run`, `error` null): the app-server opens its own files in
    `CODEX_HOME` and could clash with the worker. The general bucket is the

    ends codex and its child processes at once (`timed out`). Other failures:
    `could not run codex from THOTH_CODEX_BIN: ...`, `app-server answered

    the app-server exiting before it answers, or `no quota windows`.

    when it is `false`, at most 24 hours old and newer than the newest
    rollout reading, the profile is `exhausted` and `recommend` says
    `ordinary usage not allowed` (such a reply is stored even with no
    windows); `true` or `null` leave the state to the window percentages. A
    codex profile with no reading at all ranks with the reason "no quota
    reading yet; run `thoth profile usage --refresh`".
  - Claude Code refresh, under the same switch, happens only on a manual
    `profile usage --refresh`; the automatic refresh never starts claude

    official claude CLI (`THOTH_CLAUDE_BIN`, default `claude`) as `claude -p
    /usage --output-format stream-json --verbose --no-session-persistence
    --model haiku --strict-mcp-config`, in `$THOTH_HOME`, with stdin closed
    and `CLAUDE_CONFIG_DIR` set to the profile's config directory.
    `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN`
    are removed from claude's environment (never read), since any of them
    would make claude use that credential instead of the profile's login.
    claude signs in and talks to Anthropic itself; Thoth reads no login
    file and lists nothing in the config directory. `/usage` is a local
    command: it opens no model turn and uses no model quota;
    `--no-session-persistence` leaves no conversation record,
    `--strict-mcp-config` starts no MCP server, and `--model haiku` keeps the
    cost lowest should a version ever send `/usage` to the model (that answer
    is rejected, below). A profile with a queued or running run is not asked
    (`skipped_live_run`, `error` null): claude may renew its token in the same
    config directory, and the run's `rate_limit_event` is already recording
    readings.
    Thoth reads only stream-json lines that are JSON objects: the last line
    whose `type` is `result`, and the `usage_report` of the last `assistant`
    line that has one; from it only `rate_limits.limits[]`, each row's
    `kind`, `percent` (0-100) and `resets_at`. Kind `session` becomes
    `five_hour` and `weekly_all` becomes `seven_day`; any other kind is named
    `KIND:NAME` with NAME the row's `scope.model.display_name`, else
    `scope.surface.display_name` (control characters removed, trimmed, at
    most 32 characters), or just `KIND` when there is none. A row is skipped
    when it is not an object, its `kind` is not 1-32 lowercase ASCII letters,
    digits or `_`, its `percent` is not a number from 0 to 100 (it is not
    clamped), or its name repeats an earlier row's (the first is kept). A
    `resets_at` that is not an RFC 3339 string leaves the window without a
    reset time. The reading is stored as a `live_quota` event with only
    `source` (`claude_usage`) and `windows` (`name`, `used_percent`,
    `resets_at`); nothing else from claude's answer is kept. When the
    profile is shown or ranked, each window name takes the run-event reading
    only when it was observed strictly later than the live one, otherwise the
    live one. A claude-code profile with no reading at all ranks with the
    reason "no quota reading yet; run `thoth profile usage --refresh`".
    The same `THOTH_LIVE_QUOTA_TIMEOUT_MS` limit applies. A `failed`
    entry's `error` is one of:
    - `could not run claude from THOTH_CLAUDE_BIN: ...`: the executable was
      not found, could not be resolved, or did not start.
    - `timed out`: claude did not finish (or did not close its output) within
      the limit; Thoth ends claude and its child processes.
    - `claude reported an error: ...`: claude exited with a non-zero code
      and its last `result` line has `is_error` true (for example `Not logged
      in · Please run /login`); the first 200 characters of that line's
      `result` follow, or `no message`. claude reports most errors this way
      in stream-json mode, with stderr empty. The same error is reported when
      claude exits 0 with such a line.
    - `exited with code N: ...`: claude exited with code N and no such
      line; the first 200 characters of its stderr follow.
    - `claude printed no result line`.
    - `claude did not answer /usage locally; a model turn may have run`: the
      result line's `local_command` is not `usage`.
    - `claude's /usage answer has no usage_report; a newer Claude Code is
      needed (seen with 2.1.296)`.
    - `claude could not read the plan's usage (signed out, no subscription,
      or a login without the profile scope)`: `rate_limits` is null or
      missing.
    - `claude reported no usage rows`: `rate_limits.limits` is not an array.
    - `no quota windows`: no row could be read.
    - `failed to save quota event: ...`.

    Known limits: `usage_report` is not publicly documented and has been seen
    only with Claude Code 2.1.296. A Max account's answer has not been seen
    yet, and there is no real sample of a scoped weekly row (a kind other than
    `session` or `weekly_all`; every test so far had `scope` null), so those
    names follow the rule above, and two rows that give the same name keep
    only the first. The same model-only weekly limit may appear twice, under
    the run-event name (for example `seven_day_sonnet`) and the live name
    (for example `weekly_scoped:Sonnet`). Hooks and plugins in the account's
    settings may still run in `-p` mode (`--strict-mcp-config` only blocks
    MCP servers). To run `claude -p /usage` by hand in Git Bash, prefix it
    with `MSYS_NO_PATHCONV=1`, or Git Bash turns `/usage` into a path and it
    becomes a model turn; Thoth passes argv directly and is unaffected.

  Automatic live quota refresh (QR-1). With the `live-quota` switch on,
  `thoth recommend` first refreshes the readings that are due, then ranks
  (Breaking change (RJ-1): `dispatch`, `review start` and `spec review start`
  no longer refresh, since `--profile auto` is gone). Only agy and codex profiles are queried,
  and never a `logged_out` one. Claude Code profiles are never queried
  automatically, only on a manual `profile usage --refresh`: the usage
  endpoint answers 429 when asked too often, each query starts a whole
  claude, and a running claude already records readings from its events. A profile is due when its newest reading (the
  windows' `observed_at`, a rollout reading included, or the time of an
  "ordinary usage not allowed" reply) is more than 10 minutes old, or when it
  has none. Each due profile is queried once, one after another, in
  `profile_id` order, with the same query as `--refresh`. Thoth waits for an
  answer at most the smaller of `THOTH_LIVE_QUOTA_TIMEOUT_MS` and 10 seconds;
  after codex answers it gets up to 5 more seconds to exit on its own. A codex
  profile with a queued or running run is `skipped_live_run`. A refresh never
  blocks the command: a failed, timed-out or skipped profile ranks with the
  reading stored before, and each failure gives one warning, either
  `live quota refresh for ID failed: ERROR; ranking with the previous reading`
  or, for a profile with no reading, `live quota refresh for ID failed: ERROR;
  ranking without a quota reading`. Nothing is refreshed when the switch is
  off or `THOTH_RUN_ID` is set; when nothing is due, no write connection is
  opened. Neither query opens a conversation or uses model quota. `recommend`
  reports what happened as `live_quota_refresh`: `{"enabled": bool,
  "skipped": null | "off" | "worker", "results": [{"profile_id", "status",
  "error"}]}`, where `status` is `refreshed`, `failed` or `skipped_live_run`
  and only due profiles are listed.
- `thoth recommend --role implementer|reviewer [--task TASK] [--model MODEL] [--tables] [--json]`:
  ranks profiles and says why. With `live-quota` on it first runs the
  automatic refresh above, so it may then start agy or codex and write
  readings; `--json` reports it as `live_quota_refresh` and each failure is a
  `warning: ` line on stderr. A profile is eligible only when active (or a
  rate-limited profile has a known reset after its latest rate-limit event)
  and not exhausted by an unreset 95% window. Readings older than 24 hours rank as `unknown`, after fresh `ok`
  readings; exhausted readings remain exhausted regardless of age. Ranking is
  reviewer cross-provider preference, no live runs, `ok` before `unknown`,
  lower fresh peak, then profile ID. Breaking change (RJ-1): a used-up profile
  no longer holds back its same-harness or same-provider siblings (the
  `same_provider_rotation` setting is gone); each profile is judged on its own
  facts. JSON candidates additionally report `quota_state`,
  `peak_percent`, `newest_observed_at` and `recovered` (`held` is gone). It
  lists facts only and never changes profile status; nothing dispatches by it
  (see "Automatic dispatch").
  Agy quota is evaluated per model group. Without a model, Thoth selects the
  non-exhausted group with the lowest unreset peak (response order breaks ties;
  if all are exhausted, the first). `--model` matches agy's descriptions;
  zero or multiple matches use the same best-group rule. No mapping is hard-coded.
- `thoth report [--out FILE] [--open [--section ID]] [--json]`: writes one
  self-contained HTML page in Traditional Chinese for the human owner, by
  default `$THOTH_HOME/report.html`. It shows an overview line, every
  account's quota and work (extra codex buckets muted under the account's
  own windows), the dispatch decision table (one row per model, account,
  task type and effort: runs, reviewed runs, pass rate over PASS+REJECT,
  average tokens, average quota points for the five-hour and the weekly
  window over reliable runs only, and the computers the runs came from),
  every launch's choice and outcome (Breaking change, RJ-3: task with role,
  computer and start time; the chosen account, model and effort; task type
  and difficulty; the reason, 沒寫 when none was given; the outcome; newest
  30), and each score source's fetch date,
  marked 過期 at 48 hours, every task by repo (open ones first; at most 30
  closed ones per repo), and what REJECT / UNVERIFIED reviews caught. Times
  are in the machine's time zone. `--open` opens it in the default browser;
  failing to open is a warning, not an error. `--section decision-table`
  with `--open` opens the page at that section (a `file://` URL with a
  fragment; `rundll32 url.dll,FileProtocolHandler` on Windows, `xdg-open`
  elsewhere).

  Once `$THOTH_HOME/report.html` exists, it is rewritten automatically at
  the end of every command that changes a task or run status (`task create`,
  `task update-spec`, `task close`, `dispatch`, `resume`, `cancel`, `submit`,
  `review start`, `review record`) and by the runner after it settles a run.
  The rewrite is best effort: it never creates the file, prints nothing, and
  cannot change the command's exit code or output. `thoth hook` never does
  it (the hook opens no database), and neither do read-only commands. A page
  written elsewhere with `--out` is not rewritten.

**Quota groups on a parked antigravity profile.** agy's quota comes in groups
(for example `Gemini Models` and `Claude and GPT models`). When an antigravity
run stops on quota, the runner looks up the group its model belongs to in the
profile's newest `live_quota` reading and records it as `quota_group` in the
`rate_limited` quota event and the `quota_exceeded` event. The profile is still
marked `rate_limited`, but `recommend --json` and `profile usage --json` report
that group as `parked_group` on the profile (null for a profile that is not
parked, or when no group was recorded), and a profile parked for one group
stays eligible for a model of another group (reason `parked for quota group G;
the selected group H is unaffected`), so a dispatch with such a model runs
without the `rate_limited` warning and leaves the status as it is. Whether the
parked group has reset is judged from that group's windows only. Without a
`live_quota` reading (nobody ran `profile usage --refresh`), `quota_group` is
null and the whole profile is parked, as before.

A `logged_out` profile (see docs/phase1/usage.md "Quota interruptions") is never
eligible; its reason is `status logged_out; run `thoth profile login ID``.

**The status page.** `thoth report` labels a `logged_out` account `已登出` and
a parked antigravity account with its group, `撞到額度（GROUP）` (still
`撞到額度` when no group is known). Under every `interrupted` or `failed` task it
prints the next step for the task's newest run, by its reason: quota, login,
temporary problem, crash, timeout or a plain failure, with the `thoth resume`
or `thoth profile login` command to run, or "重新派工" when there is no session
to resume.

## Automatic dispatch

Breaking change (RJ-1). Thoth only records and dispatches; it no longer picks
the account, the model or the effort. The commander gives them, using `thoth
recommend --role ROLE --task TASK` to see each account's quota:

```
thoth dispatch TASK --profile claude-b --model sonnet --effort medium --json
thoth review start TASK --profile codex-a --model gpt-5.6-luna --effort high --json
thoth spec review start TASK --profile codex-a --model gpt-5.6-luna --effort high --json
```

**`auto` is refused.** `--profile auto`, `--model auto` and `--effort auto`
(the last two in any letter case, with spaces around) make `dispatch`, `review
start` and `spec review start` exit 1 before anything else is checked or
written; the message says the value was removed, that Thoth no longer picks
for you, and names `thoth recommend --role ROLE --task TASK`. `auto` stays
reserved: `thoth profile add` refuses it in any letter case (`auto`, `Auto`,
`AUTO`).

**Model and effort are yours.** The first launch of an attempt needs
`--model` and `--effort`; `--effort` can be left out only when the model has
no effort setting (haiku; then nothing is sent) or (AGY-1) when it is an agy
model whose name ends in its level (`gemini-3.8-flash-high`; then that level
is recorded and no flag is sent, see "Effort"). A reroute in the same attempt keeps the previous run's model and
requested effort for whatever is left out: for `dispatch` the newest
implementer run of this attempt (a rework after a REJECT is a new attempt, so
it keeps nothing), for `review start` the newest reviewer run of the attempt
under review; `spec review start` keeps nothing and needs them every time.
`warnings` then says what was kept from which run. A model kept for a profile
of another harness than the previous run's (a codex model rerouted to a
Claude profile, say) is refused, naming `--model`. A missing flag is refused
before anything is written, naming the missing flag(s). There is no default
model, no rework step-up, no same-provider reviewer tier and no `treated as`
warning any more.

**What is recorded.** Every new run's spec has `launch` with exactly
`effort_requested`, `effort` and `effort_note` (older runs keep their extra
keys and are still read). `--json` no longer has `auto`, `auto_reasons` or
`live_quota_refresh`, no `auto_pick` event is written, and the launch commands
no longer refresh live quota or read the score caches.

**Labels.** Task specs may carry `task_type` (`code`, `research`, `review`,
`docs`, `mechanical`) and `difficulty` (`low`, `normal`, `high`). Any other
value is refused by `task create` and `task update-spec`; null is the same as
leaving the key out. Nothing picks by them any more; they are recorded as
written in `launch_choice`.

**Every launch is a record.** Every `dispatch`, `review start` and `spec review
start` writes one `launch_choice` event: the role and source, the task's
`task_type`, `difficulty` (null when the spec has none) and `risk`, what was
launched (profile, model, the effort requested and the effort sent), whether
the model and the effort were kept from the previous run of the same attempt
(`inherited`) and which run that is (`previous_run`), the `--reason` given, if
any, and whether `require-reason` was on.

`--reason TEXT` (MCP: `reason`) says why this profile, model and effort were
chosen; it is trimmed, an empty one is refused, and it is stored in the event.
With the switch `require-reason` on (see "Settings"; off by default), every
launch without `--reason` is refused before anything is written, a reroute in
the same attempt included; the message names `--reason` and says a human can
run `thoth config set require-reason off`. There are no exemptions.

**A parked account that has recovered.** If a dispatch, review start or spec
review start launches on a profile marked `rate_limited` whose quota window
has reset since, the profile is set back to `active` (with a `window_reset`
quota event, `source: auto`) once the run has been written, and no
`rate_limited` warning is given; if the launch fails first, nothing changes. Likewise a named dispatch or review start whose auth check
passes on a `logged_out` profile sets it back to `active` once the run has been
written, with a `login_restored` quota event (`source` `dispatch` or
`review_start`, `task_id`, `run_id`).

**A run that hits its quota.** Thoth never moves a run to another account. A
run stopped by quota ends `interrupted` with reason `quota` (the profile is
parked as `rate_limited`, the task `interrupted`), and `thoth status TASK`
says what to do: `quota used up on PROFILE; dispatch again with a profile that
still has quota: thoth dispatch TASK --profile OTHER --model MODEL --effort
LEVEL --reason TEXT (profiles with quota now: …); do not wait for PROFILE`
(`start the review again with the next reviewer in your order that still has
quota` / `start the spec review again with …` for a reviewer or spec reviewer
run). Breaking change (RJ-3): it no longer suggests waiting for the profile's
reset or resuming the run, with or without a session; `--reason TEXT` is for
the commander's reason. `status TASK --json` lists those profiles in each such
run's `profiles_with_quota`. Breaking change (RJ-1): the runner's handover on
quota, which used to continue a `--profile auto` run on another profile, is
gone.

## Handoff to another worker

**When.** A `dispatch` writes a handoff when the task is `interrupted` or
`failed` and the newest implementer run of the same attempt that actually
started ended `interrupted` or `failed` (quota, timeout, crash). The profile
does not matter: sending the task back to the same profile, for example after
its window reset, is a handoff too, and so is a re-dispatch to another account
(`thoth status TASK` lists the ones that still have quota). No other entry status writes one (`queued`, `in_review`,
`unverified`, `reject`), nor does a task set to `interrupted` by hand with no
such run. `thoth resume` never writes one. Breaking change (RJ-1): the
runner's handover on quota, which wrote one too, is gone. The new run's spec keeps the
previous run's `rework` and `reroute`, so its prompt still lists why the
attempt was sent back.

**What.** A Markdown file, `.agent/handoff.md` in the worktree, with a copy as
`handoff.md` in the new run's directory. Sections: `# Handoff` (task, attempt);
`## Why` (the previous run's id, profile, harness, model, status,
`interrupted_reason` and `ended_at`, and the new run's profile, harness and
model); `## Worktree state` (branch, base commit, then the output of
`git log --oneline <base>..HEAD` up to 50 lines, `git status --short` and
`git diff --stat HEAD` up to 200 lines each; a longer output ends with
`... (K more lines)`, and a git command that fails is written as
`(unavailable: <error>)`); `## Evidence so far` (the attempt's `command`
evidence, one line per code: `E001 exit=0 <command>`, `exit=-` when the exit
code is unknown, the newest 100 when there are more, after a
`... (K earlier rows)` line); `## What to do` (check what is done against the
acceptance criteria, finish without starting over, re-run the checks, write a
new `.agent/result.json`).

Everything in it comes from Thoth's database and from git. The previous
worker's conversation, stream, stderr, summary and result.json are not read.
Command labels and commit titles are listed as recorded, with line breaks
turned into spaces; they are text the previous worker wrote.

**Prompt and records.** The new worker's prompt gets a section
`## Continuing an interrupted run` naming the previous run, its reason and the
path; the file's content is not copied into the prompt. The run's spec gets a
`handoff` object (`previous_run`, `reason`, `from_profile`, `from_harness`,
`path`), a `handoff_written` event records the file's `sha256` and `bytes`, and
`dispatch --json` has `handoff` (`previous_run`, `reason`, `cross_provider`,
`path`; `null` when the dispatch was not a handoff). `cross_provider` is true
only when both the provider label and the harness differ. `.agent/` is
excluded from git, so the file never reaches the candidate commit.

**Failures.** If either copy cannot be written, `dispatch` exits 1 and writes
no run and no event. If the dispatch is refused after the file was written
(another run of the task is live), the worktree copy is removed again.

**Stale files.** A dispatch that is not a handoff removes a
`.agent/handoff.md` an earlier handoff left in the worktree, so the next worker
never reads an out-of-date one; if it cannot, dispatch goes on with a warning.

**No resume after a handoff.** Once a later run of the same attempt has
started, `thoth resume` refuses the earlier run (exit 1, naming the later run
and saying it was `continued`): the old conversation would carry on over the
newer run's changes. Dispatch the task again instead.

## Secret masking

Thoth masks secrets at the moment content leaves it, not when it stores it
(RD-1). Blobs keep their sha256, and a diff has to stay the diff git produced,
so the stored blobs, database rows and logs are kept exactly as they were; only
what an exit hands over is masked. With nothing to mask, every output is byte
for byte what it was before.

Two kinds of secret are recognised:

- seven key formats, by prefix and length: `anthropic-key` (`sk-ant-`),
  `openai-key` (`sk-`), `google-api-key` (`AIza`), `github-token` (`ghp_`,
  `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`), `gitlab-token` (`glpat-`),
  `aws-access-key-id` (`AKIA`, `ASIA`) and `private-key` (a block from the
  line that starts with `-----BEGIN`, names a `PRIVATE KEY` and ends in five
  dashes, through its `-----END` line, or to the end of the text when that
  line is missing; extra dashes before the BEGIN line, as a diff that deletes
  a key file has, are allowed); a `-` or `+` right at the start of a line (a
  diff's deleted or added line) does not hide a key format after it, and a
  format that runs on into an exact value stops where the value starts;
- exact values: the value of every environment variable of the thoth process
  whose name contains `KEY`, `TOKEN`, `SECRET` or `PASSWORD` (kind
  `env:NAME`), and the keys stored in `$THOTH_HOME/secrets.json` (kind
  `thoth:aistupidlevel-api-key`, `thoth:artificialanalysis-api-key`, or
  `thoth:secrets.json` for any other key), each also in its JSON-escaped form.
  A value shorter than 8 characters after trimming, or made only of digits, is
  not matched: it would mask ordinary text.

Each secret becomes `[redacted:KIND]`. KIND says which kind of secret it was
and nothing about the value: no piece of it, no length.

The exits that mask, so far:

- `thoth evidence show` (content, label and detail; the whole blob is masked
  before the first `--bytes` are taken);
- `thoth review packet` (stdout, `--out` and `--json`; a command's last 15
  lines are taken after its whole output was masked);
- the `.agent/review-input/` files of a codex or antigravity reviewer
  (`packet.md` and `evidence/<CODE>.txt`);
- `.agent/evidence-index.json` (each `label`);
- the prompt the runner hands every worker and reviewer (the run directory's
  `prompt.txt` is the same text); each value the prompt embeds is masked on
  its own first, so a key block without its END line cannot eat the
  prompt's later sections;
- a spec reviewer's `.agent/spec-review-input/spec.json`, and the author
  check's `proposed.json` and `edits.json` (their object keys and string
  values are masked (keys since RD-4), so they stay valid JSON);
- `.agent/handoff.md` (and the run directory's copy);
- (RD-3) the document every command prints on stdout, JSON and human alike,
  and the error message `--json` and the human form print on stderr; so
  `status`, `events`, `wait`, `task show`, `review show`, `config`, `doctor`
  and the rest are covered, and so is everything the plugin panel and the
  commander read from them;
- (RD-3) `thoth transcript` (each line is masked before a step's text is cut
  to 300 characters);
- (RD-3) MCP tool results, and the large results saved under `mcp/out`;
- (RD-3) `report.html` (the whole page, matching each exact value also in its
  HTML-escaped form; `--out` too);
- (RD-3) the file `thoth records export` writes to the shared records folder
  (a line with nothing to mask keeps its field order byte for byte);
- (RD-4) every other line thoth itself writes to stderr: a command-line parse
  error (with the arguments it quotes), `warning:` lines, notes such as
  `wrote FILE (N bytes)`, and what `thoth mcp` writes there.

The RD-3 exits and the RD-4 stderr lines only leave the markers and never
write `secret_redacted`: the plugin panel runs `status`, `events` and
`transcript` every few seconds.

Keys (RD-4). Every JSON exit masks each object's keys as well as its string
values, at any depth. A masked key keeps its value and the output stays valid
JSON. When two keys of one object mask to the same text, the second and later
ones, in the order of their original names, get `#2`, `#3`, and so on (the
first number that names no other key of the object). An exit that writes
`secret_redacted` counts a masked key in its `kinds`.

Cut lines (RD-4). A human line that cuts text when it is printed, such as
`thoth task result`'s source quotes (120 characters) and `thoth spec review
show`'s `after` preview (60 characters), masks the whole text before cutting
it, as `thoth transcript` does. The cut may fall inside a marker, but never
leaves a piece of the secret.

Workers (RD-3). A worker, reviewer or spec reviewer starts without the two
score key variables (`AISTUPIDLEVEL_API_KEY`, `ARTIFICIALANALYSIS_API_KEY`)
and without any other variable the masking takes for a secret: a name with
`KEY`, `TOKEN`, `SECRET` or `PASSWORD` and a value it would match, or a value
holding one of the seven formats. (RD-4) Nor does it get a variable, whatever
its name, whose whole value is a known exact value (an environment value the
masking takes by its name, or a value in `secrets.json`); a variable that only
contains one, such as PATH, still reaches it. Every other variable still
reaches it, and the runner itself keeps them all, so it can mask with them.

Specs (RD-3). `thoth task create` and `thoth task update-spec` refuse a spec
in which any line or any string value holds what looks like a secret, and
`task create` also refuses such a `--title`: exit 1, nothing stored, no event.
(RD-4) So does any object key that holds one, at any depth: keys are checked
as parsed, so a `\u` escape in the file does not hide one, and the field path
shows that key as its marker. The message starts with `refusing: the spec
contains what looks like a secret` (or `refusing: the title contains what
looks like a secret`) and names only the kinds, the field paths (`goal`,
`acceptance_criteria[1]`) and the line numbers, never the value. Refer to an
environment variable by its name instead.

The exits that hand content over once (`evidence show`, `review packet`, a
reviewer's input, a prompt, a spec reviewer's input, a handoff file) record a
`secret_redacted` event when they masked something: detail `exit`, `kinds`
(kind to count) and `evidence` (the codes involved), never the content. The
evidence index, which the runner rewrites every second, only carries the
markers. A failed write of the event does not stop `evidence show` or
`review packet`: they print their masked output, exit 0 and add one
`warning: could not record secret_redacted: …` line on stderr. For a prompt
and a spec reviewer's input, a failed write only goes to `runner-error.log`
and the worker is started anyway; a handoff's event is written in the same
transaction as `handoff_written`.

The Discord discussion room is not implemented yet; when it is, every message
it sends must go through the same masking (`src/redact.rs`).

Known limits:

- a secret already cut when it was stored (only part of it in the blob) is not
  recognised, nor is a value stored encoded (base64, URL encoding);
- only the environment variables this process sees count: a variable set in
  the Windows registry after the shell started is not known to it;
- reading local files directly (`runner-error.log`, `stream.jsonl`, the
  `blob_path` a row names, a worktree) does not go through Thoth and is not
  masked;
- values shorter than 8 characters or made only of digits are not matched;
- `config list`, `doctor` and `models --refresh` say inside a run that
  "secrets.json is not read while THOTH_RUN_ID is set": its values are not
  used there, but masking still reads the file;
- a report field holding an unterminated private-key header masks the rest of
  the page into one marker (over-masking, no leak);
- inside a run the masker sees only the run's stripped environment, so a
  value that exists only in the commander's environment is caught there by
  the formats alone; `thoth config set-secret` is the way to have it masked
  everywhere.

## Settings

`thoth config list [--json]`, `thoth config get KEY [--json]`, `thoth config set KEY VALUE [--json]` and `thoth config unset KEY [--json]` manage 16 settings: the three switches `live-quota`, `scores-auto-refresh` and `require-reason` (default off; Breaking change (RJ-1): `same-provider-rotation` is gone: a `same_provider_rotation` left in config.json has no effect and is not reported as unknown, and `config get`, `set` or `unset` of it exits 1 saying it was removed), the screen `language`, the three CLI paths `claude-bin`, `codex-bin` and `agy-bin`, `live-quota-timeout-ms`, the three score addresses `scores-url`, `aa-url` and (RJ-2) `arena-url` (`THOTH_ARENA_URL`, default `https://huggingface.co`: the Hugging Face Hub the Agent Arena dataset is fetched from), the two shared-records settings `machine-name` (default: this computer's host name, sanitised to `A-Z a-z 0-9 . _ -`) and `records-dir` (an absolute path; default `unset`), one that can only be read, `home` (`THOTH_HOME`), and the two API keys, stored with `thoth config set-secret KEY` (the value is typed at a hidden prompt or piped on stdin, never given on the command line) into `$THOTH_HOME/secrets.json`, removed with `thoth config unset-secret KEY`, and shown everywhere only as set or unset. The environment variables of the shared-records settings are `THOTH_MACHINE_NAME` and `THOTH_RECORDS_DIR`. Stored values live in `$THOTH_HOME/config.json`; an environment variable beats config.json, which beats the default, and `config list` shows each value's source and, at the end, what is kept elsewhere (profiles, checks). Setting a switch on prints its behavior and the relevant terms reminder. `config list` and `config get` are read-only. Agents must not change these settings themselves; ask the human operator to run `thoth config set` or `thoth config unset` (`thoth config set-secret` or `thoth config unset-secret` for the API keys).
`live-quota` permits Thoth to query official Antigravity agy and the official
codex CLI's app-server at two times: `profile usage --refresh` calls, which
also ask Claude Code's own `/usage` command, and the automatic refresh that
`recommend` runs before ranking, only for agy
and codex readings more than 10 minutes old (see
"Automatic live quota refresh"). It does not poll, query in the background, or
let Thoth read login material.
`scores-auto-refresh` lets the commands that read external scores (`models`,
`report` and, since RJ-2, `recommend`) refresh the score caches themselves,
at most once a day (see "Automatic refresh" below). A keyed source is
contacted only when its key is set and its cache is missing or at least 24
hours old; Agent Arena needs no key and is contacted (huggingface.co) on the
same schedule; a failed refresh keeps the old cache and prints a warning.
`require-reason` makes every `dispatch`, `review start` and `spec review
start` need `--reason` (Breaking change (RJ-1): not only a launch that differs
from a recommendation; see "Automatic dispatch"). Agents must not turn it off
themselves.

Secrets. `thoth config set-secret aistupidlevel-api-key` and `thoth config
set-secret artificialanalysis-api-key` keep the two score API keys in
`$THOTH_HOME/secrets.json`, in clear text: on Linux the file is created
readable by you only (mode 0600, repaired on every write), on Windows it
inherits the state directory's ACL, which is the same exposure as keeping the
key in your user environment variables. A worker starts with these two
variables taken out of its environment (RD-3), but a worker running as the
same OS user can still open secrets.json, or read your user-level
environment settings, directly; Thoth cannot stop that. The
environment variable always wins over the stored key, and a blank variable
counts as not set. While THOTH_RUN_ID is set (inside a run) secrets.json is
not used: `config list`, `config get`, `doctor` and `models --refresh`
see the environment only, and `set-secret`/`unset-secret` are refused (the
file is read only to mask its values in output; see "Secret masking"). Under
Git Bash (mintty) stdin looks like a terminal but is not a Windows console,
so the hidden prompt is refused: type the command in a PowerShell or cmd
window instead, or put the key alone in a file and run
`thoth config set-secret KEY < FILE`, then delete the file. Ctrl+C in the
middle of the hidden prompt may leave the terminal's echo switched off; run
`stty echo` or open a new window.

## Model inventory and scores

`thoth models [--refresh] [--json]` lists the models available to every
registered profile. Codex models come from the profile's `models_cache.json`;
Claude Code uses the aliases `haiku`, `sonnet`, `opus`, and `fable`; an
antigravity profile's models (`models_source` `agy_models`, MODELS-1) are the
list its last login check read from `agy models` and stored (see "Antigravity
workers", "The model"). Each profile says when its list was read
(`models_seen_at`, and the line `  models read at TIME`): for agy the time of
that login check, for codex the cache's own `fetched_at` (else the file's
modification time) re-formatted in UTC whatever offset codex wrote it in,
never for Claude. An agy profile with no stored list has
no models and the note `no model list stored yet; run `thoth profile check
ID``; one whose list is a day old or more has the note `model list read N
hours ago; run `thoth profile check ID` to read it again`. Each model also
says whether a run proved the account cannot use it (`unavailable`: null, or
`seen_at`, `reason`, `run_id`; the line ends ` — unavailable since TIME:
REASON`): a Claude run whose result line says `api_error`
`model_requires_usage_credits` (a Pro account asked for Fable) ends `failed`
with `error_text` `model unavailable on this account: …` (not a quota stop:
the profile is not parked, no `rate_limited` or `quota_exceeded` is written,
no login check runs), and the runner writes a `model_unavailable` quota event
(`model`, `run_id`, `task_id`, `api_error`, `api_error_code`, `error_text`,
`plan`) and a `model_unavailable` run event. While the newest such record for
that model matches the profile's current plan and no later `model_forgotten`
exists, `dispatch`, `review start`, `spec review start` and `resume` refuse
that model on that profile, naming the models it can still use and `thoth
profile forget-model ID MODEL`, which writes the `model_forgotten` event; a
plan the next login check stores differently clears it by itself. The command
also totals each model's Thoth implementer runs, reviewed runs, PASS reviews,
and REJECT reviews across registered repositories. Each model also has the new
`thoth_breakdown` array, grouped by `effort`, `task_type`, and `difficulty`.
The effort is read from `runs.spec` `launch.effort`; the task type and difficulty
are read from the task's `tasks.spec`. Its entries additionally contain
`implementer_runs`, `completed`, `reviewed`, `pass`, `reject`, `input_tokens`,
`output_tokens`, `quota_points`, and `quota_runs`; quota points come from numeric
`detail.points` in each run's latest `run_quota` event. Since DT-1 the entries
also contain `cache_read_tokens`, `cache_write_tokens`, `reasoning_tokens` and
`total_tokens` (summed like `input_tokens`: a NULL counts as 0; see "Token
kinds"), `quota_points_weekly` (the sum of `detail.seven_day.points`, null when
no run has one) with `quota_runs_weekly`, and `quota_runs_unreliable`.
`quota_points` and `quota_runs` only count runs whose latest `run_quota` event
is reliable (it has no `reliable` key, as before DT-1, or `reliable` is true);
`quota_runs_unreliable` counts the runs whose latest event says
`reliable: false`, numbers or not (Breaking change (RJ-1): `recommend` no
longer works out a quota cost per candidate; since RJ-2 its `usage` rows
carry the average points per run of each account, model, effort and task
type instead, see "Quota, recommendations and the status page").
`thoth_breakdown` still counts implementer runs only: a
reviewer run's `run_quota` is recorded for later use. A repository whose
`state.db` has not been opened by this version yet has no token-kind columns;
they read as 0 and nothing fails.

Breaking change (RJ-3): the PASS and REJECT counts are for the human only.
The human output prints them (`PASS N REJECT M` on each model line and each
labelled breakdown line), and the report page shows the pass rate; the JSON
(and MCP `thoth_models`, the same document) has none of them: a model's
`thoth` is only `implementer_runs` and `reviewed`, a `thoth_breakdown` entry
has no `pass` or `reject`, and `decision_table` has no pass rate and no
verdict (see "Quota, recommendations and the status page"). The commander
judges models by the external tables, not by Thoth's own record.

With `records-dir` set, `thoth models` also reads every other computer's
`NAME.jsonl` in that folder (see "Shared records folder (DT-3)"): this
computer's own file is skipped; a line whose `run_id` is already in this
computer's databases is skipped; a line whose profile id is not registered here
is skipped; a line counts toward the local profile with the same id and the
same model. The `thoth` and `thoth_breakdown` totals include those lines, each
`thoth_breakdown` entry has `machines` (the computers whose runs are in it,
sorted), and the JSON has a top-level `records` object with `dir` (the folder or
null), `machine` (this computer's name), `files` (one `{name, machine, lines,
skipped_lines}` per other file) and `error` (null, or why the folder could not
be read). The remote reviewed count (and the pass and reject counts of the
human output) use each run's latest verdict only. Without `records-dir`
nothing else changes.

External scores live only in `$THOTH_HOME/model-scores.json`. Ordinary
`thoth models` and `thoth report` calls read that cache and never use the
network, unless `scores-auto-refresh` is on (see "Automatic refresh" below).
Scores are from [AI Stupid Level](https://aistupidlevel.info), and all
terminal, JSON, and HTML displays identify and link that source.

`thoth models --refresh` refreshes AI Stupid Level with a free data key in
`AISTUPIDLEVEL_API_KEY` or stored with `thoth config set-secret
aistupidlevel-api-key` (sign in and create one on the
[Data keys page](https://aistupidlevel.info/account/data-keys)); without any
key it still exits 0 and fetches Agent Arena (RJ-2; it used to exit 1), and
prints a note on stderr that the two keyed sources were skipped, naming both
environment variables and `thoth config set-secret`. The note adds that
secrets.json is not read while `THOTH_RUN_ID` is set, or, when secrets.json
cannot be used, which file it is and to see `thoth config list`. It makes one
authenticated request to
`GET https://aistupidlevel.info/api/v1/models?period=latest&sortBy=combined`.
`THOTH_SCORES_URL` may replace that complete URL. A valid response must have
`success: true` and an array-valued `data`; only then is the cache replaced.
Because scores update roughly hourly and the service requires client caching,
a cache fetched less than 60 minutes ago is reused. Delete `model-scores.json`
to force another request.

A Claude alias is looked up under the model name its newest `harness_init`
event reported on that profile, with a trailing `-YYYYMMDD` removed (RJ-2:
there is no fixed alias table any more; an alias that has not run on the
profile has no `score_name`, no score and no Artificial Analysis rows until it
does). Codex slugs map exactly. Score objects contain `current`, `trend`,
`status`, `confidence_lower`, `confidence_upper`, and `observed_at`. A model is
marked as possibly degraded when `status` is not `good` or `trend` is `down`.

Artificial Analysis is an independent second source. With
`ARTIFICIALANALYSIS_API_KEY`, `--refresh` pages through the free Data API at
`GET https://artificialanalysis.ai/api/v2/language/models/free?page=N` (or the
complete page-prefix replacement in `THOTH_AA_URL`). The free tier permits 100
requests per 24 hours, so a valid `$THOTH_HOME/model-scores-aa.json` cache less
than 360 minutes old is reused; deleting that file forces a fetch. All pages
must be valid objects with array-valued `data`, and the cache is replaced only
after every page succeeds. The data remains local and must not be forwarded.

AA names are normalized by lowercasing, collapsing non-ASCII-alphanumeric runs
to `-`, and trimming `-`. A final parenthesized phrase is a variant: its first
recognized `minimal`, `low`, `medium`, `high`, `xhigh`, `max`, or `ultra` word
is the effort. Codex compares its slug. Claude compares the latest
`harness_init.detail.model` used by that alias (with a final `-YYYYMMDD`
removed); an alias without a run matches nothing (RJ-2).
Each model's added `aa` value is null or contains effort-sorted `rows` with
`name`, `effort`, the three index fields, and both per-million-token price
fields. The added top-level `external.artificial_analysis` contains `source`,
`cache`, and `unmatched_profile_models`. Terminal, JSON, and report output
always attributes these values to [Artificial Analysis](https://artificialanalysis.ai).

**Agent Arena (RJ-2).** The third source is the Hugging Face dataset
[lmarena-ai/leaderboard-dataset](https://huggingface.co/datasets/lmarena-ai/leaderboard-dataset)
(CC BY 4.0), the agent leaderboard with its `agent_*` subset boards. It
needs no key. `thoth models --refresh` always fetches it, and the automatic
refresh does when `$THOTH_HOME/model-scores-arena.json` is missing, of
another schema or 24 hours old, with the whole fetch (index plus every board)
limited to 20 seconds: each curl gets what is left, rounded up, and under a
second nothing more is fetched (the next call tries again). The index at
`BASE/api/datasets/lmarena-ai/leaderboard-dataset` (BASE is `arena-url`,
default `https://huggingface.co`) gives the dataset `sha` and its files; the
boards are `agent` plus every `agent_*` folder with a
`latest-00000-of-00001.parquet`, all downloaded at that `sha` from
`BASE/datasets/lmarena-ai/leaderboard-dataset/resolve/SHA/BOARD/latest-00000-of-00001.parquet`
(curl follows the Hub's redirect to its CDN here; the keyed sources never
follow one, so a key cannot reach another host). An unchanged `sha` downloads
nothing and only moves `fetched_at`. The parquet files are read with the
`parquet` crate (SNAPPY only, no arrow): `model_name`, `organization`,
`score` and `rank` must be there, the other kept columns may be null, extra
columns are ignored. The cache (`schema` `agent-arena-v1`) keeps every row of
every board, the `sha`, the source with its license link, and each board's
publish date; it is replaced whole only when every board was read, and any
failure leaves it untouched. An Agent Arena failure never changes an exit
code (`--refresh` prints `warning: Agent Arena refresh failed: …`). `thoth
models` shows it as `external.agent_arena` (`source`, `cache` with `sha`,
`boards`; no rows) and the plain line `scores: Agent Arena URL (CC BY 4.0)`
(or a `stale:` line without a key name); the filtered rows are what `thoth
recommend` sends. The cache never enters the records folder, an event or
evidence.

**Automatic refresh.** With `thoth config set scores-auto-refresh on`, the
commands that are about to read external scores first refresh each source whose
cache is missing or at least 24 hours old: the two keyed sources only when
their key (`AISTUPIDLEVEL_API_KEY`, `ARTIFICIALANALYSIS_API_KEY`) is set (a
source without a key is never contacted), Agent Arena always. The commands
are `thoth models` without `--refresh`, `thoth report` and (RJ-2) `thoth
recommend`, with or without `--task` (`dispatch`, `review start` and `spec
review start` read no scores, so they never fetch). Each keyed request gives
up after 8 seconds (the manual `--refresh` allows 20); Agent Arena's whole
fetch shares 20 seconds. A lock file `.model-scores.refresh.lock` in
`$THOTH_HOME` keeps two processes from fetching at once; a lock whose
modification time is more than 120 seconds old is replaced (its content is never
read), and a process that finds a fresh lock skips the refresh. The lock is best
effort: if two processes reclaim the same expired lock at the same moment, both
may fetch, and the second may get a rate-limit warning. When a refresh fails, the old cache is used unchanged and exactly one line,
`warning: automatic score refresh failed: ...`, goes to stderr; the exit code
and the JSON on stdout do not change. Nothing is fetched inside a worker
(`THOTH_RUN_ID` set), in the runner, or when a status change rewrites the
report. The MCP
server runs each tool as a child `thoth` process, so its tools refresh the same
way when the server's environment has the key, but it does not forward stderr:
read `auto_refresh` and `cache.stale` in the `thoth_models` result instead.

**Staleness.** `thoth models --json` adds `age_hours` (whole hours since
`fetched_at`, or null with no cache) and `stale` to `cache`, to
`external.artificial_analysis.cache` and to `external.agent_arena.cache`. `stale` is true when there is no cache or
it is 48 hours old or more. The top-level `auto_refresh` object has `enabled`,
`skipped` (null, or `off`, `worker`, `busy`, `manual`), `attempted` and
`refreshed` (source names), and `failed` (`source`, `error`). Plain output
prints one `stale:` line per stale source with the fix, and an `auto-refresh:`
line naming the sources refreshed by this call.

Caches without `schema: "aistupidlevel-v1"` are treated as unavailable: scores
are null and plain output names the stale file and asks for `--refresh`. The
HTML report's 派工決策表 section shows each source's fetch date and staleness; the scores themselves are in `thoth models`.

## Shared records folder (DT-3)

Three computers can pool what their runs cost and how they ended, so that the
model table looks at all of them. Thoth only writes and reads files; keeping the
folder in step between the computers is not its job.

**Settings.** `machine-name` (`THOTH_MACHINE_NAME`) is this computer's name in
the folder; the default is the host name (`COMPUTERNAME` on Windows, else
`HOSTNAME` or the first line of `/etc/hostname`), with every character outside
`A-Z a-z 0-9 . _ -` replaced by `-`, at most 64 characters, never starting with
`.` or `-`. `config set machine-name` refuses anything that is not already of
that shape; a value from the environment is cleaned up the same way. `records-dir`
(`THOTH_RECORDS_DIR`, kind `text`, default `unset`) is the absolute path of the
shared folder; `config set records-dir` refuses a relative path and does not
create the folder.

**The file.** With `records-dir` set, this computer writes
`records-dir/NAME.jsonl`: one JSON object per run, any role and any status,
from every repository registered on this computer. The file is regenerated whole
from the databases each time (never appended), so the first write covers the
whole history, each run has one line, and a verdict that arrived later is
there. It holds nothing that changes without the databases changing: the same
database contents give the same bytes. Only this file (and its `.tmp-PID`
sibling while it is being replaced) is created, replaced or written; no other
file in the folder is read for writing, deleted or renamed, and a file written
under an old machine name stays. The folder is never created.

**When it is written.** By the runner after every run ends (after the run and
task are settled), by `thoth review record`, and by `thoth records export`. A
failure never changes a run's outcome: the runner logs `records export failed:
...` in the run's `runner-error.log`, and `review record` prints one `warning:`
line on stderr and its stdout is unchanged.

**The fields.** The list is closed (no other key is ever written) and every
key is always present; a missing value is null. One line each:

- `v`: the format version, 2 (Breaking change, RJ-3; it was 1).
- `machine`: this computer's name (`machine-name`).
- `repo_id`: the repository's id in Thoth's global database.
- `repo`: the last component of the repository's path, never the whole path;
  null when there is none.
- `run_id`: the run.
- `task_id`: the task the run belongs to.
- `task_title`: the task's title; null when the run has no task row.
- `attempt`: the run's attempt number within its task.
- `role`: `implementer` or `reviewer`.
- `profile`: the account the run used.
- `provider`: the provider of that account.
- `harness`: the profile's harness (`claude-code`, `codex`, `antigravity`); null
  when the profile no longer exists.
- `model`: the model the run used.
- `effort_requested`: the effort level asked for; null for a run that has no
  `launch` record.
- `effort`: the effort level the harness was sent; null for a run that has no
  `launch` record.
- `task_type`: from the run's newest `launch_choice` event, else the task's
  spec; null when neither has one.
- `difficulty`: from the same two places as `task_type`.
- `risk`: from the `launch_choice` event, else the task's risk.
- `status`: the run's status.
- `interrupted_reason`: why the run was interrupted, if it was.
- `exit_code`: the harness's exit code, if known.
- `started_at`: when the run started.
- `ended_at`: when the run ended.
- `verdict`: the verdict of the run's latest review, as the implementer or as
  the reviewer; null when there is none.
- `tokens`: an object with `input`, `cache_read`, `cache_write`, `output`,
  `reasoning` and `total`, each a number or null.
- `quota`: null, or an object from the run's newest `run_quota` event with
  `five_hour_points`, `seven_day_points`, `reliable`, `unreliable_reasons` and
  `source`.
- `reason`: why this profile, model and effort were chosen (`--reason`): the
  `reason` of the run's newest `launch_choice` event; null when the event has
  none or it is not a string, and for a run without such an event.

Breaking change (RJ-3): the line no longer has `recommended`, `deviates` or
`exempt`, and no key replaces them. An older run's `launch_choice` that still
carries them is read for its `reason` only.

Deliberately left out, and never written: the spec (of the task and of the
run), the prompt, error text, code, the conversation, session ids, login data,
the worktree, run directory and config directory, the candidate commit and the
base commit, the allowed tools, the review findings, and every path (the
repository is only its last component).

**`thoth records export [--json]`** writes the file now (for example right
after setting `records-dir`) and prints `ok`, `path`, `machine`, `lines` and
`repos` (`wrote N run(s) from M repositor(y/ies) to PATH` without `--json`). It
exits 1 when `records-dir` is not set (`records-dir is not set; ...`), when it
is not a directory (`records-dir PATH is not a directory; ...`), or when
`THOTH_RUN_ID` is set: it is for the human operator or the commander, not for a
worker.

**Syncing.** How the computers share the folder is up to you: the usual way is
a git repository that each computer clones into `records-dir`; pull before
starting work, and commit and push the changed file when you finish.

**Reading.** `thoth models` merges the other files as described under "Model
inventory and scores": files are read in name order; a line that does not parse
(a blank line included) or whose `v` is neither 1 nor 2 is counted in
`skipped_lines` (a v1 line, from a computer whose thoth is not rebuilt yet, is
read and its `recommended`, `deviates` and `exempt` ignored); the
`machine` of a file is its name minus one trailing `.jsonl`; and a folder that
cannot be read leaves `records.error` set and the totals local. `thoth doctor` puts
`machine_name` and `records_dir` (`{value, source, exists}`) in the `config`
item's data and reports `warn` with a fix when `records-dir` is set and is not a
directory.
